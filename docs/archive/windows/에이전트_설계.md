## 1. 정한 스펙과 이유

### 1.1 언어·의존성

- **Rust, 손으로.** 사용자 지시("랭체인 랭그래프는 안 쓰고 직접 러스트", "웬만하면 C++·Rust, 라이브러리 쓰다 보면 이상한 병목").
  웹소켓(RFC 6455)·msgpack·HTTP/1.1·base64·SHA-1 을 직접 짰다.
- 남긴 크레이트 4개와 이유:
  - `serde`/`serde_json`: JSON 직렬화의 표준. 직접 짜 봐야 이득이 없다. `float_roundtrip` 기능을 켰다 — 기본 파서는 실수 마지막 자리가 1 ULP 틀릴 수 있어 재생 때 맥락 글이 달라졌다(6절).
  - `jpeg-encoder`: 의존성 없는 순수 Rust. 경계 때만 쓴다.
  - `libc`: `poll(2)`(계획 중 ping 응답), `TCP_QUICKACK`.
- **HTTPS 는 시스템 `curl` 을 부른다**(KAU API). TLS 크레이트(rustls·ring)를 들이지 않으려고. 경계에서만 부르므로 프로세스 띄우는 수 ms 는 LLM 응답(수 초)에 묻힌다. 키는 표준입력 설정(`-K -`)으로 넘겨 명령줄에 안 보인다(`llm.rs` `curl_post`).
- **C++/CUDA 로 간 것은 없다.** 에이전트 쪽에 GPU 로 갈 계산이 없다: LLM 은 서버(KAU vLLM 또는 llama.cpp CUDA)가, 영상 축소·JPEG 는 경계 때만 CPU 로 약 7 ms(5절). 물체 지도·이름 찾기는 scenemap(C++/CUDA, 같은 프로세스 C ABI)이 한다. 대량 유사도 계산이 이쪽으로 오면 손으로 짠 CUDA 로 간다.
- 실행은 WSL(ROS 2·π0.5 와 같은 곳). Windows 에는 Rust 를 깔지 않았다 — 평가기(Windows)는 웹소켓으로 WSL 의 중계기에 붙기만 하면 된다.

### 1.2 LLM 연결 — OpenAI Chat Completions 원형

- 사용자 지시 "툴콜링 메모리 서머리 와일 등등 openai 에서 준 거". 요청 `messages`(system/user/assistant/tool)·`tools`·`tool_choice:auto`, 응답 `tool_calls`, 결과는 `role:"tool"` + `tool_call_id` (`llm.rs`).
- assistant 메시지는 **표준 필드만** 남긴다(`reasoning_content` 등은 다음 요청에 안 보냄) — 수업 week02 `assistant_message_to_dict` 와 같은 이유. 생각 글 길이는 기록에만.
- 서버가 도구 호출을 못 풀고 `<tool_call>{…}</tool_call>` 글로 돌려주면 도구 호출로 바꾼다(Qwen 원형 대비). `<think>` 는 지운다.
- 대상: 지금은 **KAU API**(`https://agent.kau.ac.kr/v1`, 모델 `qwen3.5-9b`, vLLM, 문맥 16k, GPU 안 씀)로 시험. 로컬 llama.cpp(`http://127.0.0.1:8081/v1`, 문맥 8192)도 같은 코드.
- **키는 환경변수로만**: `KAU_BASE_URL` `KAU_API_KEY` `KAU_MODEL`(WSL `~/.config/behavior-2026/kau.env`, 저장소 밖). 코드·인자·기록에 키가 없다(기록에는 요청 메시지만, 머리글은 안 남김).
- **결정론**: 요청마다 `temperature 0, top_p 1, top_k 1, min_p 0, presence 0, frequency 0, repetition(repeat)_penalty 1, seed 0` 을 명시한다(llama-server 기본 presence 1.5 등은 도구 JSON 을 망칠 수 있어 반드시 덮음). 생각 모드는 `chat_template_kwargs.enable_thinking=false`. 요청 지문(sha1 16자리)을 기록한다.
  - 실측: KAU 로 같은 계획 요청 3번 → 결정 3번 모두 같음(5절). 공유 vLLM 이라 비트 재현은 보장되지 않는다(추정).
- 한 번 호출 제한 60 s, 한 경계 전체 120 s(`decision_budget_s`). 평가기 웹소켓 `ping_timeout=300`(OmniGibson `eval/utils/network_utils.py` `_wait_for_server`)보다 훨씬 짧다. 게다가 중계기가 계획 중에도 ping 에 답하므로(1.10) 끊기지 않는다.
- 로컬 모드 전용 훅: `--llm-up-cmd` `--llm-down-cmd` `--llm-health` — 16 GB 에 시뮬레이터·π0.5·Qwen 이 다 안 들어갈 때 계획할 때만 서버를 올리고 결정·요약 뒤 내린다(`ManagedLlm`). API 모드에서는 쓰지 않는다(쓰면 오류).

### 1.3 결정 인터페이스 — 상태(Core)와 결정기(Decider)를 나눔

- plan.md 0절(나중에 강화학습 플래너로 바꾸거나 병행). `Decider::decide(&mut Core, &BoundaryEvent) -> Decision{Issue|Continue|Finish}`.
- `Core` 가 상태를 다 가진다: 단계 기록, 계획 체크리스트, 물체 기억, 손에 든 것, 참조 풀기·예산·문장 만들기(`make_instruction`). 결정기를 바꿔도 그대로다.
- 결정기 2개: `LlmDecider`(도구 호출), `PriorDecider`(LLM 없이 참고 순서만 따름 — 기준선이자 강화학습 결정기의 본보기).
- 강화학습 입력: `Core::decision_input()` = 구조화된 상태(과제 번호, 트리거, 자세, 그리퍼, 지금 단계·시도 횟수, 계획 진행, 물체 표(로봇 기준 앞·왼쪽, 움직인 거리, 다룬 횟수)). **매 경계 기록에 들어가므로 기록이 곧 (상태, 결정) 학습 데이터**다.

### 1.4 언제 부르나 — 경계 5가지(`monitor.rs`)

| 트리거 | 조건(기본값) | 이유 |
|---|---|---|
| 판 시작 | 판의 첫 관측 | 첫 단계 |
| 예산 소진 | 이 단계 스텝 ≥ 예산(시연 p90 × 1.5, 1.9) | 막힘·실패 |
| 정기 확인 | 예산의 1/3 마다(최소 60 스텝) | 3위 팀 방식의 확인(arXiv 2607.06256 초록 "decide whether execution should advance, retry, or replan") |
| 이동 멈춤 | 이동 단계에서 0.3 m 넘게 움직인 뒤 20 스텝 연속 0.03 m/s·0.05 rad/s 미만 | 도착 가능성 |
| 그리퍼 변화 | 그리퍼(두 손가락 합) 0.07 m 아래 ↔ 0.09 m 위 가 10 스텝 유지(이동 단계 제외) | 잡기·놓기 가능성 |

- 두 경계 사이 최소 15 스텝. 그리퍼 범위 근거: 시연 `meta/stats.json` 손가락 하나 0~0.05 m.
- LLM 은 이때만. 과제당 시연 단계 중앙 17(π05 문서 2.6) + 확인 몇 번 정도.

### 1.5 지시 계약 — 형식 4가지와 토큰 예산

- `Instruction{skill, objects(id), names(표시 이름), spatial, memory, purpose, expected, metric, budget}` → 문장(`instruction.rs`).
- 형식(plan.md 4.1 비교용, `--format` 으로 바꿔 끼움):
  ① `task` 과제 문장 그대로 ② `subtask` 시연 주석 어휘 문장 "pick up radio from coffee table"(기본) ③ `purpose` "Purpose: … . Expected action: … ." ④ `metric` ② + "go forward 2.1 m, 0.4 m to the left, turn left 30 degrees"(실험 전용, 아래).
- 단계 이름 35종과 문장 틀은 시연 주석의 물체 칸 순서를 따른다(`vocab.rs`; 예 chop = [칼, 자를 것], place on next to = [놓을 것, 받침, 기준]). 공간 수식어는 칸별(`to_the_edge_of` → "to the edge of", `right_door` → "the right door of").
- **토큰 예산 90**: π0.5 는 `"Task: {문장}, State: {상태};\nAction: "` 을 200 토큰에서 자른다(openpi `models/tokenizer.py:22-45`, `pi0_config.py` `max_token_len=200`). PaliGemma 토크나이저로 잰 값: 상태 25차원(openpi `configs/robots/b1k.py` proprio)이면 빈 문장일 때 101 토큰 → 문장 몫 99. 여유를 두고 90. Comet 설정처럼 상태 23차원이면 몫이 더 크다.
  - 추정기(단어 1 + 숫자 한 자리 1 + 공백 뒤 숫자 +1 + 문장부호 1 + 9자 넘는 단어 +1)에 10%+1 여유를 더해 비교(`util.rs` `tokens_with_margin`).
  - 검증: 과제 8개 × 형식 4가지 556문장을 실제 토크나이저로 셌다. 추정만으로는 39개가 1~2 토큰 모자랐고, 여유를 더하면 모두 실제 이상. 실제 최대: task 56, subtask 12, purpose 26, metric 36(`render` 명령 + openpi venv sentencepiece).
  - 넘으면: purpose → expected 빼기 → 과제 문장 대신 → 단어 자르기. metric → 숫자 빼기.
- **π0.5 에 숫자 명령을 쓰지 않는다**(사용자 결정 2026-09-29).
  - 근거: 지시 형식 오프라인 실험(Comet pt50)에서 숫자 명령이 이동 방향 일치를 오히려 낮췄다(cos 0.71 → 0.54).
  - 기본 형식은 ② subtask 다. ④ metric 은 실험 전용이다: `--format metric` 을 줄 때만 쓰고 경고를 찍는다. 중계기 agent 모드에서는 거부한다(`--allow-metric-experiment` 를 같이 줄 때만 허용).
  - ②③ 문장에서는 거리·각도 숫자를 거른다(`instruction.rs` `strip_numbers`: 숫자가 든 낱말과 바로 뒤 단위를 지우고, 매달린 "by/of/to" 를 뗀다). 그래서 LLM 이 purpose/expected 에 "walk 2 meters" 를 써도 π0.5 에는 "walk" 만 간다. 시스템 글과 도구 설명에도 "숫자 거리·각도 금지"를 적었다.
  - 그래프 좌표와 오도메트리는 계획기 안쪽 판단(자동 증거·완료 판정·가까운 물체 고르기)에만 쓴다. ④ 를 실험할 때의 숫자는 LLM 이 아니라 계산으로 만든다(목표 앞 0.7 m, `planner.rs` `nav_metric`).
- **문장이 π0.5 를 얼마나 움직이나**: 지시 형식 오프라인 실험에서 공식 radio 체크포인트와 Comet pt50 모두 문장 내용을 거의 따르지 않았다(문장을 바꿔도 행동 변화가 잡음 수준, plan.md 4.1). 따라서 재학습 전까지는 에이전트가 문장으로 π0.5 를 이끄는 효과가 작다. 결정기·기억·복구 설계는 그대로 두고, 재학습(단계 문장으로 학습한 π0.5) 뒤에 효과를 잰다.

### 1.6 참조 풀기 — `back`·`the other`·손에 든 것

- 물체 기억(`graph.rs` `ObjectMemory`) = 그래프 노드 위에 에이전트가 얹는 기억: 처음 자리, 마지막 자리, 우리가 성공시킨 조작 횟수, 그래프가 본 다룸 여부.
- `back` = 처음 받침. 순서: 그래프 `on` → BDDL `:init` 받침(`bddl.rs`) → 처음 자리(scenemap `first_position`)에 가장 가까운 물체.
- `the other` = 같은 종류 중 다루지 않은 것(그래프 `handled` 또는 우리 조작). **지금 단계의 물체(방금 다가간 캔)가 조건에 맞으면 그것이 먼저** — 시연 순서가 "move to the other can → pick up the other can" 이라 둘이 같은 캔이다. `move to` 는 다룸으로 치지 않는다.
- 이름만 준 물체: 놓기 단계의 첫 물체는 **손에 든 것 먼저**, 집기·이동은 **안 다룬 것 먼저**, 그다음 가까운 순. 이전 단계를 "끝남"으로 보고하면 다음 단계 참조를 풀기 **전에** 손에 든 것부터 갱신(방금 집은 캔 → "place can in trash can" 의 캔).
- 그래프에 아직 없는 물체·방 이름은 이름 그대로 보낸다(탐색용 "move to living room").

### 1.7 자동 증거와 되묻기

- 실제 Qwen 은 증거가 분명해도(그리퍼가 물체에 닫힘, 물체 0.35 m 들림) "partial" 로 판단하고 같은 단계를 되풀이했다(5절 첫 실험). 그래서
  경계 글에 **"Automatic check: LOOKS DONE/FAILED/STILL IN PROGRESS/UNCLEAR — 근거"** 한 줄을 넣는다(`Core::evidence`):
  이동 = 목표 1.2 m 안에서 멈춤, 집기 = 그리퍼가 물체에 닫힘 + 물체 0.1 m 넘게 들리거나 0.15 m 넘게 움직임(0.005 m 아래로 닫히면 실패), 놓기 = 그리퍼가 열리고 물체가 받침 0.6 m 안.
- LLM 이 증거와 반대로 같은 단계를 다시 보내거나 계속하려 하면 **한 번 되묻는다**(오류 관찰값). 같은 호출을 한 번 더 하면 그대로 따른다. 결정은 LLM 몫으로 남긴다.
- 결정적 대체(`Core::fallback`)도 같은 증거를 쓴다.

### 1.8 기억·요약 규칙(`memory.rs`, 수업 week03 확장)

- 맥락 = **system 메시지 하나**(역할·규칙 + 과제·BDDL 목표·처음 자리 + 참고 순서 + 계획 체크리스트 + 요약 + 사실 + 단계 기록 최근 12줄 + 물체 표 25줄 + 지시 형식) + 최근 turn + 이번 사건 user 메시지(머리 카메라 영상).
  llama.cpp·vLLM 의 Qwen 템플릿이 맨 앞 system 하나만 제대로 다루는 점은 week03 `build_context` 와 같은 이유.
- turn = 경계 하나(사건 user + assistant 도구 호출 + tool 결과). 최근 3개는 원문(영상은 "[image]"로 바꿔), 창 밖으로 나간 것이 3개 쌓이면 LLM 에 요약을 시켜 합친다.
  요약 요청은 week03 `turn_to_text` 처럼 도구 메시지를 사람이 읽는 대화록으로 바꿔 보낸다. **요약은 결정을 돌려준 뒤** 계획기 스레드에서 한다(지연 경로 밖). 요약이 실패하면 단계 기록으로 결정적 요약.
- 요약에 아직 안 들어간 창 밖 turn 은 요약될 때까지 원문으로 남겨 정보 틈이 없게.
- `remember` 로 남긴 사실(최대 20개)은 요약과 따로 계속 보인다.
- 맥락 예산 9000 토큰(추정). 넘으면 참고 순서 2·3위 → 물체 표 15줄 → 오래된 turn 순으로 줄인다. 실측 요청 2.8k~7.5k 토큰(5절). 로컬 llama.cpp(8192)면 `--ctx-budget 6000`.

### 1.9 참고 순서 라이브러리 — 과제 카드(`catalog.rs`, `assets/tasks.json`)

- `bagent build-assets` 가 시연 주석 83과제 16,561판(`data/2026-challenge-demos/annotations`)을 17 s 에 읽어 과제마다
  **정확히 같은 순서 상위 3개(빈도 포함)**, 1위 비율이 20% 미만이면 **메도이드**(다른 판들과 편집거리 합이 가장 작은 판)를 넣는다.
  가장 흔한 순서의 비율 중앙값: 단계 이름만 0.51, 물체 종류·기억 수식어까지 0.40.
- 단계별 스텝 예산 = 시연 길이 p90 × 1.5(최소 90). 예: move to 1,620, pick up from 1,395, place in 1,080, open door 2,115 스텝.
- 카드에 번호·지시문·제한시간(사람 평균 × 1.5 = 평가기 `evaluator.py:279`)·방·BDDL(목표·처음 자리)도 넣는다. 평가 때는 이 JSON 하나만 있으면 된다.
- LLM 맥락에는 1위 순서 전부와 2·3위(30단계 이하일 때)를 "참고"로 넣고, 체크리스트는 1위로 채운다. LLM 은 순서 조정·물체 고르기·실패 복구를 맡는다.

### 1.10 다리(중계기) — 평가기 ↔ 중계기 ↔ π0.5

- **평가기 관측에는 prompt 가 없다**(OmniGibson `evaluator.py:576-592` `_preprocess_obs` 는 관측·`cam_rel_poses`·`task_id` 만). π0.5 문장은 서버 시작 때 고정(openpi `shared/eval_b1k_wrapper.py` `text_prompt` → `process_input` 의 `"prompt"`).
  → 중계기가 관측 맵 **끝에** `__agent_prompt__`(배치면 환경별 목록)와, 지시가 바뀐 스텝이면 `__agent_flush__` 를 덧붙이고,
  π0.5 서버 훅(`tools/serve_b1k_agent.py`)이 꺼내 쓰고 지운다. 원래 항목 바이트는 그대로, 맵 머리의 항목 수만 바뀐다.
  훅이 없는 서버는 모르는 키를 무시한다(`process_input` 이 정해진 키만 읽음).
- flush: 지시가 바뀌면 남은 행동 묶음(receding horizon 16 중 남은 것)을 버리고 바로 새로 추론(receding_horizon 모드만).
- **zero-copy**: 평가기 프레임(클라이언트 → 서버라 XOR 마스크됨)을 풀지 않는다. 맵 머리 길이가 바뀐 만큼 마스크 키를 회전(`ws::rotate_key`)해 원래 바이트를 그대로 다시 보낸다. 필요한 값(base_qvel·그리퍼·task_id)만 제자리에서 XOR 해 읽는다(`msgpack::Masked`). 큰 영상에 CPU 패스 0회.
- **흘려보내기(cut-through)**: 경계가 아닌 스텝은 프레임 머리를 받자마자 새 머리를 보내고 몸통은 받는 조각마다 바로 쓴다. 문장은 이전 스텝에 정해져 있어 꼬리를 미리 안다. 다 받은 뒤에 훑어서 오도메트리·감시.
- **붙잡기**: 스텝 수로 정해지는 경계(판 시작·예산·정기 확인)가 올 스텝, 사건 경계(이동 멈춤·그리퍼)가 난 **다음** 스텝은 통째로 받아 두고 계획 뒤 보낸다. 사건 경계는 1스텝(1/30 s) 늦게 반영된다. 작은 프레임(reset)도.
- **pause(기본)**: 결정이 올 때까지 이번 관측을 붙잡는다 → 시뮬레이터 시간 정지(점수는 시뮬레이터 스텝 기준), 결정 재현 가능. 그동안 `poll(2)` 로 두 소켓의 ping 에 답한다(평가기 300 s, π0.5 서버 websockets 기본 20 s). `--no-pause` 면 붙잡지 않고 결정이 도착한 스텝부터 바꾼다(벽시계 0, 재현은 기록으로만).
- **TCP_QUICKACK**: 소켓을 읽을 때마다 다시 건다. Windows 평가기 → WSL 경계의 약 40 ms 대기가 사라진다(5절). `BAGENT_NO_QUICKACK=1` 로 끔.
- 배치 평가(`--num-envs`): 배열 맨 앞 차원 = 환경 수. 환경마다 세션·에이전트·문장. 동시에 경계가 난 환경들은 계획기 스레드가 병렬로.
- `/healthz` 는 뒤쪽 π0.5 서버가 살아 있을 때만 200(평가기가 먼저 부른다).
- 평가기가 연결될 때 서버가 먼저 보내는 metadata 는 그대로 넘긴다. reset 은 응답이 없다.

### 1.13 평가기 연결(link) — 중계기 대신

- π0.5 가 평가기 프로세스 안으로 들어가면서(네이티브 C++/CUDA 엔진, 검은 화면 (A) 때문) 웹소켓 중계기(1.10)가 낄 자리가 없어졌다.
  - 계획기의 Core·Decider·경계 감시(`EnvSession`)는 그대로 쓴다. 전송층만 새로 짰다(`link.rs`).
  - 평가기 안 파이썬 접착부(`src/integ/glue/simlink_policy.py`)가 TCP 하나로 붙는다. 머리 12 B + 몸통 형식이다.
- 스텝마다 요약(proprio 61)을 보내고 답을 기다리지 않는다. ACK(`hold_next`·`want_next`)는 다음 스텝 첫머리에 읽는다.
  - 경계 스텝만 WAIT 로 보내 결정을 기다린다. 시뮬레이터 시간 정지는 중계기 pause 와 같다.
  - 사건 경계를 1스텝 늦게 붙잡는 것도 중계기와 같다.
- 결정 → 접착부: `prompt`(단계 문장 모드일 때만), `flush`, `stage`(단계 번호, `StageTrack`: 계획 진행률 × 과제 단계 수), `stage_mode`.
  - 기본은 과제 문장 고정 + 단계 번호다(plan.md 4.1 (다)+(라)).
- 위치: `PoseEstimator`(`pose.rs`). 적분(= `odom.rs`)이 기본이고, 바깥 추정기 고정점을 보정으로 받는다(`Corrected`).
  - `BoundaryEvent.pose` 는 이 추정값이다.
- 카메라 외부 자세: proprio 관절값 + R1Pro URDF 순기구학(`fk.rs`). 평가기 `cam_rel_poses` 는 안 쓴다.
- 관측 내보내기는 `ObsSink` 뒤에 있다. 이 크레이트는 ROS 를 모른다.
  - `bagent link` 는 세기만 한다(`NullSink`). ROS 발행은 WSL 노드 `src/integ/simlink`(r2r)가 한다.
- 명령줄 → 에이전트 공장은 `setup.rs` 로 옮겼다. `bagent relay` 와 simlink 가 같이 쓴다.
- 자세한 스펙·실측·실행은 [통합_실시간.md](통합_실시간.md) 에 있다.

## 3. 메시지 흐름

```
평가기(Windows, OmniGibson) ──ws──▶ 중계기(WSL, Rust) ──ws──▶ π0.5 서버(WSL, openpi + 훅)
   관측(msgpack, 마스크)            │ 매 스텝: 머리 다시 쓰고 흘림, base_qvel·그리퍼 읽기          │ __agent_prompt__ → prompt
   ◀────────── 행동(그대로) ────────┘ 경계: 붙잡고 ▶ 계획기 스레드 ─▶ LLM(KAU/llama.cpp)        │ __agent_flush__ → 바로 추론
                                                 └▶ 씬그래프(`SceneGraph`)
```

경계 하나의 LLM 메시지 배열:

```
[system]  역할·규칙(prompts/system.md) + 과제·BDDL 목표·처음 자리 + 참고 순서 + 체크리스트 + 요약 + 사실 + 단계 기록 + 물체 표 + 형식
[최근 turn 들]  user(지난 사건, 영상은 "[image]") / assistant(tool_calls) / tool(결과) …
[user]    "Boundary at step 298 of 3224 … Trigger: … Current step #2 … Grippers now: … Automatic check: LOOKS DONE — … " + 머리 영상
[assistant] tool_calls: graph_query(...)            ← 필요할 때만
[tool]      {"status":"ok","matches":[…]}
[assistant] tool_calls: issue_command(previous="done", skill="press", objects=["radio_89"], …)   ← 끝내는 도구
[tool]      {"status":"ok","sent":"press radio","budget_steps":…}
```

반복 한도 8번, 도구 없이 글만 오면 재촉(2번까지), 인자 JSON 오류·모르는 단계 이름·재시도 한도 초과는 오류 관찰값으로.
결정 뒤: 단계 기록 닫기 → 체크리스트 상태 → 다룸 표시(그래프에도) → 손에 든 것 → 새 단계 열기 → (스레드에서) 요약 → 로컬 모드면 서버 내리기.

## 6. 시험

  5. LLM 이 계속 오류여도 대체 결정으로 radio 성공. 6. 잘못된 도구 인자·모르는 단계 이름·글만 답 → 오류 관찰값, 대체 없이 성공.

## 7. 실행 방법

WSL, 크레이트 폴더 `/mnt/c/behavior-2026/src/agent`. 빌드 산출물은 WSL 쪽에(`/mnt/c` 빌드는 느림).

```bash
export PATH=$HOME/.cargo/bin:$PATH CARGO_TARGET_DIR=$HOME/cargo-target/agent
cargo test --release                      # 49개
cargo build --release; B=$CARGO_TARGET_DIR/release/bagent
$B build-assets --root /mnt/c/behavior-2026         # assets/tasks.json 다시 만들기(17 s)

$B sim --scenario trash --llm kau --no-images       # 가짜 세계 + 실제 Qwen
$B replay runs/<폴더>/trace.jsonl [--verify] [--html 1]
$B bench-local --mode agent [--rgbd] [--no-stream]  # 중계기 지연
```

실제 평가(시뮬레이터는 다른 에이전트 담당, GPU 사용 전 `nvidia-smi` 확인):

```bash
         --format subtask --trace-dir runs/eval_radio

```

평가기 안 π0.5(지금 경로): `bagent link --listen 0.0.0.0:7801 --llm kau`(관측은 세기만). scenemap 까지 잇는 한 판은 simlink(`--graph scenemap`)로
