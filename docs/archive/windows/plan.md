# 구현 계획 — 토론하면서 고쳐 나가는 문서

근거 자료는 [docs/](../../README.md). 정한 것은 6절, 안 정한 것은 4절, 진행은 5절.

## 0. 핵심 아이디어

**동적 3D 씬그래프 + AI 에이전트(또는 강화학습) + VLA 의 결합.**
- 동적 씬그래프(scenemap, 새로 만듦): 2D SLAM 지도 + YOLOE 로 찾은 물체를 깊이로 3D 위치에 등록·갱신 → 기억.
- AI 에이전트(Qwen): 그 그래프로 긴 계획·단계 추적·실패 복구. 결정기는 LLM 과 분리돼 있어 강화학습 결정기로 바꿔 끼울 수 있다.
- VLA(π0.5): 지금 단계 지시 + 카메라로 행동.
- 구현 원칙: **병목 제로.** C++/CUDA 를 손으로(라이브러리는 뜻밖의 병목), 조율은 Rust, PyTorch 안 씀.

## 1. 스펙

| 층 | 내용 | 코드 |
|---|---|---|
| **입력** | 카메라 3대 RGB + depth → scenemap: 깊이 가상 스캔으로 2D SLAM(지도·위치), YOLOE(과제 BDDL 물체 이름 프롬프트)로 물체 검출 → 깊이로 3D 위치 → 물체 지도 등록·갱신. 계획기는 같은 프로세스 C ABI 로 조회. 과제 지시·BDDL 목표도 입력 | `src/scenemap/`, `src/ovdet/` (설계 `docs/scenemap_설계.md`) |
| **판단** | Qwen3.5-9B(지금은 KAU API). 단계 경계에서만 호출(판 시작·예산 소진·정기 확인·이동 멈춤·그리퍼 변화). 도구 호출·기억·요약, 시연 대표 단계 순서 참고. `back`/`the other` 는 그래프로 풀어 구체 물체로 | `src/agent/` (Rust) |
| **제어** | π0.5 가 단계 지시 문장 + 카메라 3장 + 관절 상태로 행동 묶음. 숫자 명령 금지. 추론은 네이티브 C++/CUDA 엔진으로 평가기 프로세스 안에서 | `src/pi05_native/` |

## 2. 구조

```
평가기 ── 관측(RGB·depth·proprio·cam_rel_poses) ─▶ [중계기(Rust)] 관측 바이트 그대로 + 지시 문장 키 덧붙임
                                                    ├─ 매 스텝: 흘려보냄(LLM 없음), base_qvel 적분·경계 감지
                                                    └─ 경계: 에이전트 ─ scenemap(2D 지도 + 물체 지도) ─ Qwen
π0.5 ◀── 관측 + 지시 ──┘   → 행동 묶음 → 평가기
```

- 평가기는 두 개를 나란히 둔다: **원본**(공식 v3.9.3 그대로, 제출 수치용)과 **포팅**(우리 엔진 + 네이티브 π0.5, 개발 실험용). 같은 입력·같은 결과 JSON, `compare` 로 대조.
- 실험 실행기: `tools/exp_run.ps1` (`run` / `compare` / `table`, `-Backend original|ported`, 검은 프레임 나오면 그 판 무효).

## 3. 사실 (설계가 기대는 것)

- **대회 환경**(원문): 성능 측정 장비 RTX 4090 · Ryzen 9 7950X · Ubuntu 22.04.5, 최종 평가 GPU "RTX 3090, A5000, and TitanRTX"(상위 5팀, 비공개 인스턴스). 리더보드는 공식 평가기로 공개 인스턴스 0~9 를 한 번씩 돌린 **자체 보고**(검증 0건). 현재 1위 Autolab 0.322, 2위 0.211, 3위 0.127.
- 관측 제한: RGB·depth·proprio 만. 로봇 전역 위치 금지 → base_qvel 적분. 학습 때는 정답 정보 사용 가능. BDDL 과제 정의는 평가 때도 같다.
- **π0.5 는 지금 가중치로는 문장 내용을 거의 따르지 않는다**(오프라인 실험, radio 시연 160 표본 × 7 형식, `logs/probe_*_20260929_*.md`):
  - 공식 radio 체크포인트: 시연 오차 작음(이동 0.011, 이동 방향 cos 0.96). 문장을 바꿔도 변화가 잡음 수준(①' 0.0050 vs 다른 형식 0.0055~0.0070).
  - Comet pt50: 오차 약 2배. 문장 변화 역시 잡음의 1.0~1.6배, 숫자 명령은 방향이 오히려 나빠짐.
  - 2026 데모로 openpi 를 학습하면 문장이 과제 이름("turning on radio")이고 서빙은 긴 문장 — radio 체크포인트는 두 문장에 거의 같은 행동.
- π0.5 메모리: 모델 6.4 GiB, 프로세스 약 8.7 GB, 추론 약 115 ms / 32 스텝 묶음.
- **검은 화면(이 Windows PC)**:
  - (A) 다른 프로세스가 GPU 를 약 5 GiB 넘게 잡으면 RTX 컬러 출력이 통째로 빈다(깊이 정상). 같은 프로세스 안 메모리는 괜찮다 → π0.5 를 평가기 프로세스 안(네이티브 엔진)으로.
  - (B) 다른 프로세스가 없어도 OmniGibson 큰 장면에서 카메라 일부가 3 스텝 주기로 빈다(판마다 운, 늦은 프레임이 아니라 안 채워진 버퍼). 렌더 설정으로는 안 없어짐. 원인 조사 중.
  - Windows Docker/WSL 에는 NVIDIA Vulkan 이 없어 시뮬레이터 렌더 불가("The Isaac Sim container is only supported on Linux").
- 통신: Windows 평가기 ↔ WSL 서버 왕복을 TCP_NODELAY + TCP_QUICKACK 으로 32 → 4 ms.
- 시연 단계 순서: 과제마다 가장 흔한 순서의 비율 중앙 0.51. 100과제 중 유체·천 0, 물리 입자 6, 입자 없음 80.
- 평가 속도(원본): 약 7~10 스텝/초, 장면 로딩 약 2 분.
- **Windows 공식 ≠ Linux 공식(비트)**: 같은 행동열로 스텝 0 부터 다르다(robot_qpos 최대 1.5e-4, qvel 0.15). JSON 은 success·q_score·steps 가 같고 이동 거리만 약 0.5% 차이. Linux 공식은 반복 실행이 비트 동일 → 비트 기준은 Linux, 이 PC 수치는 근사.
- 이 PC 디스크: C: 931 GB 에 WSL 디스크(194 GB)까지 얹혀 여유가 적다. 공간이 모자라면 윈도우 저장 공간 센스가 %TEMP% 를 청소해 공식 평가기의 og.tempdir 가 지워지고 평가기가 죽는다(09-29 23:57 실제 발생, WSL 테스트 segfault 덤프 18 GB 가 주범이라 지움).

## 4. 쟁점

### 4.1 π0.5 가 지시를 따르게 하기 — 우리 구조의 핵심 위험
- 3절대로 지금 가중치는 단계 문장을 거의 무시한다 → 에이전트가 문장으로 π0.5 를 이끌 수 없다.
- 선택지:
  - (가) 시연 주석의 단계 구간에 단계 문장을 붙여 π0.5 재학습(데이터 파이프라인은 준비됨: `src/fasttrain`). 외부 GPU 필요(LoRA 도 22.5 GB 초과).
  - (나) 이동은 계산 제어기(그래프 좌표 + 오도메트리), 조작만 π0.5.
  - (다) 과제 단위로 쓰고 에이전트는 기억·복구(재시작, 과제 문장 전환)만.
- (라) **단계 번호 통로**: 2025 1위 모델은 문장 대신 과제 임베딩 + **단계(stage) 입력**으로 학습됐다("Stage tracking with voting logic … passed as input to the model", `refs/behavior-1k-solution/README.md`). 계획기가 씬그래프 기억으로 단계 번호를 정해 넣으면 학습된 통로로 모델을 이끌 수 있다.
- **밤사이 결정(09-29 23:30, 사용자 위임 "알아서 해결해봐")**: (다) 과제 단위 + (라) 단계 번호 통로로 간다. 1위 모델을 네이티브 엔진에 올려 과제 0~49 보험 점수를 먼저 확보하고, 계획기가 단계 번호를 고치는 효과를 잰다. (나) 이동 계산 제어기는 뒤로.
- **학습은 보류**(사용자 결정: "학습은 일단 보류고 최적화까지만") → (가) 재학습은 미룬다. 학습 데이터 파이프라인은 최적화·검증까지만 끝낸다. 숫자 명령은 쓰지 않는다(정함).

### 4.2 검은 화면 (B)
- Fabric 무대 기록 칸 3 → 4(`fabricDefaultStageFrameHistoryCount=4`)는 **해결책 아님**: 공식 평가기 재시험에서 칸 4 판도 오른손목 50/151 이 3 스텝 주기로 검었다(앞선 0/3 은 우연). 물리·판정·JSON 은 칸 3 과 비트 동일 — 해는 없지만 효과도 없어 채택 안 함.
- 해석: 렌더 결과를 3칸 고리로 돌려 쓰는데 한 칸이 안 채워진다(같은 상태에서 render() 를 더 부르면 머리 카메라 검정이 12 중 2 → 8). 그 고리는 Fabric 기록이 아니라 RTX 렌더러 안쪽으로 추정.
- **09-30 보류(사용자 결정)**: 다중 GPU 끔(IsaacSim#507·#509 축)도 효과 없음, 렌더 2회·렌더 완료 대기도 검정 남음. 사용자가 Linux 듀얼 부팅을 준비 → (B) 는 Linux 에서 재현 여부부터 본다. 외부 조사: `docs/archive/조사_검은프레임_외부보고.md`.
- (이전 계획) carb 설정 트리 전수(값 3·frame/inflight/async/waitIdle 류) → 렌더 동기화 후보를 하나씩, 짧은 판 5 연속 0 이면 효과. 전부 효과 없으면 "설정으로 못 고침 → 렌더 가능한 Linux 필요" 확정. 그때까지 이 PC 평가는 검출해 무효 표시·같은 설정 재실행만(점수 보고 고르기 금지).
- **10-02 리눅스(RTX 4090, 드라이버 580) 확인 — (B) 없음 확정**: radio 0 행동 5 판 연속 0/151, nf_a 재생 2 판 0/501(카메라 3 대 모두). (B) 는 Windows 쪽 문제 → 제출용·비트 기준 평가는 리눅스 PC 에서 한다([docs/Linux_설치.md](../../Linux_설치.md)).
- 네이티브 π0.5 평가기 안 실행(기본 설정)에서도 (B) 는 그대로: 머리·왼손 각 100 프레임, 전부 스텝 번호 mod 3 = 1.

### 4.3 Linux GPU 장비
- 대회 환경 기준(평가 수치·엔진 정답지·렌더 비교), 재학습, 대량 평가에 필요. 지금은 WSL 에 Linux Isaac Sim 을 설치해 물리 기준만 뜨는 중(렌더는 WSL 불가).

### 4.4 위치 추정 (평가 때는 GT 금지 → 실시간 추정)
- 실측(원본 HDF5 GT, 13 에피소드): **base_qvel 적분만으로는 크게 틀어진다** — 이동 10 m 에서 중앙 1.16 m(최대 2.9 m), 에피소드 끝 중앙 1.6 m(최대 9.7 m), yaw 최대 166°. 기록 각속도가 실제 회전보다 크다(비율 0.88~0.97, 에피소드마다 다름).
- 대응: 깊이 기반 보정(keyframe 깊이 점 → 정적 지도 point-to-plane, 평면 3자유도) CPU 시제품 → 손 CUDA. 카메라 외부 자세(robot2cam)는 정확해 그대로. 통합 쪽 위치 추정기는 교체 가능한 자리로.

### 4.5 평가량·보험
- 원본 평가기로 1,000 판은 PC 한 대로 수백 시간. 보험: 2025 1위 가중치(과제 0~49, 받아 둠)로 점수 확보 — 유효한 평가 환경이 먼저.

## 6. 정한 것

- 연결: π0.5 + scenemap 은 단계 지시로. 인지 스택은 새로 만든 scenemap(2D SLAM + YOLOE 물체 지도, 사용자 팀 robot-programming-team 의 plan·model_selection 을 따름).
- 계획기 LLM: 지금은 KAU API(`qwen3.5-9b`), 키는 `~/.config/behavior-2026/kau.env`(저장소 밖). 제출용은 로컬 Qwen(GPU). 결정론 설정(temperature 0, seed)을 요청마다 명시.
- 지시: 모호하지 않게, 숫자 명령 금지, π0.5 문장 90 토큰 이내.
- 언어: C++/CUDA 손으로 + Rust 조율, 파이썬은 공식 파이썬 프로세스 접착부·일회성 도구만, PyTorch 금지. 에이전트 프레임워크 금지(OpenAI 호환 API 원형을 직접).
- 평가기 두 개(원본 = 제출 수치, 포팅 = 개발). 가속·포팅은 대회 벤치마크 결과가 달라지면 안 된다. 검증 기준은 대회 환경(Linux).
- 시뮬레이터 엔진을 뜯어서 우리 엔진으로(물리 PhysX = C++ = CUDA 비트 사슬, 렌더는 새로 짜 통계 비교). 자체 평가 물리는 GPU 로 판 여러 개.
- 검은 화면은 근원 해결만(다른 프레임으로 채우는 우회 금지, 검출은 유지).
- 플래너 강화학습을 새로 만들지 않는다(LLM 유지, 결정기 자리만 열어 둠).
- 저장소: GitHub 비공개 `juyoung020/behavior-2026` 하나, 브랜치 없이 main, 경로 지정 커밋. README 는 영어, docs 는 한국어.
