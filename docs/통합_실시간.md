## 2. 정한 스펙과 이유

### 2.1 연결 하나(simlink)가 계획기와 관측 발행을 같이 한다

- 이유 셋:
  - 소켓·위치 추정기·경계 동기화가 한 곳에 있다.
  - 경계 스텝이면 그 프레임을 먼저 그래프에 넣고(settle, 2.8) 결정한다.
  - 계획기 `BoundaryEvent.pose` 와 meridian `/camera/pose` 가 **같은 추정값**이다.
- 계획기 크레이트는 ROS 를 모른다.
  - 전송층 `link.rs` 는 `ObsSink` 트레이트 뒤로 관측을 넘긴다.
  - 시험·단독 실행은 `NullSink`(`bagent link`), ROS 발행은 simlink 의 `RosSink` 가 한다. 그래서 `cargo test` 가 전송층 전체를 덮는다.
- 계획기는 WSL 에서 돈다. KAU 키(`~/.config/behavior-2026/kau.env`), scene_server(127.0.0.1:7791), Rust 툴체인이 모두 WSL 에 있다.
  - Windows 쪽은 파이썬 접착부뿐이다.

### 2.2 매 스텝 경로 — 답을 기다리지 않는다

- 접착부는 스텝마다 STEP(proprio 61 f32 + 요청된 영상)을 보내고 **답을 기다리지 않는다**.
  - 다음 스텝 첫머리에 전 스텝의 ACK 를 읽는다. 시뮬레이터 한 스텝(약 100 ms) 동안 이미 와 있다.
  - ACK 에는 `hold_next`(다음 스텝이 경계일 수 있음)와 `want_next`(보낼 카메라)가 든다.
- 경계 스텝만 WAIT 로 보내고 결정이 올 때까지 기다린다. 시뮬레이터 시간이 멈추므로 점수에는 안 들어간다.
  - 판 시작·예산 소진·정기 확인이 올 스텝은 미리 안다.
  - 사건 경계(이동 멈춤·그리퍼 변화)는 난 **다음** 스텝을 붙잡는다. 1스텝 늦는 것은 중계기와 같다([에이전트_설계.md](에이전트_설계.md) 1.10).
- 영상 보내기는 뒤 스레드가 한다.
  - 시뮬레이터 스레드는 미리 잡아 둔 버퍼(카메라·종류마다 3칸)로 memcpy 만 한다.
  - 한 칸을 다시 쓰기 전에 그 칸을 쓴 메시지가 다 나갔는지 순번으로 확인한다.
  - 평가기 텐서를 넘겨 둔 채 보내면, 다음 스텝이 같은 메모리에 쓸 때 영상이 섞일 수 있다(추정). 그래서 복사한다.
- 실측(가짜 평가기, 400 스텝, 4절): 영상 없는 스텝 약 0.05 ms, 머리 RGB-D 스텝 p50 0.49 ms / p99 1.8 ms.
  - 동기로 보내면 각각 0.13 ms, 1.6 ms / 5.3 ms 다.

### 2.3 keyframe 정책은 Rust 쪽이 정한다(`KeyCfg`)

- 무엇을 언제 보낼지는 link 가 ACK 로 요청한다. 접착부는 요청받은 것만 보낸다.

| 카메라 | 언제 | 이유 |
|---|---|---|
| 머리 RGB-D | 카메라 광학 자세가 5 cm 또는 3° 넘게 움직였을 때, 아니면 6 스텝마다 | meridian frontend 입력(머리만 씀). 움직일 때는 트래커가 이어지게 자주, 멈추면 드물게 |
| 손목 RGB-D | 경계 스텝만(기본). `--wrist-every N` 으로 주기 | LLM `look` 영상. 손목 토픽은 앞으로의 다중 카메라 frontend 용 |
| 전부 | 경계 스텝 | LLM 영상 + 그 순간 그래프 갱신 |

- 영상은 평가기 텐서 그대로(RGBA u8, 깊이 f32 m) 보낸다. 자르기·축소·mm 변환은 받는 쪽(Rust)이 한다(2.4). 파이썬 쪽 numpy 연산은 0 이다.
- 대역: 가짜 평가기 600 스텝에서 470 MB(머리 107장 + 경계 7번 전 카메라)다. 매 스텝 다 보내면 약 4.7 GB 다.

### 2.4 영상 변환 — frontend 입력 계약([meridian_통합설계.md](meridian_통합설계.md) 2.1)

- 머리 720x720 에서 가운데 720x540(위 90 줄 버림)을 자르고 640x480 으로 줄인다.
  - RGB 는 면적 평균(분리 가능한 상자 필터, 가중치 합 1)이다.
  - 깊이는 obs_player 와 같은 칸 고르기(최근접)다. m → mm 로 반올림하고 10 m 에서 자르며, 0·음수·NaN·무한대는 0 이다.
- K: (306, 306, 360, 360) → (272, 272, 320, 240). 값은 평가기 `eval_utils.CAMERA_INTRINSICS` 에서 받는다(HELLO).
- 손목은 480x480 그대로다(`/camera_left/*`, `/camera_right/*`).
- 변환은 simlink 의 ROS 스레드가 한다. 머리 한 장 p50 5.5 ms / p90 13 ms 이고, link 스레드는 안 막힌다.
- 시험 5개: 기하가 obs_player 와 같음, 가중치 합 1, 자르기 띠, 깊이 규칙, 손목 통과.

### 2.5 위치 추정기 자리(`pose.rs` `PoseEstimator`)와 meridian_odom 계약

- `QvelIntegrator`: base_qvel 30 Hz 전진 오일러 적분이다. `odom.rs`·`demo_player.py`·obs_player 와 같은 식(시험으로 비트 동일 확인).
- `Corrected`: 안쪽 적분에 바깥 보정 `T_map_odom` 을 앞에 곱한다.
  - 바깥 추정기가 시각 t 의 절대 자세 `fix` 를 주면, link 는 같은 stamp 의 보정 전 자세 `raw_t` 를 기록(최근 1024 스텝)에서 찾는다.
  - 그리고 `T_map_odom = fix ∘ raw_t⁻¹` 로 바꿔 넣는다(`correction_from_fix`). 추정기 지연(수 스텝)이 있어도 맞물린다.
- 적분만으로는 10 m 이동에 중앙 1.2 m 틀어진다([meridian_통합설계.md](meridian_통합설계.md) 12.9). meridian 의 깊이 보정 시제품은 8판 최대 3.5 cm 다.
  - 실시간 판 `meridian_odom`(손 CUDA)이 들어오면 `--pose-source meridian` 으로 바꾼다.
- meridian_odom 계약(2.1·12.9):
  - simlink 는 매 스텝 `/base_qvel`(TwistStamped, 로봇 기준 원값)과 `/camera/extrinsic`(PoseStamped, 베이스 기준 머리 카메라 = robot2cam)을 낸다.
  - `--pose-source simlink`(지금 기본): simlink 가 자기 추정으로 `/camera/pose`·`/base_pose` 도 낸다.
  - `--pose-source meridian`: 그 둘은 meridian_odom 이 낸다. simlink 는 `/base_pose` 를 받아 위 고정점으로 넣는다(발행자 둘이 안 되게).

- 옮겨진 물체 처리 입력(meridian 12.12): simlink 는 매 스텝 두 토픽을 더 낸다.
  - `/robot/eef`(`PoseArray` [왼, 오른]): 베이스 기준 팔 끝 자세, proprio `eef_*_pos`·`eef_*_quat` 17:24·42:49(xyzw).
  - `/robot/gripper`(`JointState` name [left_gripper, right_gripper]): position = 두 손가락 합, 24:26·49:51.
  - 둘 다 평가기 proprio 표(`PROPRIOCEPTION_INDICES["R1Pro"]`)와 대조했다(시험 `eef_grip_indices`). 자기 스텝 stamp 로 내므로 영상 k(stamp k-1)와는 k-1 값이 짝이다(2.7).

### 2.6 카메라 외부 자세 = proprio 순기구학(`fk.rs`) — 규칙

- 평가기가 관측에 넣어 주는 `cam_rel_poses` 는 평가기 `_preprocess_obs` 가 만든 값이다.
  - 재료가 시뮬레이터 카메라 자세 API(`camera.get_position_orientation()`)와 로봇 전역 자세다.
  - 규칙 해석상 쓰지 않는다(코디네이터 09-30). **접착부는 이 값을 보내지도 않는다.**
- 대신 proprio 의 `trunk_qpos`(53..57)·`arm_left_qpos`(3..10)·`arm_right_qpos`(28..35)로 계산한다.
  - 체인은 R1Pro URDF(`r1pro.urdf`): base_link → torso_joint1..4 → zed_joint(머리), … → arm_joint1..7 → gripper·realsense(손목).
  - 여기에 링크 → 카메라 prim 고정 변환을 곱한다.
- 고정 변환은 시연(학습 데이터)의 `robot2cam_pose` 로 한 번 뽑았다(`src\integ\fk\fit_cam_fk.py`). 평가 때는 이 상수만 쓴다.
  - 머리: zed_link 에서 (6 cm, 0, 1 cm), Rx(π).
  - 손목: realsense_link 에서 회전만 90° 이다.
- 재현 오차(시연 0·200번 판 482 표본): 세 카메라 모두 위치 최대 0.002 mm, 각 최대 0.0001°.
  - 순기구학 + 상수 하나로 robot2cam 을 그대로 만든다.
  - Rust 판 시험은 시연 한 프레임에서 f32 관절값 기준으로 0.1 mm·0.01° 안이다.
- 뿌리는 base_link 다. robot2cam 이 base_link 기준이라는 것도 같은 표본으로 확인된다(뿌리가 다르면 고정 변환이 흩어진다. 실측 흩어짐 0.002 mm).

### 2.7 시각 맞추기 — 영상(스텝 k) = 스텝 k-1 의 장면

- render 에이전트 확인: 공식 관측 영상 k 는 스텝 k-1 끝의 장면으로 그려진다. 깊이가 1~2 ulp 까지 일치한다. 반면 proprio 는 스텝 k 뒤 값이다.
- simlink 는 자세·`/camera/extrinsic`·`/base_qvel` 을 매 스텝 **그 스텝 상태의 stamp** 로 낸다. 영상 k 는 **스텝 k-1 의 stamp** 로 낸다.
  - frontend 는 "영상 stamp 이하 최신 자세"를 쓰므로, 영상 k 는 k-1 에 낸 자세·robot2cam 과 맞물린다.
  - 손목 자세도 k-1 값으로 영상과 같은 stamp 다. 판 첫 스텝은 직전이 없어 자기 stamp 다.
- π0.5 에 넘기는 관측은 공식 그대로 둔다. 학습 데이터도 같은 어긋남으로 녹화됐을 것이다(추정).

### 2.8 경계에서 그래프 기다리기(settle)

- 경계 스텝은 전 카메라 영상을 받아 발행한 뒤 기다린다. graphcore 가 그 영상 stamp 이상의 commit 이벤트를 낼 때까지, 또는 400 ms 까지다.
  - 그다음 계획기가 scene_server 를 조회한다. 시뮬레이터가 멈춰 있어 점수 영향이 없다.
- frontend 는 물체를 확정(keyframe 2번)하거나 갱신(2 s)할 때만 조각을 내므로, 대부분의 경계에서 400 ms 를 다 기다린다.
  - 프레임 처리 완료 신호가 있으면 줄일 수 있다(9절 요청).

### 2.9 π0.5 에 넣는 것 — 과제 문장 + 단계 번호(plan.md 4.1 (다)+(라))

- `--prompt-mode task`(기본): π0.5 문장은 학습된 과제 문장 그대로 둔다. 계획기 결정(단계 문장)은 기록·기억·복구와 단계 번호에만 쓴다.
  - 지금 가중치는 단계 문장을 거의 따르지 않는다(plan.md 3절).
  - `--prompt-mode subtask` 는 중계기 agent 모드처럼 문장을 바꾸고 남은 행동 묶음을 버린다(flush).
- 단계 번호(`StageTrack`): 2025 1위 모델의 단계는 시연 시간을 과제마다 5~15 등분한 것이다("solely based on the timestamps").
  - 그래서 계획 진행률도 "시연에서 그 단계까지 걸린 시간 비율"로 잰다: 계획 체크리스트 단계마다 시연 p50 길이를 무게로 쓴다.
  - 지금 단계 안에서는 걸린 스텝만큼(그 단계 p50 까지) 나아간다.
  - 단계 = ⌊진행률 × 단계 수⌋.
  - 같은 계획 단계를 계속·재시도하면 걸린 스텝을 이어 센다(되돌아가는 것 방지).
  - 단계 수는 2025 표다(엔진이 알려 주면 그 값, 아니면 `src\integ\glue\stage_table_2025.json`, 과제 0~49).
- `--stage external`(기본): 결정마다, 그리고 진행률이 단계 경계를 넘을 때 ACK 로 `stage`(mode 1 = 외부 고정)를 보낸다.
  - 접착부는 1위 모델(`Pi05NativePolicy.kind == 1`)이면 `Pi05NativePolicy.set_stage(slot, stage, fixed)`(C API `pi05_set_stage`)를 부른다.
- `--stage vote`: 보내지 않는다. 모델 자체 투표를 쓰고, 계획기 추정은 `stage_est` 로 기록만 한다. `native_steps.csv` 의 모델 단계와 비교할 수 있다.
- 문장 모델(radio 체크포인트)에는 단계 입력이 없다. 접착부가 한 번 알리고 기록만 한다.

### 2.10 그 밖

- ROS: 통합 판은 `ROS_DOMAIN_ID=38` 을 쓴다. 다른 에이전트의 meridian 시험(37)과 토픽이 섞이지 않게 하려는 것이다.
  - 모든 프로세스가 `fastdds_shm.xml`(공유메모리 32 MB)을 쓴다. 발행은 RELIABLE 이다.
  - ROS 발행 줄이 차면 평소 패킷은 영상만 버리고, 경계 패킷은 기다려서라도 보낸다.
- 평가기: `RGBDFullResWrapper`(깊이 필요)를 쓴다. π0.5 는 720/480 영상을 엔진 안에서 224 로 줄인다(openpi `resize_with_pad` 와 비트 동일).
  - Kit 설정은 기본 그대로다. 검은 프레임(B)이 나오면 그 판은 무효로 표시하고 수만 센다.
    - 계획기·meridian 연결 수치(지연·호출 수·그래프 갱신)는 검은 프레임과 상관없이 본다.
- 파이썬은 접착부(소켓·버퍼 복사·결정 넣기)와 일회성 도구(`summarize_run.py`, `fit_cam_fk.py`, `link_bench.py`)만이다. PyTorch 는 없다.
  - 평가기가 요구하는 반환 텐서 감싸기는 Pi05NativePolicy 몫이다.
  - meridian frontend 는 아직 연구실 파이썬+torch 판이다. C++ 판은 다른 에이전트가 포팅 중이다.

## 3. 프로토콜(`link.rs` 머리말)

머리 12 B = `magic "BLNK" u32, type u16, flags u16, len u32`(리틀 엔디언) + 몸통.

| 방향 | type | 몸통 |
|---|---|---|
| 접착부 → | HELLO(1) | JSON: task, task_id, num_envs, hz, max_steps, cams[{name, w, h, k}], stage_count, prompt |
| ← | HELLO_ACK(0x81) | JSON: ok, task, planner, hold(true), want(첫 스텝 전부), pose |
| → | RESET(2) | 없음(새 판, 계획기가 돌아올 때까지 기다린 뒤 초기화) |
| → | STEP(3) | 32 B(step u64, t f64, flags u32(WAIT=1), env u16, n_proprio u16, n_crp u16 = 0, n_frames u16) + proprio f32 × 61 + 영상 머리 16 B × k(cam u8, kind u8(0 RGBA8, 2 깊이 f32), h u32, w u32, nbytes u32) + 영상 바이트 |
| ← | ACK(0x83) | step u64, hold_next u8, has_decision u8, want_next u16(카메라 c 의 RGB = 1<<2c, 깊이 = 1<<2c+1), json_len u32 + 결정 JSON |
| → | BYE(4) | 없음 |

결정 JSON은 아래와 같다. 비경계 스텝의 단계 갱신은 `kind: "stage"` 다.

```
{"kind":"issue|continue|finish|stage","prompt":null|"…","flush":false,"stage":3|null,"stage_mode":1,"stage_est":3,
 "text":"<계획기 단계 문장>","source":"llm|fallback|…","step":123,"trigger":"episode_start|settled|…","decide_ms":…,"settle_ms":…}
```
