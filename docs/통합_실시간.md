# 통합 — 평가기 · π0.5 · 계획기 · scenemap 을 실시간으로 잇기

작성 2026-09-30. 코드는 다음 두 곳에 있다.
- `src/agent/src/` 의 `link.rs`·`pose.rs`·`fk.rs`·`setup.rs`: 계획기 크레이트의 전송층.
- `src/integ/`: 노드 simlink, scenemap 가짜 구현(`scenemap_stub`), 평가기 접착부, 실행기, 순기구학 도구.

인지 스택 scenemap(2D SLAM + YOLOE 물체 지도, C++/CUDA, ROS 없음 — [scenemap_설계.md](scenemap_설계.md))은 simlink 가 **같은 프로세스
C ABI** 로 부른다(12절).

근거는 [plan.md](../plan.md) 0~6절, [에이전트_설계.md](에이전트_설계.md), [scenemap_설계.md](scenemap_설계.md),
[π05_네이티브엔진.md](π05_네이티브엔진.md) 7절이다. 추정은 "(추정)"으로 적었다.

## 0. 한눈에

| 무엇 | 상태 |
|---|---|
| 평가기 ↔ 계획기 연결 | **동작**. TCP 한 줄, 전송층 `bagent link`. Core·Decider·경계 감시는 그대로. 시험 51개 + simlink 1개 통과 |
| 평가기 → 인지 스택 | **scenemap 같은 프로세스 C ABI**(`sm_push_proprio`·`sm_push_image`). libscenemap 이 아직 없어 헤더에 맞춘 가짜 구현(자세 = base_qvel 적분, 물체 없음)으로 연결·시험했다. 진짜가 오면 `SCENEMAP_LIB_DIR` 로 바꿔 링크 |

| 위치 | `PoseEstimator` 자리 그대로. `--pose-source scenemap`(기본)이면 scenemap slam2d 자세를 고정점으로 받는다(`Corrected`) |
| 카메라 외부 자세 | proprio 관절값 + R1Pro 순기구학(계획기 `fk.rs`, scenemap 도 같은 상수). 평가기 `cam_rel_poses` 는 안 씀(규칙) |
| 종단 한 판 | 유효 판 없음 — 이 PC 에서 scenemap 구성으로 돌릴 것(5절) |

## 1. 구조

```

       simlink(src/integ/simlink, Rust, 한 프로세스) ◀───────┘
```

## 2. 정한 스펙과 이유

### 2.1 연결 하나(simlink)가 계획기와 인지 스택을 같이 든다

- 이유:
  - 소켓·위치 추정기·경계 동기화가 한 곳에 있다.
  - 경계 스텝이면 그 프레임을 먼저 scenemap 에 넣고(settle, 2.8) 결정한다.
  - 계획기 `BoundaryEvent.pose` 와 scenemap 자세가 같은 값이다(2.5).
  - scenemap 은 같은 프로세스라 질의가 함수 호출(스냅숏)이다.
- 계획기 크레이트(`src/agent`)는 C/C++ 를 링크하지 않는다.
  - 전송층 `link.rs` 는 `ObsSink` 트레이트 뒤로 관측을 넘기고, 그래프 질의는 `SceneQuery` 트레이트로 받는다.
  - 시험·단독 실행은 `NullSink`·`MemScene`(`bagent link`). scenemap FFI 는 simlink 의 `sm.rs` 가 한다.
  - simlink 는 시작 때 `bagent::setup::register_scene` 으로 질의를 등록하고, `--graph scenemap` 이 그것을 쓴다.
- 계획기는 평가기와 같은 PC 에서 돈다. KAU 키는 `~/.config/behavior-2026/kau.env`(저장소 밖, 이 PC 에는 아직 없음).

### 2.2 매 스텝 경로 — 답을 기다리지 않는다

- 접착부는 스텝마다 STEP(proprio 61 f32 + 요청된 영상)을 보내고 **답을 기다리지 않는다**.
  - 다음 스텝 첫머리에 전 스텝의 ACK 를 읽는다. 시뮬레이터 한 스텝(약 100 ms) 동안 이미 와 있다.
  - ACK 에는 `hold_next`(다음 스텝이 경계일 수 있음)와 `want_next`(보낼 카메라)가 든다.
- 경계 스텝만 WAIT 로 보내고 결정이 올 때까지 기다린다. 시뮬레이터 시간이 멈추므로 점수에는 안 들어간다.
  - 판 시작·예산 소진·정기 확인이 올 스텝은 미리 안다.
  - 사건 경계(이동 멈춤·그리퍼 변화)는 난 **다음** 스텝을 붙잡는다. 1스텝 늦는 것은 중계기와 같다([에이전트_설계.md](에이전트_설계.md) 1.10).
- 영상 보내기는 뒤 스레드가 한다.
  - 시뮬레이터 스레드는 미리 잡아 둔 버퍼(카메라·종류마다 3칸)로 memcpy 만 한다.
  - 한 칸을 다시 쓰기 전에 그 칸을 쓴 메시지가 다 나갔는지 순번으로 확인한다.
  - 평가기 텐서를 넘겨 둔 채 보내면, 다음 스텝이 같은 메모리에 쓸 때 영상이 섞일 수 있다(추정). 그래서 복사한다.
- 실측(가짜 평가기, 4절): 이 PC 에서 다시 잴 것.

### 2.3 keyframe 정책은 Rust 쪽이 정한다(`KeyCfg`)

- 무엇을 언제 보낼지는 link 가 ACK 로 요청한다. 접착부는 요청받은 것만 보낸다.

| 카메라 | 언제 | 이유 |
|---|---|---|
| 머리 RGB-D | 카메라 광학 자세가 5 cm 또는 3° 넘게 움직였을 때, 아니면 6 스텝마다 | scenemap 입력(가상 스캔·검출). 움직일 때는 자주, 멈추면 드물게 |
| 손목 RGB-D | 경계 스텝만(기본). `--wrist-every N` 으로 주기 | LLM `look` 영상. scenemap 에도 넘긴다(손목 깊이는 설계 7절 "머리만으로 충분한가" 용) |
| 전부 | 경계 스텝 | LLM 영상 + 그 순간 그래프 갱신 |

- 영상은 평가기 텐서 그대로(RGBA u8, 깊이 f32 m) 보내고, simlink 도 그대로 scenemap 에 넘긴다(자르기·축소는 scenemap 안에서). 파이썬 쪽 numpy 연산은 0 이다.
- 대역: 가짜 평가기 600 스텝에서 470 MB(머리 107장 + 경계 7번 전 카메라)다. 매 스텝 다 보내면 약 4.7 GB 다.

### 2.4 영상 — 원 텐서 그대로

- simlink 는 평가기 원 텐서(머리 720² · 손목 480², RGBA u8,
  깊이 f32 m)와 그 해상도의 K(평가기 `eval_utils.CAMERA_INTRINSICS`, HELLO 로 받음)를 `sm_image` 로 넘긴다.
- 카메라마다 RGBA·깊이 두 조각을 한 `sm_image` 로 묶는다. `dets = NULL` → scenemap 이 검출기(YOLOE, `src/ovdet`)를 부른다(설계 4.1).

### 2.5 위치 추정기 자리(`pose.rs` `PoseEstimator`)와 scenemap 자세

- `QvelIntegrator`: base_qvel 30 Hz 전진 오일러 적분(`odom.rs` 와 같은 식, 시험으로 비트 동일).
- `Corrected`: 안쪽 적분에 바깥 보정 `T_map_odom` 을 앞에 곱한다.
  - 바깥 추정기가 시각 t 의 절대 자세 `fix` 를 주면, link 는 같은 시뮬 시각의 보정 전 자세 `raw_t` 를 기록(최근 1024 스텝)에서 찾아
    `T_map_odom = fix ∘ raw_t⁻¹` 로 바꿔 넣는다(`correction_from_fix`). 추정기 지연(수 스텝)이 있어도 맞물린다.
- `--pose-source scenemap`(기본): simlink 입력 스레드가 패킷마다 scenemap 스냅숏의 `pose()`(slam2d 자세, 시뮬 시각)를 읽어 고정점으로 준다.
  가짜 구현은 같은 적분이라 보정은 항등이다. `--pose-source simlink` 면 적분만.
- 적분만으로는 10 m 이동에 중앙 1.2 m 틀어진다(원본 HDF5 GT 13판). 깊이 보정 시제품은 8판 최대 3.5 cm(설계 3.1 후보 C).
- 팔 끝·그리퍼(옮겨진 물체 처리 입력)는 scenemap 이 `sm_push_proprio` 의 proprio 에서 직접 읽는다(17:24·42:49, 24:26·49:51).
  link 는 같은 값을 `ObsPacket.eef`·`grip` 에 두고(시험 `eef_grip_indices`).

### 2.6 카메라 외부 자세 = proprio 순기구학(`fk.rs`) — 규칙

- 평가기가 관측에 넣어 주는 `cam_rel_poses` 는 평가기 `_preprocess_obs` 가 만든 값이다.
  - 재료가 시뮬레이터 카메라 자세 API(`camera.get_position_orientation()`)와 로봇 전역 자세다.
  - 규칙 해석상 쓰지 않는다(코디네이터 09-30). **접착부는 이 값을 보내지도 않는다.**
- 대신 proprio 의 `trunk_qpos`(53..57)·`arm_left_qpos`(3..10)·`arm_right_qpos`(28..35)로 계산한다.
  - 체인은 R1Pro URDF(`r1pro.urdf`): base_link → torso_joint1..4 → zed_joint(머리), … → arm_joint1..7 → gripper·realsense(손목).
  - 여기에 링크 → 카메라 prim 고정 변환을 곱한다.
- 고정 변환은 시연(학습 데이터)의 `robot2cam_pose` 로 한 번 뽑았다(`src/integ/fk/fit_cam_fk.py`). 평가 때는 이 상수만 쓴다.
  - 머리: zed_link 에서 (6 cm, 0, 1 cm), Rx(π).
  - 손목: realsense_link 에서 회전만 90° 이다.
- 재현 오차(시연 0·200번 판 482 표본): 세 카메라 모두 위치 최대 0.002 mm, 각 최대 0.0001°.
  - 순기구학 + 상수 하나로 robot2cam 을 그대로 만든다.
  - Rust 판 시험은 시연 한 프레임에서 f32 관절값 기준으로 0.1 mm·0.01° 안이다.
- 뿌리는 base_link 다. robot2cam 이 base_link 기준이라는 것도 같은 표본으로 확인된다(뿌리가 다르면 고정 변환이 흩어진다. 실측 흩어짐 0.002 mm).

### 2.7 시각 — 시뮬 시각, 영상(스텝 k) = 스텝 k-1 의 장면

- 모든 stamp 는 **시뮬 시각**(초, 판 시작 = 0, 스텝 k = k/hz)이다. 경계에서 시뮬이 멈추면 시간도 멈춘다(설계 2절 "시간 규칙 = stamp").
- render 에이전트 확인: 공식 관측 영상 k 는 스텝 k-1 끝의 장면으로 그려진다(깊이 1~2 ulp 일치). proprio 는 스텝 k 뒤 값이다.
- simlink 는 `sm_push_proprio` 를 매 스텝 **그 스텝 시각**(k/hz)으로, `sm_push_image` 를 **k-1 시각**으로 넣는다.
  scenemap 은 영상 stamp 와 같은 시각의 proprio(= k-1 값)로 순기구학·자세를 짝짓는다. 판 첫 스텝은 직전이 없어 자기 시각.
- π0.5 에 넘기는 관측은 공식 그대로 둔다.

### 2.8 경계에서 지도 기다리기(settle)

- 경계 스텝 패킷은 줄이 차도 버리지 않고, 계획기는 scenemap 입력 스레드가 그 패킷(전 카메라 영상 포함)을 다 넣은 뒤에 질의한다.
  - 같은 프로세스라 "반영 끝"을 정확히 안다(패킷 순번).
  - 진짜 scenemap 은 keyframe 처리 시간(YOLOE + slam2d + objmap)만큼(설계 목표 수 ms, 재서 적는다).

### 2.9 π0.5 에 넣는 것 — 과제 문장 + 단계 번호(plan.md 4.1 (다)+(라))

- `--prompt-mode task`(기본): π0.5 문장은 학습된 과제 문장 그대로 둔다. 계획기 결정(단계 문장)은 기록·기억·복구와 단계 번호에만 쓴다.
  - 지금 가중치는 단계 문장을 거의 따르지 않는다(plan.md 3절).
  - `--prompt-mode subtask` 는 중계기 agent 모드처럼 문장을 바꾸고 남은 행동 묶음을 버린다(flush).
- 단계 번호(`StageTrack`): 2025 1위 모델의 단계는 시연 시간을 과제마다 5~15 등분한 것이다("solely based on the timestamps").
  - 그래서 계획 진행률도 "시연에서 그 단계까지 걸린 시간 비율"로 잰다: 계획 체크리스트 단계마다 시연 p50 길이를 무게로 쓴다.
  - 지금 단계 안에서는 걸린 스텝만큼(그 단계 p50 까지) 나아간다.
  - 단계 = ⌊진행률 × 단계 수⌋.
  - 같은 계획 단계를 계속·재시도하면 걸린 스텝을 이어 센다(되돌아가는 것 방지).
  - 단계 수는 2025 표다(엔진이 알려 주면 그 값, 아니면 `src/integ/glue/stage_table_2025.json`, 과제 0~49).
- `--stage external`(기본): 결정마다, 그리고 진행률이 단계 경계를 넘을 때 ACK 로 `stage`(mode 1 = 외부 고정)를 보낸다.
  - 접착부는 1위 모델(`Pi05NativePolicy.kind == 1`)이면 `Pi05NativePolicy.set_stage(slot, stage, fixed)`(C API `pi05_set_stage`)를 부른다.
- `--stage vote`: 보내지 않는다. 모델 자체 투표를 쓰고, 계획기 추정은 `stage_est` 로 기록만 한다. `native_steps.csv` 의 모델 단계와 비교할 수 있다.
- 문장 모델(radio 체크포인트)에는 단계 입력이 없다. 접착부가 한 번 알리고 기록만 한다.

### 2.10 그 밖

- ROS 는 없다.
  - scenemap 입력 줄(기본 6)이 차면 평소 패킷은 영상만 버리고 proprio 는 남긴다(자세 적분이 비지 않게). 경계 패킷은 기다려서라도 넣는다.
- 평가기: `RGBDFullResWrapper`(깊이 필요)를 쓴다. π0.5 는 720/480 영상을 엔진 안에서 224 로 줄인다(openpi `resize_with_pad` 와 비트 동일).
  - Kit 설정은 기본 그대로다. 검은 프레임(B)이 나오면 그 판은 무효로 표시하고 수만 센다.
    - 계획기·scenemap 연결 수치(지연·호출 수·지도 갱신)는 검은 프레임과 상관없이 본다.
- 파이썬은 접착부(소켓·버퍼 복사·결정 넣기)와 일회성 도구(`summarize_run.py`, `fit_cam_fk.py`, `link_bench.py`)만이다. PyTorch 는 없다.

## 3. 프로토콜(`link.rs` 머리말)

머리 12 B = `magic "BLNK" u32, type u16, flags u16, len u32`(리틀 엔디언) + 몸통.

| 방향 | type | 몸통 |
|---|---|---|
| 접착부 → | HELLO(1) | JSON: task, task_id, num_envs, hz, max_steps, cams[{name, w, h, k}], stage_count, prompt |
| ← | HELLO_ACK(0x81) | JSON: ok, task, planner, hold(true), want(첫 스텝 전부), pose |
| → | RESET(2) | 없음(새 판, 계획기가 돌아올 때까지 기다린 뒤 초기화) |
| → | STEP(3) | 32 B(step u64, t f64, flags u32(WAIT=1), env u16, n_proprio u16, n_crp u16 = 0, n_frames u16) + proprio f32 × 61 + 영상 머리 16 B × k(cam u8, kind u8(0 RGBA8, 2 깊이 f32), h u32, w u32, nbytes u32) + 영상 바이트 |
| ← | ACK(0x83) | step u64, hold_next u8, has_decision u8, want_next u16(카메라 c 의 RGB = 1<<2c, 깊이 = 1<<2c+1), json_len u32 + 결정 JSON |
| → | BYE(4) | 없음 |

결정 JSON은 아래와 같다. 비경계 스텝의 단계 갱신은 `kind: "stage"` 다.

```
{"kind":"issue|continue|finish|stage","prompt":null|"…","flush":false,"stage":3|null,"stage_mode":1,"stage_est":3,
 "text":"<계획기 단계 문장>","source":"llm|fallback|…","step":123,"trigger":"episode_start|settled|…","decide_ms":…,"settle_ms":…}
```

## 11. 실험 계획 — 단계 번호: 모델 투표 vs 계획기 외부 지정

- 조건: 1위 모델(PiBehavior)이 평가기 안에서 돌고(π05 문서 7절), 과제 0~49 중 여럿.
- 같은 판(과제·인스턴스·씨앗)을 둘로 돌려 q_score 를 비교한다.
  - 1위 모델 + simlink `--stage vote`: 모델 투표. 계획기 추정은 기록만 한다.
  - 1위 모델 + simlink `--stage external`: 계획기 진행률 단계를 외부 고정한다.
- 함께 볼 것:
  - 모델 투표 단계(`native_steps.csv` stage)와 계획기 추정(`decisions.jsonl` stage_est)의 차이
  - 외부 지정 판에서 단계가 모델 투표보다 늦거나 빠른 구간
  - 단계 되돌리기가 실패 복구에 쓰였는지
- 판정: 과제별 q_score 평균과 성공 수. 판이 적어 잡음이 크니 과제마다 인스턴스 여러 개로 한다(평가 속도는 plan.md 4.5).
