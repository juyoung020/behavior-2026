## 0. 한눈에

1. **목적**: 에이전트·강화학습·VLA 를 대량으로 학습·시험할 바탕 시뮬레이터. 대회 공식 평가는 주최 측이 공식
   OmniGibson/Isaac Sim 으로 하므로 **우리 엔진은 공식을 대신하지 않는다**. 그래서 층마다 "공식과 얼마나 같은가"를 숫자로 증명한다.
2. **구조 결정**: PhysX 는 **정답지(oracle)** 로만 쓴다. 최종 엔진은 BEHAVIOR 가 실제로 쓰는 부분만 **손으로 짠 C++ → CUDA**
   (JSBSim 포팅과 같은 방식). 최종 엔진이 PhysX 라이브러리를 부르는 구조가 되지 않게 한다.
3. **PhysX 정확한 버전 소스를 찾았다**: 공개 태그 `107.3-omni-and-physx-5.6.1` (PhysX SDK 5.6.1 + omni.physx 107.3).
   이 PC Isaac Sim 5.1 의 DLL 안 버전 문자열 "5.6.1" 과 일치하고, 태그 README 가 직접 "IsaacSim v5.1.0 ↔ 이 태그" 로 짝지어 준다(3절).
4. **100과제 물리 종류**: 유체 0, 천 0, 물리 입자(잘린 채소·팝콘·치즈 가루) 6, 시각 입자(얼룩·먼지, 동역학 없음) 14,
   입자·천이 전혀 없는 과제 80. → 강체 + 관절체 + 고정/구 조인트만 제대로 옮기면 **94과제의 동역학**이 덮인다(2절 표 2).
5. **물리 층 시제품(층 0 정답지)**: 공식 평가기의 PhysX 호출 전체를 OmniPVD(.ovd)로 뜨고, 우리 PhysX 빌드로 처음부터 같은
   호출을 같은 순서로 재생해 매 서브스텝 결과를 비트 비교하는 도구를 만들었다. **자체 시험 600 스텝 전부 비트 동일**
   (관절체 드라이브·흉내 관절·고정 조인트 붙였다 떼기·볼록/삼각 메시·순간이동·힘·잠/깸 포함). 공식 기록 비교는
   GPU 가 검은 화면 진단에 묶여 아직 못 돌렸다(8절). 기록·재생 도구는 준비돼 있어 GPU 가 풀리면 5분 안에 돈다.
6. **우리 엔진(손으로 짠 C++) 첫 단계**: 자유 강체(중력·감쇠·속도 제한·자이로·잠금·잠 판정)가 PhysX 와
   **강체 3,000개 × 1,200 스텝 전부 비트 동일**(6.1절). 다음은 섬 묶기와 접촉이 있는 풀이 경로.
7. **기준은 Linux 대회 환경**(사용자 결정 09-29): 층 0 정답지는 이 PC 윈도 공식이 아니라 Linux 공식(Ubuntu 22.04 + pip isaacsim 5.1)
   에서 뜬다. 이 PC 는 WSL2 안에 물리 전용으로 설치해 맞춘다(9절). 렌더 기준은 Linux GPU 장비가 필요하다.
8. **자체 평가는 GPU 물리**(사용자 결정 09-29): 자체 평가·학습의 물리는 손으로 짠 CUDA(층 2)로 판 여러 개를 한꺼번에 돌리고,
   대회 환경 CPU PhysX 와 비트 동일(층 0 → 1 → 2 사슬)을 지킨다. PhysX 자체 GPU 파이프라인은 CPU 와 결과가 달라 쓰지 않는다(참고 측정만).
   구조와 목표 처리량은 10절.

## 5. 층 0 정답지 설계 (시제품)

### 5.1 왜 OmniPVD 인가
- RepX 장면 덤프(`get_physx_interface().save_scene_to_repx`)는 실수를 `%g`(유효숫자 6자리)로 써서 비트 복원이 안 된다
  (`physx/source/physxextensions/src/serialization/Xml/SnPxStreamOperators.h:78`).
- OmniPVD 는 PhysX SDK 자신이 모든 객체 생성·설정값과 매 simulate 결과를 float 원본 그대로 쓰는 기록이다.
  Kit 설정 두 개(`/persistent/physics/omniPvdOvdRecordingDirectory`, `/physics/omniPvdOutputEnabled`)만 켜면 omni.physx 가
  PxPhysics 를 다시 만들며 기록을 붙인다(`omni.physx/plugins/Setup.cpp:444-560`). 평가기 코드는 안 고친다.

### 5.2 OVD 에 없는 것과 메우는 방법

| 빠진 것 | 근거 | 메우는 방법 |
|---|---|---|

### 5.3 재생 원리와 찾은 함정 (자체 시험으로 확인)
- 객체는 "create + 그 순간 속성 전부" 가 기록되고 `PxPhysics.<목록> add` 가 뒤따른다 → 그때 같은 인자로 만든다.
  그 뒤 set 은 API 호출이라 같은 setter 를 부른다. `PxScene.elapsedTime` set = simulate() 표시(`NpScene.cpp:2839`),
  그 뒤 stopFrame 까지는 fetchResults 결과(`NpSceneFetchResults.cpp:277-470`)라 적용하지 않고 비교만 한다.
- 함정 ① **정규화하는 setter**(setGlobalPose, setCMassLocalPose, PxShape::setLocalPose, 생성 자세, PxJoint::setLocalPose)는
  정규화된 값이 기록된다. 그대로 다시 넣으면 한 번 더 정규화돼 끝 비트가 바뀐다 → getNormalized() 결과가 기록값과 비트 같은
  입력을 찾아 넣는다(자체 시험 30회 전부 찾음).
- 함정 ② **값이 같아도 setter 를 불러야 한다**: setDriveTarget 은 자동 깨우기(`NpArticulationJointReducedCoordinate.cpp:400`)가
  걸리고, 안정화(stabilization)가 깸 카운터를 보므로 동역학이 달라진다.
- 함정 ③ API 한 번이 속성 여러 개를 남긴다(setDriveParams → 8개 배열, setSolverIterationCounts → 2개 등) → 한 호출로 되돌린다.
- 함정 ④ 생성 기록과 이어지는 API 호출의 경계: 같은 속성이 두 번 나오면 두 번째부터 API 호출이다.
- 함정 ⑤ 프레임 명령의 문맥 핸들은 장면 포인터다(`OmniPvdPxSampler.cpp:101`).

## 6. 최종 엔진 구조 (손으로 짠 C++ → CUDA)

```
[한 번] 공식 평가기 + physx_capture.py ──▶ 장면 추출물 (OVD·convex.bin·filters·시각 메시)  ─ 에셋 파생물, git 제외
                                                     │ 변환 (우리 이진 형식: 강체·모양·관절체·재질을 SoA 배열로)
                                                     ▼
[학습] 우리 엔진 ──  C++ 참조판(한 판, CPU)  ──비트 비교──▶  층 0 정답지(PhysX 재생)
                  └ CUDA 판(판 수천~수백만, SoA, 판 하나 = 스레드 묶음)  ──비트 비교──▶  C++ 참조판
                  제어기·보조 잡기·물체 상태·BDDL 도 같은 GPU 메모리에서 (파이썬 없음)
                  렌더: 우리 CUDA 래스터 → 정책 입력 (통계 검증)
```

- 옮기는 순서(각 단계마다 정답지와 비트 비교 후 다음):
  1. 강체 적분 + 중력 (접촉 없음) → 2. 관절체 Featherstone 정동역학 + 드라이브(위치·속도) + 관절 한계·마찰·흉내 관절
  → 3. 접촉 생성(PCM: 볼록-볼록, 볼록-상자/평면, 볼록-삼각 메시) → 4. TGS 접촉 준비·풀이(마찰 패치) → 5. 넓은 단계(PABP)와
  섬·잠 관리(결정성의 핵심: 쌍·제약 순서) → 6. 고정/구 조인트(보조 잡기) → 7. 광선 질의(보조 잡기) → 8. CUDA 로 옮기기.
- 비트 동일을 지키려고: 부동소수 축약 끔(`-ffp-contract=off`, CUDA `-fmad=false`), PhysX 의 SIMD 4묶음 배치 순서 그대로,
  SSE 근사 연산(`_mm_rsqrt_ps` 등)을 쓰는 곳은 결과표를 그대로 흉내(CPU 제조사마다 다를 수 있음 — 인텔/AMD 차이는 수치로 기록).
- 판 여러 개: 장면 하나를 SoA 배열로 펴고 판마다 복제. 판 사이 상호작용 없음 → GPU 에서 판 하나를 워프/블록 하나에 두는
  방식(추정 — 장면 크기(물체 188~1,328개)에 따라 블록 크기 정함).

  모양 플래그·거르개 값(트렁크 0, 뒷유리 그룹 3)·국소 자세·척도, 볼록 메시(원본 그대로; 근사 12 개는 모두 바깥 덤불). omni 거르개 셰이더·pairFound 이식도 원본과 대조.
- 남은 후보(다음): omni 의 접촉 보고 대상 쌍 처리, OVD 에 없는 형상 값(척도 회전 등)의 실제 값, 같은 관절체 안 접촉의 풀이 경로 차. 이 문제는 로봇 관절체에도 걸리므로 S1·S2 보다 앞에 둔다.

## 10. 자체 평가 파이프라인 (GPU 물리 + 판 묶음 + 네이티브 π0.5, 한 GPU)

사용자 결정(09-29): "우리 자체 평가는 빠르게 할 수 있게 물리도 GPU로".

```
한 GPU 안 (호스트 왕복 없음, 장치 버퍼끼리)
  π0.5 네이티브 엔진(C++/CUDA, 별도 작업) ── 행동 묶음 [N판 × 23] ─┐
                                                                  ▼
  제어기 커널 (관절 위치·속도 목표, 바닥 속도, 그리퍼)  ─▶ 드라이브 목표 [N판 × 자유도]
  물리 커널 × 4 서브스텝 (층 2: 손으로 짠 CUDA, CPU PhysX 와 비트 동일)
     넓은 단계 → 접촉 생성(PCM) → 섬 묶기 → TGS 풀이(강체+관절체+조인트) → 적분 → 잠
  보조 잡기 커널 (광선·접촉 → 고정 조인트 생성/해제)
  물체 상태 커널 (열림·켜짐·안/위·온도·잘림 …) → BDDL 술어 커널 → 종료·q_score
  렌더 커널 (추후: 카메라 3대 RGB·깊이) ──────────────────────────── 관측 [N판] ─▶ π0.5
```

- 판 묶음: 장면 하나를 SoA 배열로 펴고 판마다 상태만 복제(형상·재질·관절 구조는 공유). 판끼리 상호작용 없음 →
  판 하나를 CUDA 블록(또는 워프) 하나에 두고, 판 안의 섬·접촉은 PhysX 와 같은 순서로 처리한다(비트 동일의 조건).
- 비트 사슬: 층 0(Linux 공식 CPU PhysX) = 층 1(우리 C++) = 층 2(우리 CUDA). 옮기는 단위마다 층 1 과 층 2 를 같이 만들고
  세 쪽을 같은 입력으로 비트 비교한다. PhysX 자체 GPU 파이프라인(`USE_GPU_DYNAMICS`)은 CPU 와 결과가 달라 자체 평가에 쓰지 않는다
  (필요하면 "얼마나 다른지"만 참고로 잰다).
- 목표 처리량 (추정, 잴 것): 물리만 판 4,096 개 동시에 판·스텝/초 10⁵ 급. 대조군은 CPU PhysX 단일 코어(볼록 300개 더미 ≈ 230 스텝/초),
  공식 평가기 10.4 스텝/초. 전체 루프에서는 π0.5 추론이 병목일 것(판 묶음 추론으로 줄임, π0.5 작업 쪽 수치 사용).
- 메모리 (추정): 판 하나 상태 = 강체 수백 개 × 약 200 B + 관절체 링크 수십 개 + 접촉 수천 개 × 약 100 B ≈ 0.5 MB →
  판 4,096 개 ≈ 2 GB. π0.5 약 9 GB 와 같이 24 GB GPU 에 들어간다(16 GB 인 이 PC 는 판 수를 줄인다).
- 첫 실측 (자유 강체만, 접촉 없음 — 처리량 판단에는 아직 의미 작음): 판 1,024 개 × 강체 1,000 개 × 600 서브스텝을
  RTX 5070 Ti 에서 0.034 s (강체·서브스텝 1.8×10¹⁰/초). 같은 장면 PhysX 단일 스레드 0.187 s(판 하나). 층 0 = 층 1 = 층 2 비트 다름 0.

### 10.1 포팅 평가기 인터페이스 (사용자 결정 09-29: 평가기 두 개를 나란히)

| | 공식 원본 평가기 | 우리 포팅 평가기 |
|---|---|---|
| 쓰임 | 제출 수치 | 개발·학습 실험 (판 N 개) |
| 몸통 | OmniGibson + Isaac Sim (CPU PhysX, RTX) | 이 엔진 (층 2 CUDA 물리 + 제어기·보조 잡기·물체 상태·BDDL 커널, 렌더 추후) |
| 붙이는 곳 | 평가기 가속 에이전트의 실험 실행기 기본값 | 같은 실행기의 `--backend ported` |

- **입력은 원본과 같게**: 과제 이름, 인스턴스 번호(`--instance-indices`, `--mode public_test`), 로봇 설정 yaml, 제한시간
  (사람 평균 × 1.5 = `EVAL_TIMEOUT_MULTIPLIER`, 또는 `--max-steps`), 정책 서버 주소(웹소켓, 같은 프로토콜). 판 수는 `--num-envs`.
- **장면은 원본에서 한 번 뽑은 추출물**을 쓴다(과제·인스턴스별 OVD + 볼록 메시 + 거르개 표 + 물체·방 이름표). 에셋을 직접 읽지 않는다
  → 에셋 파생물이라 저장소 밖(`~/engine-data/scenes/<과제>/<인스턴스>/`)에 둔다.
- **결과 JSON 은 원본과 같은 형식·파일 이름**: `json/<과제>_<인스턴스>_<롤아웃>.json` 에 `task, instance_id, rollout_id, steps, success,
  agent_distance{base,left,right}, normalized_agent_distance, q_score{final}, time{simulator_steps, simulator_time, normalized_time}`
  (원본 예: `outputs\eval_turning_on_radio_20260929_195500_nf_a\json\turning_on_radio_301_0.json`).
- **비교(compare)는 검증 사다리와 같은 도구**: 포팅 평가기는 `--trace` 에서 원본과 같은 키로 `trace.npz` 를 쓴다
  (`action, active, terminated, truncated, robot_pose, robot_qpos, robot_qvel, obj::<BDDL 이름>, goal_satisfied, agent_delta,
  obs::robot::proprio, obs::robot::cam_rel_poses, static::scene_offset`) → `tools\trace_compare.py <원본 결과> <포팅 결과> --strict` 로
  층 1·2(물리)·층 2(판정)를 한 번에 본다. 영상 키(`obs_hash::`)는 렌더가 생기기 전까지 비교에서 빠진다.
- 같은 행동열 재생(`tools\replay_policy_server.py`)을 두 평가기에 똑같이 붙이면 "같은 인스턴스·행동열 → 차이" 가 된다.
- **관측 시점 규칙 (09-30, render B 실측)**: 공식 관측 영상(스텝 k)은 **스텝 k-1 끝의 장면 상태로 그려진다**(렌더가 한 스텝 늦다).
  k-1 자세로 그리면 depth 차 중앙 0.05~0.24 µm(1~2 ulp), 같은 스텝 자세로 그리면 중앙 0.04~1.9 mm·머리 p99 6 cm. 반면 `proprio`·`cam_rel_poses` 는
  스텝 뒤 값이다. 이 한 스텝 어긋남이 공식 동작이므로 포팅 평가기도 **영상은 물리 스텝 전 자세로, proprio·cam_rel_poses 는 스텝 뒤로** 똑같이 어긋나게 낸다.

### 12.2 비트 규칙 (모든 모듈 공통, 어기면 비트가 깨진다)

1. **float32, 연산 순서는 PhysX 원본 그대로.** 식을 정리·인수분해·재배열하지 않는다. 원본 줄을 주석으로 단다(`파일:줄`).
2. **컴파일**: CPU `-O2 -ffp-contract=off -fno-fast-math`, CUDA `-fmad=false -prec-div=true -prec-sqrt=true -ftz=true`
   (`tests/CMakeLists.txt` 의 `ENGINE_*_FLAGS`).
3. **FTZ·DAZ**: PhysX 는 simulate 안(풀이·접촉 등)에서 SSE 를 FTZ+DAZ 로 둔다(`PxSIMDGuard`, `physx/include/foundation/unix/PxUnixFPU.h`).
   호스트 참조판은 그 구간을 `FtzScope`(tests 의 예) 안에서 돌리고, GPU 는 `-ftz=true`. 생성·setter(API 구간)는 FTZ 없이.
4. **수학 함수**: 제곱근 `psqrt`, 사인·코사인 `glibc::sinf/cosf`(`common/glibc_sincosf.h`, glibc 2.35 FMA 판),
   **`glibc::atanf/atan2f/asinf/acosf`(`common/glibc_trig.h`, 09-30 통일 — joints 이식본을 옮김)**. 모두 float 전 범위 libm 과 비트 동일
   (`tests/common/test_glibc_trig`: atanf·asinf·acosf 2^32 전부 FTZ 켬·끔, atan2f 특수 361 쌍 + 무작위 2.7 억 쌍 — CPU 다름 0, GPU 는 `test_glibc_trig_gpu`).
   모듈 사본(`core/joints/glibc_trig.h`, `core/contact/px/glibc_acosf.h`)은 **include 를 `core/common/glibc_trig.h`(`eng::glibc`)로 바꾸고 자기 시험을 다시 돌린 뒤 지운다**.
   다른 libm 함수(exp·log·tan …)가 필요하면 리드에게 — glibc 이식 + 2^32 전수 시험 후 common 에 넣는다.
5. **PhysX SIMD(aos) 코드**: `Vec3V/Vec4V/FloatV/BoolV/QuatV/Mat33V` 와 그 함수는 **`common/aos.h` 하나만** 쓴다(12.7, 모듈별 사본 금지).
   PhysX 원본 헤더에서 기계적으로 만든 것이라 셔플·가로 연산 순서가 원본 그대로다.
   `…Fast` 함수(rcpps/rsqrtps 근사)는 `sse_emu.h` 가 `approx_tables_zen5.inc` 표로 흉내 낸다(호스트·GPU 같은 값). **비트 기준 CPU 는 AMD(Zen)**: 대회 성능 측정 장비가
   AMD Ryzen 9 7950X(Zen 4)(`docs/raw/site_challenge_evaluation.md:193` 부근), 이 PC 는 Ryzen 9 9950X(Zen 5). 인텔은 근사값이 달라
   그 경로(삼각 메시 PCM `GuPCMTriangleContactGen.cpp:103`, 상자-상자 `GuPCMContactBoxBox.cpp:140`)가 다를 수 있다. 최종 평가 장비 CPU 는 원문에 없음.
6. **순서**: 배열 순회·해시맵 순회·쌍 목록·섬 순서가 결과 순서를 정하는 곳은 PhysX 순서를 그대로 재현한다(`PxHashMap` 순회 포함).
   PhysX CPU 는 스레드 수와 무관하게 결정적이다(자체 시험 스레드 1·4 비트 동일) → **단일 스레드 실행 순서**를 기준으로 옮긴다.
7. **메모리**: 판마다 고정 용량 배열(넘치면 오류 표시), 동적 할당·포인터 사슬 없이 번호(index)로 잇는다. GPU 판 하나 = 블록 하나.

  한 1D 제약 묶음을 **어떻게 준비·풀지**는 joints 함수를 부른다(접촉 제약 준비·풀이는 solver 자신).
- **joints ↔ articulation**: 관절체 링크에 붙은 조인트(한쪽이 링크)는 링크의 **단위 응답**(unit response, 링크에 단위 충격을 줬을 때의 속도 변화)을
  articulation 함수로 받아 쓴다(`DyFeatherstoneArticulation.cpp` 의 getImpulseResponse 계열, `DySolverExt.h`). 행 준비는 joints, 응답 계산은 articulation.
- **joints → omni**: 장면 질의(광선·겹침) 함수. omni 의 보조 잡기가 부른다.
- **omni → 전체**: 제어기가 쓰는 것은 드라이브 목표·속도 목표·관절 힘(=PhysX API 호출과 같은 효과), 보조 잡기는 조인트 생성/해제 요청뿐.

### 12.6 GPU 잠금 (전원 공통 — CUDA 시험·Kit 부팅·평가기 등 GPU 를 쓰는 모든 일)

GPU 는 한 장(16 GB)을 여러 작업이 나눠 쓴다. **쓰기 전에 잠금을 잡고, 끝나면 바로 푼다.**
- 잠금 = `C:\behavior-2026\.gpu_lock` 디렉터리 만들기(WSL 에서는 `/mnt/c/behavior-2026/.gpu_lock`). 만들기에 성공한 쪽이 주인.
- 안에 `owner.txt` (한 줄에 키=값): `owner=` `purpose=` `start_epoch=` `end_epoch=`(유닉스 초) `vram_gb=`.
- 이미 있으면 30~60 초 간격으로 다시 시도. **오래됨 판정은 `now_epoch > end_epoch + 900` 하나뿐**. 시간 문자열로 계산하지 말 것
  (`date -d "<시각> + 15 min"` 은 "+15" 를 시간대로 읽어 틀린다 — 09-29 실제 사고). `end_epoch` 를 못 읽으면 지우지 않는다.
- 한 번에 30 분 이내. 남의 잠금은 풀지 않는다. WSL RAM(30 GB)도 빠듯하니 큰 작업은 잠금 기간 안에서만.
- **디스크 (09-30 공지)**: C: 가 꽉 차서 render 평가기가 죽었다(저장 공간 센스가 %TEMP% 청소 중 og.tempdir 삭제). WSL 디스크(ext4.vhdx)도 C: 위에 있어서
  WSL `df` 의 여유는 가짜다. ① 1 GB 넘는 기록(OVD·덤프·영상)은 쓰기 전에 C: 여유를 본다. ② 끝난 중간 파일은 **자기 것만 이름을 지정해** 바로 지운다.
  ③ segfault 하는 시험은 한 번에 약 2 GB 덤프(`%TEMP%\wsl-crashes`)를 남긴다 → 되풀이 실행 말고 gdb 로 본다. 스크립트에는 `ulimit -c 0` 를 둔다.

- **대기표 형식은 하나: `<20자리 0 채움 epoch_ns>_<owner>`, 내용 `owner= purpose= host= pid= start_epoch= end_epoch= minutes= vram_gb=`, 기다리는 동안 end_epoch=now+60 갱신.

### 12.7 aos(SIMD 수학) 하나로 통일 (09-29 결정)

같은 일을 하는 사본이 모듈마다 생겼다: contact `core/contact/px/{aos.h, sse_emu.h, gen_aos.inc}`, solver `core/solver/saos.h`(FloatV 한 칸),
joints `core/joints/jsimd.h`(작은 손 집합). **`core/common/aos.h` 하나로 합친다.**

**무엇인가**
- `aos.h` = PhysX 5.6.1 aos 헤더 7개(`PxUnixSse2AoS.h`, `PxVecMath.h`, `PxUnixTrigConstants.h`, `PxVecMathSSE.h`, `PxUnixSse2InlineAoS.h`,
  `PxVecQuat.h`, `PxVecTransform.h`)를 공식 Linux 빌드와 같은 분기(SSE2, SSE4 없음, clang)로 골라, `__m128`→`sse::m128`, `_mm_*`→`sse::_mm_*`
  **이름만 바꾼 생성물**이다(`scripts/gen_aos.py`, 손으로 고치지 말 것). 이름 공간 `eng::aos`, 함수 이름은 PhysX 와 같다.
- `sse_emu.h` = SSE 명령의 칸별 흉내(호스트·CUDA 공용). min/max 는 maxps/minps 규칙, comi 는 NaN 이면 0, rcpps/rsqrtps 는 Zen 5 표.
- 전역 상수(삼각 계수·마스크)는 호스트판 `이름_h` 와 GPU `__constant__` 판 `이름_d` 두 벌이고, `ENG_G(이름)` 으로 고른다.

**증명** (`tests/common/`, 생성기 `scripts/gen_aos_test.py`)
- `test_aos_diff`: 값 인자만 받는 aos 함수 **286개** × 난수 2만 입력(보통 값·큰/작은 값·특수값 섞음, 형별 규칙 지킴)을 진짜 PhysX(SSE 하드웨어)와
  비교한다. 우리 CPU판: **다른 함수 0개, 비교 572만 번**(FTZ/DAZ 켬·끔 둘 다).
- `test_aos_diff_gpu`: 같은 함수를 CUDA 커널에서 돌려 PhysX CPU 결과와 비교한다(층 2). **다른 함수 0개.**
- 시험이 제대로 잡는지 확인: 우리 쪽만 FMA 축약을 허용해 빌드하면 CPU·GPU 모두 **46 함수가 1 ulp 다르게** 나온다(M33Inverse 등).
- 시험에서 뺀 것: 포인터 인자(적재·저장), 템플릿(`V4Perm` 등), 16비트 정수 연산, 비트마스크 등 43개(`SKIP` 목록). 적재·저장은 memcpy 라 뜻이 자명하다.

**FloatV 한 칸 표현 (solver 제안)**
- PhysX 는 FloatV 를 SSE 네 칸에 같은 값으로 들고 다닌다. 한 칸만 들고 다니면 GPU 레지스터·연산이 준다.
- 근거 시험: FloatV 를 돌려주는 함수(와 FloatV 만 받는 BoolV 함수) **52개**가 진짜 PhysX 에서 네 칸이 비트까지 같다(NaN 은 값 무늬 무시).
  - **예외 1: `V4ExtractMax/Min`.** +0 과 -0 이 섞인 입력이면 칸마다 0 의 부호가 갈린다(maxps 는 같으면 둘째 인자).
    PhysX 안에서 쓰는 3곳(`GuPersistentContactManifold.h:173,496`, `DyResidualAccumulator.h:127`)은 모두 `V4Abs` 결과를 넣어 -0 이 없다 → 영향 없음.
  - **예외 2: NaN 값 무늬.** 칸마다 다를 수 있다. 비교 규칙상 NaN 끼리는 같은 것으로 본다.
- 구현: 별도 사본 대신 **`-DENG_AOS_FLOATV_ONE_LANE` 컴파일 선택**으로 넣었다. `FloatV` 가 `sse::FV1{float}` 가 되고, 벡터로 쓰일 때 네 칸으로 복제된다.
  식은 생성물 그대로이고 형변환만 끼므로, 인라인 뒤 안 쓰이는 칸 계산은 컴파일러가 지운다.
  같은 차분 시험(`test_aos_diff_1lane`): **예외 1 의 두 함수(±0 섞인 입력)만 다르고 나머지 284개는 비트 동일.**
- 기본은 네 칸판(선택 끔)이다. 한 칸 선택은 모듈 시험(PhysX 정답지 비교)이 선택 켬에서도 비트 동일일 때 그 모듈 빌드에서 켠다.
  이유: 함수 단위 시험은 "PhysX 가 Vec 값을 FloatV 자리에 그대로 넘기는" 코드(형이 같아 원본에선 합법)를 못 잡는다. 이건 모듈 단위에서만 드러난다.

**Px 값 형 한 벌 (09-30 결정 (1))**: `PxVec3·PxVec4·PxQuat·PxMat33·PxTransform·PxBounds3·PxPlane` 과 PxMath 스칼라 함수는

### 14.3 렌더러 입력 형식 (변환기 출력 = 작업자 B 의 불러오기 입력)

폴더 하나에 `.npy` 여러 장(작은 끝, C 순서). 읽기·쓰기는 `tests/render/io/npy.h`. 행렬 **Aff = float32 12 개, 행 우선 3x4, p' = A p + t**
(USD 행 벡터 행렬 M 에서 `A[r][c] = M[c][r]`, `t[r] = M[3][r]`). 인스턴스 월드 = `anchor_world ∘ rel`.

| 파일 | 모양·형 | 뜻 |
|---|---|---|
| `geom_ntri` / `geom_flags` | [G] i32 | 기하별 삼각형 수 / 1 = 모서리 법선 있음, 2 = UV 있음 |
| `tri_pos` | [T,9] f32 | 삼각형 꼭짓점 v0,v1,v2 (물체 공간). T = Σ geom_ntri, 기하 순서로 이어 붙임(BLAS 굽기 전 순서) |
| `tri_nrm` / `tri_uv` | [T,9] / [T,6] f32 | 모서리 법선(없으면 0) / 모서리 UV(없으면 0). 면 삼각분할은 부채꼴(면 첫 꼭짓점 기준) |
| `tri_slot` | [T] i32 | 재질 칸: 0 = 메시 전체 재질, k ≥ 1 = k 번째 GeomSubset |
| `inst_geom` `inst_anchor` `inst_slot_base` `inst_flags` | [I] i32 | 인스턴스(USD 메시 prim) → 기하, 기준 prim, `slot_mat` 시작, 깃발(1 양면, 2 로봇 몸, 4 왼손 좌표) |
| `inst_rel` | [I,12] f32 | 기준 prim 에 대한 상대 Aff |
| `slot_mat` | [S] i32 | 재질 칸 → 재질 번호 (재질 없는 메시는 마지막 "default" 회색 OmniPBR) |
| `mat_f` | [M,24] f32 | 열: albedo rgb, tint rgb, uv_scale uv, uv_off uv, uv_rot(라디안), roughness, metallic, opacity, emissive rgb(세기 곱함), albedo_add, albedo_brightness, albedo_desaturation, rough_tex_influence, metal_tex_influence, opacity_threshold, specular_level (`meta.json` `mat_f_cols`) |
| `mat_i` | [M,8] i32 | 열: tex_albedo, tex_rough, tex_metal, tex_normal, tex_opacity, tex_emissive(-1 없음), flags(1 opacity 켬, 2 opacity 텍스처, 4 방출, 8 건너뜀=유리·투과, 16 모르는 셰이더), kind(0 OmniPBR, 1 OmniSurface, 2 OmniGlass, 3 UsdPreviewSurface, 9 기타) |
| `tex_info` / `texels` | [K,4] i64 / [N,4] u8 | (w, h, 텍셀 시작 번호, 1 = sRGB) / RGBA8 텍셀 (행 우선, 위→아래 = 이미지 파일 순서) |
| `light_i` | [L,4] i32 | type(0 구, 1 사각, 2 원판, 3 먼 빛, 4 돔, 5 원기둥), anchor(-1 = 고정: `light_rel` 이 월드), 처음 보임, 0 |
| `light_f` | [L,16] f32 | radiance rgb(= color·intensity·2^exposure·색온도), radius, width, height, length, angle(도), cone angle(도), cone softness, treatAsPoint, normalize, intensity, exposure, diffuse, specular (`light_f_cols`) |
| `light_rel` | [L,12] f32 | 조명 Aff (anchor -1 이면 첫 프레임 월드). 빛은 조명 좌표 -Z 로 나감(USD) |
| `frame_<k>/anchor_world` | [A,12] f32 | 스텝 k 기준 prim 월드 Aff |
| `frame_<k>/inst_visible` | [I] u8 | 메시 보임 |
| `frame_<k>/light_world` | [L,12] f32 | 조명 월드 Aff (움직이는 조명 확인용) |
| `frame_<k>/cam_<역할>` | [16] f32 | Aff 12(열 = 카메라 x·y·z 축(정규화, 카메라는 -Z 를 봄) + 위치) + tanx, tany, znear, zfar. 역할 = head, left_wrist, right_wrist. 해상도는 `meta.json` `frames[].cams[역할].w/h` |
| `meta.json` | | 개수, 열 이름, 경로 이름표(anchor·inst), 재질 종류 수, 못 찾은 텍스처, RTX 설정, 프레임별 카메라 원값·`cameraProjection`·검은 칸 |

- **렌더러가 실제로 읽는 것은 한 파일 형식**이다: `tests/render/capture/convert_scene.py <덤프>` 가 덤프에서 바로
  `scene.rsc` + `frame_<k>.rfr` (작업자 B 의 `core/render/rsc_io.h` 머리 주석 형식)을 만든다. 위 `.npy` 표는 비교 도구·사람 확인용이다.
  - 재질 f32[24]: 0-2 albedo(텍스처 있으면 tint, 없으면 constant·tint), 3 tex_albedo, 4-5 uv_scale, 6-7 uv_off, 8 uv_rot(라디안), 9 roughness,
    10 metallic, 11 opacity, 12-14 emissive, 15 flags(1 = enable_opacity), 16 albedo_add, 17 albedo_brightness, 18-23 비움.
  - 조명: 조명마다 기준 prim 칸을 하나 더 둔다(번호 = 메시 기준 prim 수 + 조명 번호, rel = 항등). 프레임의 기준 prim 행렬 뒤에 조명 월드 행렬이 붙는다.
    조명 f32[32]: 0 type, 1 anchor, 2 visible, 3-5 radiance, 6 radius, 7 width, 8 height, 9 length, 10 angle, 11 cone angle, 12 cone softness, 13-24 rel.
  - 카메라 f32[20]: world 12(열 = 정규화한 카메라 축 + 위치), tanx, tany, znear, zfar, w, h. 순서 head, left_wrist, right_wrist.
    tan 은 첫 기록 스텝의 `cameraProjection`(있으면)을 모든 프레임에 같이 쓴다.
  - 프레임 영상 이름 = 덤프 키 그대로: `img::<역할>::rgb`(u8 H×W×4), `img::<역할>::depth_linear`(f32), `noise<r>::<역할>::…`.
  - 검산: `tests/render/io/rsc_check.cpp`(렌더러 불러오기로 읽어 개수·범위·카메라·영상 목록을 찍음, `~/engine-build/render-tools/rsc_check`).
- `tanx = (horizontalAperture/2)/focalLength`, `tany = tanx·H/W` (정사각 픽셀). `cameraProjection` 이 있으면 `P[0][0] = 1/tanx`, `P[1][1] = 1/tany` 로 검산한다.
- 픽셀 (행 r, 열 c) 중심 광선: `x = (c+0.5)/W·2-1`, `y = 1-(r+0.5)/H·2`, 카메라 방향 `(x·tanx, y·tany, -1)` → 맞은 t 가 그대로 depth_linear.

#### 14.6.1 잡음 제거 경로 (09-30, `core/render/denoise.h`)

공식 RTX(RaytracedLighting)는 픽셀당 광선 몇 개 + 잡음 제거기로 매끈한 영상을 낸다. 우리도 같은 생각으로 짰다(라이브러리 없이 손으로).
1. `shade_gbuf` (`denoise.h:50`): 1차 맞은 점의 **알베도·법선(팔면체 16+16 비트)·거리·인스턴스**를 G 버퍼에 적고,
   빛은 **알베도를 곱하기 전 확산 조도**(직접광 + 튕김 + 돔)와 **알베도에 안 곱하는 빛**(방출 + 반사)으로 나눠 적는다.
   튕김 1 번 이상에서 온 표본은 채널마다 `clamp_ind / 노출` 로 자른다(반딧불 — 작은 밝은 조명을 튕김 광선이 우연히 맞힌 점).
2. `atrous_pixel` (`denoise.h:172`): 가장자리를 피하는 à-trous 웨이블릿(Dammertz 2010). 5×5 B3 스플라인, 간격 1·2·4·8(4 번이면 반지름 30 픽셀).
   이웃 가중치 = 커널 × **같은 인스턴스만** × 법선 cos³² × 평면 거리 `1/(1+(|n·(q-p)|/(0.01·거리·간격))²)`.
   조도만 흐리므로 텍스처는 선명하게 남는다.
3. `compose_pixel`: `알베도 × 조도 + 반사·방출` → 노출 → 톤매핑 → sRGB 8 비트.
- 합 순서는 (dy, dx) 이중 반복으로 고정, 초월 함수 없음(cos³² 은 제곱 다섯 번) → 층 1 = 층 2 비트.
- 층 2 는 커널 셋(`kShade`/`kAtrous`/`kCompose`, `render_cuda.cuh`), 층 1 은 같은 함수를 스레드로 돌리고 단계 사이에 합류한다(`render_host.h`).
  작업 공간은 픽셀당 72 B(G 24 B + 조도 핑퐁 2 × 24 B): 720²+480²+480² 한 판 = 71 MB, 224² × 3 한 판 = 11 MB.

### 16.2 비트 규칙에서 새로 찾은 것

- **aos 3곳**: 바닥 역관성 `invertInertiaV`(`DyFeatherstoneArticulationUtils.h:564`), `translateInertia`(:829), 응답 행렬 곱. SSE `V3Dot` 은
  `(x+z)+y` 순서(`PxVecMathSSE.h:965`, 이 빌드엔 SSE4 없음), `M33Neg` 은 `0 - x`. 스칼라 식으로 칸마다 같게 짰고 모듈 시험으로 확인했다
  (12.7 의 `common/aos.h` 로 바꿀 수 있으나 이 세 곳뿐이라 보류 — 바꾸면 같은 시험으로 다시 확인).
- `PxClamp(v, lo, hi) = PxMin(hi, PxMax(lo, v))` — 인자 순서가 다르면 ±0 이 갈린다(`PxMath.h:142`).
- 원본 버그도 그대로: 관절 속도 비율 계산이 축 배열을 **dof 번호로** 읽는다(`DyFeatherstoneArticulation.cpp:4025`), 회전 드라이브 오차가 `jointOffset` 만 쓴다(:2549).
- **applyCache(위치)는 링크를 바로 순간이동**시킨다(`DyFeatherstoneInverseDynamic.cpp:410`). 이걸 빼면 150 스텝 순간이동 뒤 1e-1 까지 벌어졌다.
- **잠 시점**: sleepCheck 가 비활성 요청을 낸 다음 스텝에도 관절체는 **풀린다**(섬 관리가 풀이와 병렬). 적분 뒤 속도만 0 으로(강체와 달리 자세 되돌리지 않음).
- PhysX checked 빌드는 잘못된 API 호출을 무시한다(정적 < 동적 마찰, 링크 관성 0, 한계 low > high 등). 우리 API 도 같은 검사로 무시한다 — 안 그러면 한쪽만 값이 바뀐다.
- 무작위 관절체 일부는 발산해 NaN 이 된다. 양쪽이 **같은 스텝에 같은 칸이** NaN 이 되고(NaN 부호만 다름) 그 앞은 전부 비트 같다 → 시험은 "양쪽 NaN" 으로 따로 센다.

### 16.4 solver·joints·contact 가 쓰는 자리

- **solver**: 섬 묶음에 관절체가 있으면 PhysX 와 같은 자리에서 `computeUnconstrainedVelocitiesTGS(a, dt, g, 1/lengthScale, extEvery)` →
  `setupSolverConstraintsTGS(a, stepDt, invStepDt, dt)` → 반복마다 `solveInternalConstraints(...)`(eSOLVE_ARTICULATION_CONTACT_LAST 이고
  접촉 묶음이 있으면 PhysX 처럼 접촉 앞/뒤 두 번: `firstPassConfig/secondPassConfig`, `DyTGSDynamics.cpp:2595-2640`) → 위치반복 끝마다 `recordDeltaMotion(a, stepDt, scratch)` → `saveVelocityTGS(a, 1/dt)` →
  속도반복 → `updateBodiesTGS(a, dt, scratch)` → `sleepCheck`. 위치/속도반복 수는 **섬 묶음 최댓값**을 넣어야 한다(`DyTGSDynamics.cpp:1690-1704`).
  잠 요청이 난 관절체는 다음 스텝을 풀고 `putToSleep`(`ScPipeline.cpp:2702`).
- **정적 제약(링크-정적 물체 접촉·1D 행)**: PhysX 는 관절체 내부 풀이 안에서 링크별로 푼다(`DY_STATIC_CONTACTS_IN_INTERNAL_SOLVER`).
  우리 `solveInternalConstraints` 는 템플릿 인자 `Static` 을 받는다: `count1D(a, link)`, `countContact(a, link)`, `solve1D/solveContact(a, link, i, v, imp, dv, data)`.
  구현 `ArtStatic`(art_static.h)이 링크별 목록(`StaticLists`)을 읽고, 목록 번호 i 의 제약을 푸는 함수 두 개(solver 가 `solveExt1DStep`·
  `solveExtContactStep` 을 감싸 넣음)를 부른다. 준비는 `prepareStaticList(목록, 개수, …, linkA, linkB, prep)` — 정렬·당기기·링크별 개수는
  관절체가, 한 제약의 준비 식(`SetupSolverConstraintStep`·`createFinalizeSolverContactsStep`)은 `prep` 로 solver/joints/contact 가.
  목록에 넣는 시점은 PhysX 처럼 제약 분할 때(`DyConstraintPartition.cpp:269`, solver 몫), 목록 비우기는 `clearStaticLists`(준비 시작 때).
- **joints·contact (링크에 붙은 동적 제약)**: `getImpulseResponse(a, link, 선형, 회전, dv선형, dv회전)`(= `FeatherstoneArticulation::getImpulseResponse`),
  풀이 중 속도 `pxcFsGetVelocity`, 충격 적용 `pxcFsApplyImpulse(s)`. 번호는 LL 링크 번호(`a.ll[생성 번호]`).
  joints 의 `Art` 템플릿 인자(`core/joints/tgs_1d.h` NoArt 모양)에는 `ArtRef{&a}`(art_adapters.h)를 그대로 넘긴다.
- **omni(제어기)**: `jointSetDriveTarget/Velocity`(자동 깨우기 포함), `applyCache`(텐서 API set_dof_*), `linkGlobalPose`.

### 18.2 붙이기·떼기 순서와 부수효과 (`joint_lifecycle.h`)

PhysX 가 조인트를 만들 때(`PxD6JointCreate`, 두 행위자가 장면에 있으면 바로) 하는 일, 순서대로:
1. 제약 번호를 받는다(`createID`: 빈 번호 목록의 **뒤에서** 꺼내고, 없으면 새 번호). 이 번호가 writeback 칸이자 `getGPUIndex`.
   writeback 칸은 0 으로 초기화, 상수 블록도 0.
2. 두 동적 몸체(강체·링크)마다 `BF_HAS_CONSTRAINTS`(1<<8)를 올리고 `numCountedInteractions++`. **이 수는 잠 판정에 들어간다**
   (`DySleep.cpp:69,142,195`) — 조인트가 붙은 몸체는 잠드는 속도가 달라진다.
3. 섬 관리자에 간선 추가(solver 가 받는 `EV_EDGE_ADD` 사건).
4. 쌍 지도(행위자 쌍 → 조인트)에 넣는다. **이미 같은 쌍이 있으면 덮지 않는다.**

지울 때(`release`): 쌍 지도에서 그 쌍 칸을 지운다(**같은 쌍의 다른 조인트가 넣은 칸이어도 지운다**) → 간선 제거 → 몸체마다 counted--,
남은 제약이 없으면 flag 내림 → 번호 반납은 **미뤘다가 fetchResults 끝(`postReportsCleanup`)에 한꺼번에** 푼다. 풀 때 맨 끝 번호면 번호 수를 줄이고,
아니면 빈 목록 뒤에 붙인다. 그래서 같은 프레임에 지우고 만든 조인트는 새 번호를 받고, 다음 프레임에 만들면 방금 푼 번호를 다시 받는다.

거르개(contact 가 부름): `jointedPairFiltered(a, b)` — 두 몸체 모두 flag 가 없으면 거르지 않고, 있으면 지도에서 찾아 `eCOLLISION_ENABLED` 가 없으면 버린다.
**새 쌍이 생길 때만** 본다. 조인트를 만들어도 이미 닿아 있던 손-물체 접촉 쌍은 그대로 남는다(원본 동작).

깨우기: 조인트 생성·해제 호출은 **wakeCounter·잠 상태를 바꾸지 않는다**(시험으로 확인). 잠든 물체를 깨어 있는 손에 붙이면 깨어나는 것은
다음 simulate 에서 섬 관리자가 새 간선을 처리할 때다(`PxsIslandSim` processNewEdges/processLostEdges — solver 몫). joints 는 간선 사건을 PhysX 순서로 내놓기만 한다.
setDrivePosition/Velocity 의 autowake 는 `d6_joint.h` 의 `needsWake` 규칙(wakeCounter < 재설정값이면 wakeUp, 링크면 그 관절체)으로 호출자가 적용한다.

- 준비: 묶음 머리가 4개면 `prepareD6Step4` 를 먼저 해 보고, 실패하면(행 0 인 조인트가 있으면) 하나씩 `prepareD6Step` 로 준비한다(`DyTGSDynamics.cpp:1181-1259`).

### 17.4 스펙 결정 (이유)

- **섬 순서까지 PhysX 와 같게**: 풀이 결과는 섬 안 몸체·접촉 순서에 따라 비트가 달라진다. 그래서 섬 관리 전체를 그대로 옮겼다.
  PhysX 는 `IG_LIMIT_DIRTY_NODES = 0`(`PxsIslandSim.h:47`)이라 한 프레임 dirty 노드 상한이 꺼져 있다. 우리도 상한을 두지 않는다.
- **마찰 패치는 접촉 관리자별로 스텝을 넘어 이어진다**(두 벌 arena 를 번갈아 쓴다). 0 으로 되돌리는 세 경우는 17.2 에 있다.
- **원본의 이상한 곳도 그대로 둔다**:
  - 4개 묶음 되쓰기는 마찰 개수 대신 `numNormalConstrs` 를 본다(`DyTGSContactPrepBlock.cpp:2897`).
  - 4개 묶음 준비는 이미 끝난 칸의 쓰레기 값도 계산한다.
  - 단일 경로 풀이는 세계 몸체(풀 0)에도 속도를 쓴다.
- **섬 관리가 재운 몸체는 되돌린다**(`ScPipeline.cpp:2640-2690`). 이걸 빠뜨리면 잠드는 스텝부터 달라진다.
- **FloatV 한 칸**: solver 시험 전체가 선택을 켜도 비트 동일이다. 그래서 solver 빌드에서는 켜도 된다. 단 한 실행 파일 안에서 aos 를 쓰는 번역 단위는 모두 같은 선택이어야 한다.
- **GPU = 블록 하나가 판 하나, 판 안은 분할 단위로 스레드가 나눠 푼다 (09-30 v2)**:
  - 준비(기술자·분할·제약 준비)와 되쓰기는 스레드 0 이 차례로 한다. 반복 풀기는 분할 순서대로 진행하고, 분할 안의 묶음 머리를 스레드 32 개가 나눠 푼다.
    같은 분할의 머리는 동적 몸체를 서로 나누지 않으므로 PhysX 단일 스레드 결과와 같다. 몸체 적분도 나눠 한다(`solveBatchPrep / solveBatchIterate / solveBatchFinish`, `solverStepPar`).
  - 예외 1: 넘침 제약(분할 64 개를 넘친 것)이 든 첫 분할은 스레드 0 이 차례로 푼다.
  - 예외 2: 세계 몸체(풀 0)는 여러 머리가 함께 쓴다. 질량이 0 이라 늘 같은 값(+0)이 쓰이므로 결과는 같다. 시험으로도 비트 동일을 확인했다.
  - 판 작업 공간(`SolverBoard`)은 공유 메모리에 하나 두고, 스레드 0 이 스텝 입력을 적용한다. 호스트는 `solverStep`(스레드 1 개)을 쓰며, 같은 함수에 `nt = 1` 을 넘긴 것이다.
- **처리량 (RTX 5070 Ti, 판 512)**: joints 176몸체 장면은 판 안 스레드 1 개일 때 판·스텝/초 34,425 이고, 32 개일 때 55,443 이다(CPU 단일 스레드 대비 107 배).
  boxes 256몸체 장면은 1 개일 때 95,357, 32 개일 때 124,700 이다(97 배). 판 64 개면 GPU 가 덜 차서 14,153 / 30,207 이다.
  FloatV 한 칸 판도 같은 수준이다(55,013 / 121,682). 큰 함수는 `__noinline__`(`SV_HDN`)으로 두었고, 스택은 32 KB 이다.

### 17.5 남은 것 / 막힌 곳

- **관절체**: 16.4 의 자리(관절체 내부 풀이·정적 제약 목록·충격 응답)를 반복 루프에 붙인다. 섬 관리의 관절체 노드도 아직이다.

- **Sc 층 사건 처리를 우리 것으로 바꾸기**: 조인트 끊김 → 섬 간선 제거·캐시 지움 대상 고르기(행위자 상호작용 수 비교), 새 관리자·잃은 닿음 → 깨움.

- 운동학 몸체, CCD, 반복마다 외력(`externalForcesEveryTgsIteration`, 기본 꺼짐), 잔차 보고.
- 접촉 입력을 contact 모듈 출력으로 바꿔 끼우기(형식은 12.3 에 확정). 지금 시험은 PhysX 가 만든 접촉을 넣는다.
- GPU 처리량 다음 단계: 준비(접촉 준비가 가장 무겁다)는 아직 스레드 0 혼자 한다. 묶음 머리별 준비는 서로 독립이지만, 제약 자료 arena 의 자리 잡기를 먼저 해야 나눌 수 있다.
  또 4칸 묶음은 판 안 32 스레드 중 한 스레드가 네 칸을 다 푼다. 칸을 스레드에 나누는 것도 다음 후보다.

### 17.2 비트 규칙 (omni 에서 새로 찾은 것)

- **warp 커널은 FMA 를 켠 채 컴파일된다**(`warp/native/warp.cu` NVRTC `--fmad=true`). 식을 그대로 옮기면 끝비트가 다르다. FMA 자리는 PTX(NVVM 이 묶은 `fma.rn`)와
  SASS(ptxas 가 `mul.f32`+`add.f32` 를 묶은 FFMA)에서 읽어 `warp_f32.h`·`states.h` 에 명시적 `fma_` 로 박았다. 규칙 하나: 두 곱의 합 `a*b + c*d` 는 **앞 곱을 묶는다** →
  `fma(a,b, c*d)`, 세 곱은 `fma(e,f, fma(a,b, c*d))`. omni CUDA 는 `-fmad=false -ftz=false`(warp·numpy 는 비정규수를 유지).
- **GPU 종류 의존 (09-30 확인)**: warp 1.12 의 NVRTC(CUDA 12.9)는 sm_120(이 PC)에서 **NVVM 20**, sm_89·86·75(측정·평가 GPU)에서 **NVVM 7** 을 쓴다.
  같은 PTX 를 ptxas 로 굽으면 sm_89 와 sm_120 의 FFMA 자리는 같았다(정규화 뒤 30 커널 다름 0) → 차이는 NVVM 단계뿐.
  그래서 sm_89 의 NVVM 7 PTX 를 sm_120 용으로 바꿔 warp 캐시에 넣고(`~/engine-build/omni/warpcache_nvvm7`, 불러온 뒤 md5 불변 확인) 같은 60 장면 정답을 다시 떴다
  (`states_nvvm7`) → 우리 층 1 과 **모든 상태 다름 0**. 결론: FMA 표는 **아키텍처 무관**(sm_89·86·75·120). 커널 명령 수 차이(inside_inv_world 의 `fma(x,1,c)` ↔ `add` 등)는 값이 같은 표기 차이였다.
- **torch 쪽**: Linux 평가기에서 `T.*` 는 `torch.compile`(inductor CPU)이다. inductor 는 `-ffp-contract=off -fno-unsafe-math-optimizations` 로 짓는다
  (`torch/_inductor/cpp_builder.py:539`, `config.py:937`) → FMA·재배열 없음. 생성 C++(`TORCH_LOGS=output_code`)의 순서를 그대로: 4 원소 합은 벡터 줄이기
  `(a0+a2)+(a1+a3)`, 3 원소 합은 순차, 정규화는 나눗셈, `std::acos(float)` = glibc `acosf`(`core/common/glibc_trig.h`). eager `th.norm(3-벡터)` 는 반대로 FMA 가 있다
  (`sqrt(fma(z,z, fma(y,y, x*x)))`, ATen 을 FMA 로 지은 것).
- **CPU 종류 의존**: 파이썬 `@`(aten.mm 4x4)는 "순서대로 곱·합"이 맞았고(FMA 사슬 후보는 11 % 다름), 제어기의 numpy 4x4 는 OpenBLAS SkylakeX FMA 사슬이었다.
  둘 다 CPU 가 고른 BLAS 경로라 **다른 CPU(AVX2 만, 인텔)에서는 바뀔 수 있다** — 이 PC(Zen5 AVX512)에서 확인한 값이다.
- **원자 덧셈**: 온도의 `incoming_heat_rate` 는 공식이 `wp.atomic_add` 라 열원 둘 이상이 한 물체에 동시에 닿으면 GPU 에서 더하는 순서가 비결정이다(공식끼리도 끝비트가 갈릴 수 있음).
  우리는 열원 번호 순으로 더한다(결정적).
- **파이썬 비교**: Cooked·Frozen 은 float32 값을 `.item()` 으로 꺼내 파이썬 수(double)와 비교, AttachedTo 문턱은 float32 텐서 비교(스칼라가 float32 로) — 둘 다 공식 함수로 확인.

- **노드 활성 질의 시점 (시험으로 확인)**: 새 겹침으로 상호작용을 만들 때의 `isSpeculativeNodeActive` 는 **simulate 직전의 추측 섬 상태**(API 깨움·새 행위자 반영 뒤,

- **행위자 상호작용 목록**은 조인트(ConstraintInteraction)·관절체 관절(ArticulationJointSim)과 섞여 있고 지우면 마지막을 그 자리로 옮기므로, 섞인 순서가 요소 상호작용 순서를
  정한다. 그래서 이 층이 목록 전체를 들고, joints·articulation 은 `addExternalInteraction / removeExternalInteraction` 으로 자리표를 넣고 뺀다(Interaction::registerInActors 순서).
  solver 가 조인트 끊김 때 고르는 "상호작용 수가 적은 쪽"도 이 목록 길이다.
- **캐시 지움(solver → contact, 12.3)**: 조인트 끊김이면 solver 가 `setActorsInteractionsDirty(행위자, eFILTER_STATE, -1, eRB_ELEMENT)` 를 부르고, 다음 스텝
  `updateDirtyInteractions` 가 재거르기 → `updateState` → `resetManagerCachedState`(관리자 재등록: 좁은 단계 목록에서 빼고 새 목록 끝에 다시)를 한다.
  마찰 패치 0 은 `ContactManager::cachedStateEpoch` 가 바뀌는 것으로 solver 가 안다.

### 19.5 스펙 결정 (이유)

- **기계 번역**: PCM·GJK·EPA·ABP·AABB 관리자는 SIMD 식과 해시·정렬 순서가 결과를 정하므로, 손으로 옮기지 않고 원본 문장을 그대로 번역했다(오타 위험 제거).
  쌍 관리층은 Sc 객체 모형(포인터 사슬)이라 번역 대신 번호 기반으로 손으로 짰다.
- **작업(task)은 한 스레드로 차례대로**: ABP·AABB 관리자의 작업은 각자 버퍼에 쓰고 번호 순서로 합치므로 결과 순서가 스레드 수와 무관하다(시험: PhysX 스레드 0~16 모두 같음).
- **쌍 관리층의 시험 방식**: 섬 관리는 solver 몫이라, PhysX 가 섬 관리자에 한 호출을 링커 `--wrap` 으로 떠서 우리 갈고리 호출과 비교한다(solver `test_islands` 와 같은 방식).
  섬 넣기 작업이 여럿이면 `addPreallocatedContactManager` 를 부르는 순서가 스레드마다 달라서 이것만 간선 번호로 맞춰 비교한다(내용은 같음).

### 19.6 남은 것 / 막힌 곳

- **층 2 좁은 단계 커널 오류(조사 중)**: `test_contact_gpu` 에서 모양 쌍 커널이 불법 메모리 접근으로 멈춘다. 쌍 하나씩 띄우는 진단(`CX_FIND=1`)으로 **상자-캡슐**(PhysX
  `pcmContactCapsuleBox`) 에서 처음 난다는 것까지 좁혔다. 스택 64/256 KB 모두 같다. 이 PC 의 CUDA 12.8 에 compute-sanitizer·cuda-gdb 가 없어 종류별로 더 좁히는 중.
- 접촉 수정 쌍(PxPairFlag::eMODIFY_CONTACTS, omni 표면 속도)의 수정 가능 스트림(PxModifiableContact)은 아직 — `--np` 시험에서는 그 쌍을 만들지 않는다.
- 층 2 로 옮길 것: 경계 상자(이미 호스트·장치 공용), ABP·AABB 관리자·쌍 관리층(지금 호스트 전용: 동적 배열·해시). 판마다 고정 용량 배열로 다시 짜야 한다.
- 조인트 끊김(풀이 중) 때의 자리표 처리(만들기·없애기는 시험함), 삼각 메시 PCM(공식 장면에 없음), 접촉 보고(omni `RigidContactAPI` 가 쓰는 접촉 쌍·힘).

  리드에게 두 방안(공용 prelude 를 번역본으로 / 변환 연산자) 을 보냈다.
