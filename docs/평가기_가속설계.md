   "병목 제로" 설계(7절)는 뜨거운 경로를 손으로 짠 C++/CUDA(물리 콜백·접촉 복사·관측 계산·변화 감지 커널)로 한꺼번에 치우는 것이고,
   라이브러리는 공식과 같아야 하는 곳(PhysX·RTX·x264·warp 상태 커널, 공식 OmniGibson·Isaac 안의 torch)만 남긴다 — 평가기 내부를 바꾸므로 **개발용**.
   우리 코드에는 torch 를 쓰지 않고, π0.5 도 네이티브 C++/CUDA 엔진으로 간다(사용자 결정, 7절 "torch 경계").
6. **시제품(하나)**: 가장 큰 '없앨 수 있는' 병목인 통신을, 평가기에 이미 있는 공식 인자 `--replay-action-chunk-size 16` 에 응답하는
   π0.5 서버(`src\fasteval\pi05_chunk_server.py`)로 줄이는 시제품을 만들었다. 등가 검증·속도 측정은 검은 화면 조사에 GPU 를 쓰느라 아직 못 돌렸다(명령 준비됨). 9절.

## 1. 조건과 규칙

사용자 조건: 물리 120 Hz / 렌더 30 Hz / 행동 30 Hz, 정책이 받는 관측(RGB·depth·proprio), 종료·BDDL 목표 판정, q_score·지표 JSON 이
공식 평가기와 같아야 한다. 같다는 것을 증명 못 하는 가속은 "불가". 언어: GPU 로 할 수 있는 일은 C++/CUDA, 나머지 새 코드는 Rust,
파이썬은 OmniGibson·평가기 프로세스에 거는 얇은 접착부만. 목표는 "병목 제로".

- "Final evaluation must be reproducible from the files you submit." (submission:33)
- "Do not modify the output JSON files or rollout videos in any way." (submission:72)
- "After running the evaluation script at `OmniGibson/omnigibson/eval/eval.py`, each rollout produces:" (submission:23)

정리
- 공식 인자(`--num-envs`, `--replay-action-chunk-size`)와 우리 서버 쪽 변경은 제출 README 의 "full evaluator command" 에 적으면 되는 범위다.
- **평가기 내부를 바꾼 가속판으로 만든 JSON 을 제출에 써도 되는지는 원문에 없다.** "evaluation script at eval.py" 로 만든다고만 적혀 있다 → Discord 에 물을 것(11절). 그 전까지 가속판은 **우리 개발 반복용**이다.
- "같다"의 범위: 같은 PC·같은 드라이버에서 공식 평가기와 같음. 주최 측 GPU(원문 "RTX 3090, A5000, and TitanRTX", submission:84)와 이 PC(RTX 5070 Ti)는 RTX 렌더·DLSS 가 달라 픽셀이 원래 다를 수 있다 (추정 — RTX 실시간 렌더 + DLSS, 5.2).

#### 5.2.1 원인 가르기 — 변수를 하나씩 떼어 냈다

Isaac Sim 단독 재현 `tools\isaac_black_repro.py`(OmniGibson 없음): 같은 conda `behavior`, 같은 PC·드라이버, 카메라 3 대 224², 카메라마다 render product,

결론(측정 기준)
- **Windows 의 Isaac Sim 5.1 은 GPU 의 다른 사용자가 VRAM 을 일정량 이상(이 16 GB 카드에서 4~6 GiB 사이) 잡고 있고 아직 넘치지 않을 때, RTX 의 RGB(LdrColor) 출력을 통째로 비운다.**
  depth 같은 다른 출력은 멀쩡하다. 이것이 평가기에서 본 모양과 같다.
- 평가기에서의 비율과 맞춰 보면: π0.5 서버(XLA 8 GB 선점) 같이 → 100%, 다른 LLM(약 7 GB) 같이 → 17~100%, 환경 2 개 → 100%.
- 기전은 추정이다: WDDM 은 프로세스마다 VRAM 예산을 주고(다른 프로세스가 쓰는 만큼 줄어듦) RTX 의 메모리 예산 관리자(`gpu::unstable::IMemoryBudgetManagerFactory`,
  Kit 로그의 gpu.foundation 인터페이스)가 그 예산을 보고 일부 출력을 건너뛰는 것으로 보인다. 리눅스는 예산 방식이 달라 채점 장비·다른 팀에서는 대부분 정상인 것과 맞는다(추정).
- 원인 후보 정리: 렌더 설정 — 아님. OmniGibson 코드 — 방아쇠는 아님(단독 재현). VRAM 압박 — **맞음**. Windows(WDDM 예산) — 유력(리눅스 비교 필요, `tools\linux_black_frame_repro.sh`).
  드라이버 591.86(5.1 시험값 580.88) — 배제 못함(바꾸지 않음, 사용자 결정).

결과
- **지금까지 이 PC 의 radio π0.5 점수(0.0)는 정책을 평가한 값이 아니다.** 원인이 Windows 의 다른 프로세스 VRAM 예산 쪽이면 리눅스 채점 장비와는 무관하다(추정).
- 이 PC 에서 로컬 평가가 유효하려면 같은 GPU 의 **다른 프로세스 VRAM 을 문턱 아래로** 둬야 한다: π0.5 서버(XLA 8 GB 선점)를 같은 16 GB GPU 에 올리는 구성은 불가,
  평가 중 LLM 등 다른 GPU 프로그램 금지, 화면 프로그램(브라우저·Discord 등 약 1.5~2 GB)도 줄일수록 좋다. 평가기에서도 다른 프로세스 0.56·2.9·5.4 GB(`gpu_hog` 0·2·4 GiB)로는
  전부 검은 상태가 안 났다(5.2.2 표 `eh_*`) — 단독 재현의 문턱(4~6 GiB)과 맞는다. 다만 그때도 아래 (B) 가 따로 난다.
- 검은 프레임은 물리를 바꾸지 않는다(5.1 — 행동이 같으면 물리 비트 동일). 폐루프에선 정책 행동을 바꾼다.

재발 방지와 대응
- 평가 런처: `run_eval_radio.ps1 -BlackGuard warn|abort` — 정책에 들어갈 RGB 가 전부 0 이면 그 스텝에서 경고 또는 중단. `-BlackDiag` 는 호스트/GPU 경로 비교(진단).

  원인을 없애는 것만 목표로 한다(사용자 결정). 원인 후보: 렌더 설정, VRAM 압박, 드라이버(591.86, 5.1 시험값 580.88), **Windows(Vulkan 강제 경로)**.

### 6.1 쓰는 법

```
# 기준 기록: 공식 평가기 + 고정 행동열 (π0.5 로 한 번 돌린 결과의 actions.npz 를 재생)
powershell -ExecutionPolicy Bypass -File C:\behavior-2026\tools\run_replay_eval.ps1 -Actions <기준>\actions.npz -Trace -Tag ref
# 가속판(또는 다른 설정)으로 같은 행동열 -> 비교
python C:\behavior-2026\tools\trace_compare.py <ref 결과폴더> <가속판 결과폴더> --check --strict
python C:\behavior-2026\tools\trace_compare.py <A> <B> --env-a 0 --env-b 1     # 묶은 실행의 다른 환경끼리
python C:\behavior-2026\tools\trace_compare.py <A> <B> --negative              # 도구 자체 음성 대조
```

- 항목마다 `비트 동일 / 허용오차 안 / 다름` + 최대 |차이| + 처음 비트가 다른 스텝 + 처음 임계를 넘은 스텝. 결과 JSON 은 항목마다 따로.
- 두 채널: `trace.npz`(평가기 안에서 읽기만 하는 기록) 와 `server_log.npz`(서버가 받은 관측). 후자는 평가기에 아무것도 안 붙인 실행에도 있다
  → `nf_plain` 과 `nf_a` 를 비교해 **기록 자체가 결과를 안 바꾼다**는 것도 확인했다(5.2).
- `trace_images.npz`: 몇 스텝(0,1,2,10,50,100,…,500)의 카메라 원본 → 픽셀 차이 비율·평균·최대와 검은 화면 여부.

### 6.2 한계
- 폐루프(정책이 픽셀을 보고 행동)는 픽셀이 실행마다 달라 궤적이 갈라질 수 있다 → 폐루프 비교는 여러 판의 점수 분포로만 할 수 있다(비쌈).
  픽셀을 바꾸지 않는 가속은 재생 비교(비트)만으로 충분하다. 픽셀을 바꿀 수 있는 가속(타일 렌더 등)은 이 단계에서 "불가" 로 둔다.
- 서버 쪽 변경(행동 묶음 등)은 시뮬레이터 없이 같은 관측열을 두 경로에 넣어 행동을 비트 비교한다(`src\fasteval\verify_chunk_equivalence.py`).

### 6.3 부품 교체용 그림자 실행 (설계)
C++/Rust 로 옮기는 부품(7절: 물리 콜백, 관측 계산 등)은 `src\fasteval\` 의 얇은 파이썬 접착부가 공식 함수를 감싸
① 공식 함수 실행 → ② 같은 입력으로 새 함수 실행 → ③ 출력 비트 비교(다르면 스텝·항목 기록) → ④ 공식 출력을 돌려준다.
진행은 공식 값으로 하므로 차이가 누적되지 않고, 첫 불일치가 곧 그 부품의 버그다. 통과한 뒤에만 새 함수 출력으로 진행하는 모드로 바꾸고
6.1 의 재생 비교(비트 동일)를 한 번 더 한다.

## 7. 병목마다 — "병목 제로" 설계, 언어, 결과 위험, 검증

원칙(사용자 지시): 뜨거운 경로(매 스텝 도는 곳)는 라이브러리 호출(torch 연산, numpy, PyAV 등) 대신 **손으로 짠 C++/CUDA**. 라이브러리를 남기는 곳은
손으로 짜는 것이 비합리적인 경우(공식과 같아야 하는 닫힌 내부)만. GPU 가 아닌 조율 코드는 Rust. 파이썬은 평가기 프로세스에 거는 얇은 접착부만.

**torch 경계**(사용자 방침 "파이토치 갖다 버리고 최대한 최적화할수있을만큼 최적화")
- **우리가 짜는 코드에는 torch 가 없다.** 서브스텝 콜백(컨트롤러·보조 잡기), 접촉 복사, proprio, 관측 전처리(카메라 상대 pose), 통신, π0.5 추론 —
  전부 손으로 짠 C++/CUDA(+조율 Rust). π0.5 는 `src\pi05_native\` 의 네이티브 엔진(다른 에이전트 담당, 로컬은 평가기 안 pybind11, 제출은 리눅스 네이티브 웹소켓 서버).
- **공식 OmniGibson·Isaac Sim 안의 torch 는 그대로 둔다.** 공식 평가기와 결과가 같아야 하므로 공식 코드 경로(물체 상태·BDDL·지표·컨트롤러 원본 등)는 손대지 않는다.
- 경계에서의 약속: 우리 C++ 가 공식 torch 함수를 **대신하는** 곳(위 뜨거운 경로)은 6.3 의 그림자 실행으로 공식 torch 출력과 **비트 동일**을 먼저 보이고,
  그 뒤 재생 비교(6.1, `--strict`)를 통과해야 쓴다. 비트가 안 맞으면 그 항목은 공식 torch 그대로 둔다(불가).
- π0.5 엔진은 우리 제출물(정책)이라 공식 평가기와 같을 필요는 없다(규칙은 "reproducible from the files you submit"). 다만 공식 JAX 체크포인트와
  행동이 얼마나 다른지는 같은 관측열로 재서 적는다(반올림이 달라 비트 동일은 기대하지 않음 — 폐루프 점수로 판단).

- 24 GB(채점용): π0.5 8 GB + 시뮬 환경 1~2 개(추정). 환경을 묶으면(`--num-envs`) 렌더·Kit 고정비가 나뉘어 처리량이 오를 수 있으나(측정 대기) **N=1 과 결과가 비트 단위로 다르다**(5.4) — 공식 재평가가 어떤 N 으로 도는지 모르면 로컬 N 을 정할 수 없다(11절 질문).
- 추론 760 ms 는 5070 Ti 에서 RTX 렌더와 GPU 를 나눈 값이다. π0.5 단독 추론 시간은 9절 검증 스크립트에서 잰다.

## 9. 시제품 — 행동 묶음 재생 서버 (`src\fasteval\pi05_chunk_server.py`)

고른 이유: 4절에서 '없앨 수 있는' 것 중 가장 큰 것이 통신(π0.5 루프 28 ms, 재생 루프 30 ms = 31%)이고, 평가기에 이미 공식 인자가 있어
평가기를 한 줄도 안 바꾸고 제출에도 쓸 수 있다. C++/CUDA 로 새로 짤 뚜렷한 파이썬 병목 하나는 없었다(4절: 각 2~5 ms).
언어: 파이썬 — openpi 정책이 JAX 파이썬 객체라서 붙는 접착부(버퍼 인덱싱 몇 줄)뿐이다. 계산은 JAX/XLA.

동작
- 요청에 `__action_chunk_size__ = K` 가 있으면 평소처럼 `act()` 로 첫 행동을 만들고(16 스텝 경계라 추론이 돈다), 같은 버퍼에서 이어지는 K−1 개를
  `action_chunk` 로 준다. 버퍼 위치·스텝 카운터를 K−1 만큼 넘겨 다음 요청이 공식 경로와 같은 스텝(16 의 배수)에서 추론하게 한다.
- K 가 재계획 경계를 넘으면 거부한다(원문 "choose `K` so replay never crosses the policy's replanning boundary").
- 묶음 요청이 없으면 openpi 공식 서버와 똑같이 동작한다.

결과가 같은 이유 (구조)
- 공식 경로(`eval_b1k_wrapper.py` `act_receding_horizon`)는 16 스텝마다만 추론하고, 사이 스텝의 관측은 크기 조정만 하고 버린다 → 안 보내도 같다.
- JAX 난수(`policy.py:65` `jax.random.key(0)`, `:75` 추론마다 split)는 추론 횟수가 같으므로 같은 순서로 쪼개진다.
- 평가기 클라이언트는 묶음 첫 행동이 `action` 과 비트 같은지 확인하고(`network_utils.py` `th.equal`), 나머지를 그대로 쓴다.

검증 (`src\fasteval\verify_chunk_equivalence.py`, JSBSim 틀: 같은 입력 → 두 경로 → 출력 전부 비트 비교)
아직 못 돌렸다 — 검은 화면 조사가 우선이 되어 GPU 를 거기에 썼다. 돌리는 법: `wsl -d Ubuntu-22.04 -u juyoung -- bash /mnt/c/behavior-2026/tools/run_verify_chunk.sh`
(같은 관측열 64 스텝, 배치 1·2, 음성 대조 2 가지 포함, 통과하면 exit 0). 서버 단 단위로는 구조상 같다(위).

속도
아직 못 쟀다. 예상(추정): π0.5 루프에서 통신 28.0 ms × 15/16 ≈ 26 ms/스텝 감소 → 151.6 → 약 125 ms(1.21 배). 이 PC 에서는 검은 화면 때문에 π0.5 를 시뮬레이터와 같은 GPU 에 올린 실행 자체가 무효라, 서버를 다른 GPU·PC 에 둔 뒤에 잰다.

## 13. 한 명령 실험 실행기 (`tools\exp_run.ps1`)

사용자 지시 "최대한 빠르게 실험해볼 수 있게 세팅" + "오리지널 평가기도 두자, 우리가 포팅한 평가기랑".

```
powershell -ExecutionPolicy Bypass -File C:\behavior-2026\tools\exp_run.ps1 run -Matrix C:\behavior-2026\tools\exp\smoke_radio.json [-Backend original|ported] [-Reuse] [-DryRun]
powershell -ExecutionPolicy Bypass -File C:\behavior-2026\tools\exp_run.ps1 table -Dir <실험 폴더>
powershell -ExecutionPolicy Bypass -File C:\behavior-2026\tools\exp_run.ps1 compare -A <실험·판 폴더> -B <실험·판 폴더>
```

- 입력: 행렬 JSON(과제 × 인스턴스 × 설정). 설정 = 정책 종류(`local` 0 행동 · `replay` 행동열 · `websocket` 외부 서버 · `native` 평가기 프로세스 안),
  로봇 설정, 래퍼, 제한시간(0 = 공식 1.5 배), 묶음 재생 K, 추가 평가기 인자. 형식은 스크립트 머리 주석.
- 결과: `outputs\exp_<이름>_<시각>\<backend>\<설정>\<과제>\i<인덱스>\` 에 공식과 같은 `json\*.json`·`trace.npz`·`actions.npz`(+재생이면 `server_log.npz`),
  판마다 상태 `status.jsonl`, 표 `summary.md`·`results.csv`(설정 × 과제: 판·유효·무효·오류·평균 q_score·성공·스텝·판당 벽시계).
- **무효 판정**: 판마다 `--black-guard=abort` — 정책에 들어갈 RGB 가 전부 0 인 첫 스텝에서 그 판을 끊고 "무효(스텝, 카메라)" 로 적는다. 고쳐 넣지 않는다(5.2).
- **GPU 잠금**: 원본 평가기 판(프로세스)마다 공용 잠금 `tools\gpu_lock.ps1`(owner=exp_run, 최대 30 분)을 잡고, 잡은 뒤 nvidia-smi 로 다른 시뮬레이터가 없고
  사용량이 문턱(기본 3.5 GB — 검은 화면 (A) 문턱 4~6 GiB 아래) 밑인지 본다. 안 맞으면 잠금을 풀고 60 초 뒤 다시.
- **두 평가기**
  - `original`: 공식 v3.9.3 그대로(BEHAVIOR-1K 무수정) + 계측·검출만(`eval_instrumented.py`). 가속 부품을 섞지 않는다. 제출·리더보드 수치는 이것으로만.
  - `ported`: 우리 엔진(`src\engine`)·네이티브 π0.5·가속 부품. 지금은 자리만 — 진입 모듈이 생기면 `BEHAVIOR_PORTED_EVAL` 로 붙인다. 약속: 공식 eval.py 와 같은 인자·같은 결과 형식.
  - `compare`: 두 결과에서 같은 설정\과제\인덱스끼리 짝지어 `trace_compare.py --check --strict --pixels-report-only` — 스텝별 행동·proprio·관절·로봇/과제 물체 pose·
    목표 조건·지표·결과 JSON(q_score 포함)은 비트 동일만 통과, 영상은 RTX 잡음(5.1)이라 표에만. 노이즈 바닥 쌍(`nf_a` vs `nf_b`)으로 시험: 통과(비트 동일 19, 픽셀 다름 9),
    음성 대조(`nf_neg`)는 실패로 잡힘(다름 10, JSON 3).
- **정책 연결**: `native` = `--native-policy=모듈:함수` 로 공식 `load_policy` 자리에 평가기 프로세스 안 정책을 넣는다(평가기 코드는 그대로 — 정책은 우리 제출물).
  네이티브 π0.5(`src\pi05_native\`, pybind11)가 나오면 여기에 붙는다. 다른 프로세스 VRAM 이 0 이 되어 검은 화면 (A) 도 없어진다. 그 전에는 `local`·`replay` 로 실행기 자체를 시험한다.

장면 로딩(인스턴스마다 약 2 분)을 줄이는 방법과 검은 화면
| 방법 | 결과가 공식과 같나 | 검은 화면 | 결정 |
|---|---|---|---|
| 인스턴스마다 새 프로세스(공식 기본, `--num-envs 1`) | 공식 그대로 | (A) 없음(문턱 아래), (B) 있음 | **기본** |
| `-Reuse`: 한 프로세스에서 공식 `evaluator.run()` 을 인스턴스마다 다시 부름(공식 `--num-rollouts` 가 쓰는 경로, `--instances-seq`) | 새 프로세스 판과 비트 동일인지 **아직 확인 안 함** | 같음 | 확인 뒤에만 켬(개발용) |
| 공식 `--num-envs N`(여러 판 한 배치) | **N=1 과 물리 비트가 다름**(5.4) | 이 PC 에서 100%(원인 미확인 — 같은 프로세스 CUDA 메모리는 방아쇠가 아니었다, 5.2.1) | 안 씀 |

- 공식 eval.py 는 인스턴스 수 = `--num-envs` 를 강제한다. 그래서 재사용은 공식 main 에 첫 인스턴스만 넘기고, 첫 `run()` 호출을 가로채 인스턴스마다 공식 `run()` 을 부른다.
  한 프로세스에 넣는 인스턴스 수는 잠금 30 분 이내가 되게 `reuse_batch`(기본 5). 검은 프레임으로 끊기면 남은 인스턴스는 새 프로세스로 이어 간다.
- 통신: 재생 서버는 기본 quickack(4.3). `websocket` 은 외부 서버가 켜야 한다.
