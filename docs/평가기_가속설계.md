측정 결과 원본은 `outputs/eval_*_<태그>/` (timing.json · trace.npz · server_log.npz), 명령은 12절. 시간·VRAM 수치는 이 PC 에서 다시 잴 것.

## 0. 한눈에

1. **검은 프레임**: 이 PC 의 공식 평가기는 검은 프레임 0 (0 행동 5 판 0/151, 재생 2 판 0/501 — [Linux_설치.md](Linux_설치.md) 4절).
   검출(`tools/eval_instrumented.py --black-guard`, `tools/black_frame_check.py`)은 제출 판 증거로 계속 켠다. 검은 프레임을 다른 프레임으로 바꿔 넣는 방식은 쓰지 않는다. 5.2절.
2. **물리·판정은 같은 행동열이면 비트 단위로 재현된다.** 같은 행동을 다시 넣은 실행 5 번(π0.5 폐루프 1 + 재생 4)에서 관절·로봇 pose·
   과제 물체 pose·목표 조건·지표·결과 JSON 이 전부 비트 동일. **픽셀만 매번 다르다**(RTX 잡음).
   → 판정 기준: 물리·판정·지표·JSON = 비트 동일만 통과, 픽셀 = 평균 |차| 3 이하. 음성 대조(0.01 rad 한 번)는 정확히 그 스텝에서 잡혔다. `--num-envs 2` 는
   스텝 0 부터 물리가 N=1 과 다르다. 5절.
3. **radio, 헤드리스, 224 RGB, 환경 1 개** 기준 스텝당 시간 분해(정책 추론·통신·RTX 렌더 제출·물체 상태 캐시·물리 콜백·PhysX 등)는 이 PC 에서 다시 잴 것. 4절.
4. **못 없애는 것(불가)**: RTX 렌더(GPU 대기·카메라 읽기 포함)·PhysX — 닫힌 내부라 다시 짜서 같은 결과를 낼 수 없다. 정책 추론은 모델 계산.
   나머지를 **전부 0 으로 만들 때의 상한**은 8절.
5. **C++/CUDA 로 새로 짤 뚜렷한 파이썬 병목 하나는 없다.** 파이썬 쪽은 여러 항목에 흩어져 있고 물체 상태는 이미 warp CUDA 그래프다.
   "병목 제로" 설계(7절)는 뜨거운 경로를 손으로 짠 C++/CUDA(물리 콜백·접촉 복사·관측 계산·변화 감지 커널)로 한꺼번에 치우는 것이고,
   라이브러리는 공식과 같아야 하는 곳(PhysX·RTX·x264·warp 상태 커널, 공식 OmniGibson·Isaac 안의 torch)만 남긴다 — 평가기 내부를 바꾸므로 **개발용**.
   우리 코드에는 torch 를 쓰지 않고, π0.5 도 네이티브 C++/CUDA 엔진으로 간다(사용자 결정, 7절 "torch 경계").
6. **시제품(하나)**: '없앨 수 있는' 병목인 통신을, 평가기에 이미 있는 공식 인자 `--replay-action-chunk-size 16` 에 응답하는
   π0.5 서버(`src/fasteval/pi05_chunk_server.py`)로 줄이는 시제품을 만들었다. 등가 검증·속도 측정은 아직 못 돌렸다(명령 준비됨). 9절.

## 1. 조건과 규칙

사용자 조건: 물리 120 Hz / 렌더 30 Hz / 행동 30 Hz, 정책이 받는 관측(RGB·depth·proprio), 종료·BDDL 목표 판정, q_score·지표 JSON 이
공식 평가기와 같아야 한다. 같다는 것을 증명 못 하는 가속은 "불가". 언어: GPU 로 할 수 있는 일은 C++/CUDA, 나머지 새 코드는 Rust,
파이썬은 OmniGibson·평가기 프로세스에 거는 얇은 접착부만. 목표는 "병목 제로".

규칙 원문 ([raw/site_challenge_submission.md](raw/site_challenge_submission.md), [raw/site_challenge_evaluation.md](raw/site_challenge_evaluation.md)):
- "Final evaluation must be reproducible from the files you submit." (submission:33)
- "Do not modify the output JSON files or rollout videos in any way." (submission:72)
- "After running the evaluation script at `OmniGibson/omnigibson/eval/eval.py`, each rollout produces:" (submission:23)
- README 에 넣을 것: "Instructions for evaluating your policy, including the full evaluator command, wrapper path, robot config path, Docker image details or IP address information." (submission:102)
- "Run challenge evaluation from the `v3.9.3` tag of `BEHAVIOR-1K`, not the older `v3.9.0` tag. The challenge evaluator and dataset interfaces in `v3.9.3` include the latest compatibility fixes that the organizers will use for evaluation." (evaluation:28)
- "You should evaluate your policy 1 time on each instance, using the default `1.5x` mean-human-length timeouts provided by our evaluation script." (evaluation:182)
- "Because the simulator can be nondeterministic, different rollouts of the same policy may produce different results for a given instance. This is expected." (evaluation 표 "Simulation nondeterminism")
- 행동 묶음 재생: "Only enable replay when the server returns an action sequence intended to be executed open-loop from the current observation, such as one receding-horizon policy chunk, and choose `K` so replay never crosses the policy's replanning boundary." (evaluation:66 부근)
- `--num-envs`: "Number of logical environments processed together as one evaluation batch." (evaluation:51)

정리
- 공식 인자(`--num-envs`, `--replay-action-chunk-size`)와 우리 서버 쪽 변경은 제출 README 의 "full evaluator command" 에 적으면 되는 범위다.
- **평가기 내부를 바꾼 가속판으로 만든 JSON 을 제출에 써도 되는지는 원문에 없다.** "evaluation script at eval.py" 로 만든다고만 적혀 있다 → Discord 에 물을 것(11절). 그 전까지 가속판은 **우리 개발 반복용**이다.
- "같다"의 범위: 같은 PC·같은 드라이버에서 공식 평가기와 같음. 주최 측 GPU(원문 "RTX 3090, A5000, and TitanRTX", submission:84)와 이 PC(RTX 4090)는 RTX 렌더·DLSS 가 달라 픽셀이 원래 다를 수 있다 (추정 — RTX 실시간 렌더 + DLSS).

## 3. 측정 방법

도구 (평가기 코드는 한 줄도 안 바꿈)
- `tools/eval_instrumented.py` — 공식 `omnigibson.eval.eval` 을 그대로 부르면서 함수들을 '겉싸개'로 감싸 perf_counter 로 들어간/나온 시각만 적는다.
  구간은 호출 경로(`step/apply_actions/env.step/sim.step/app.update/physx`)별 '자기 시간'. PhysX 계산 = 앞 콜백 끝 ~ 뒤 콜백 시작(서브스텝마다).
  겉싸개 비용 실측 1.2 μs/호출(`t2` 에서 스텝당 약 400 번 → 0.5 ms). `--summary` 가 경로를 아래 병목 항목으로 묶는다.
- 예전 `tools/profile_eval.py`(cProfile)는 지웠다: Kit 이 `carb.profiler` 를 불러오며 파이썬 프로파일 훅을 가져가서, 그 뒤로 아무것도 안 잡혔다.
- `tools/replay_policy_server.py` — 기록한 행동열을 그대로 돌려주는 서버. 정책 쪽 잡음이 빠지고 시뮬레이터만 남는다. 받은 관측을 해시로 남겨,
  평가기에 아무것도 안 붙인 실행도 비교할 수 있다.
- `tools/transport_bench.py` — 시뮬레이터 없이 정책 왕복만(평가기 클라이언트와 같은 연결 인자).

## 4. 병목 표

`python tools/eval_instrumented.py --summary <결과폴더>/timing.json` 출력(앞 20 스텝 뺌). "GPU 대기" 는 warp 가 `wp.synchronize_stream` 에서
렌더가 끝나기를 기다린 시간(`--deep` 일 때만 따로 보임, 아니면 '물체 상태 캐시'에 들어감). 재생 실행의 '정책 추론'은 재생 서버가 받은 관측을 해시로 남기는 시간이다.

### 4.1 radio · 224 RGB · 환경 1

이 PC 에서 다시 잴 것. 항목: 정책 추론(서버 계산) · 통신(웹소켓 왕복, 서버 계산 뺌) · 렌더 제출·Kit 갱신(`app.update` 자기 시간) · GPU 대기 · 물체 상태 캐시(warp, CPU 쪽) ·
서브스텝 앞 콜백(컨트롤러 + 보조 잡기) · 영상 저장(크기조정 + x264) · PhysX(4 서브스텝) · 관측 전처리(카메라 상대 pose) · proprio · 서브스텝 뒤 콜백(접촉 읽기) ·
update_visuals(radio 물체 244 개마다) · 카메라 읽기 GPU→CPU · 그 밖 · BDDL 목표 판정(종료 + 보상).
- 정책 추론은 receding horizon 16 이라 16 스텝마다만 돈다(481 스텝 중 35 스텝).
- `--deep` 이면 앞 콜백 안(보조 잡기 `robot.post_step`, 그리퍼·관절 컨트롤러, 홀로노믹 베이스, flush), 뒤 콜백 안(`RigidContactAPI.read_from_physx`), 물체 상태 캐시 안(PhysX 자세·관절 읽기, 상태 종류별 pre/post)이 따로 나온다.

### 4.2 공식 RGB-D 래퍼 (머리 720², 손목 480², depth 포함) — 재생 `t3`

이 PC 에서 다시 잴 것. 요청 크기는 7.83 MB(224 RGB 는 0.60 MB).

### 4.3 통신만 따로 (`tools/transport_bench.py`, 시뮬레이터 없이)

- 클라이언트 소켓의 TCP_NODELAY 는 이미 켜져 있다(측정 도구가 확인).
- **고침(서버 쪽)**: 리눅스 서버 소켓에 TCP_NODELAY 를 켜고, 받을 때마다 TCP_QUICKACK 을 다시 켠다(리눅스는 이 표시를 한 번 쓰고 되돌린다, `man 7 tcp`) — 지연 ACK(리눅스 기본 40 ms) 회피.
  `tools/replay_policy_server.py --quickack`(websockets 15 의 `create_connection` 으로 연결 클래스만 바꿈 — 보내는 바이트는 그대로).
  네이티브 π0.5 웹소켓 서버도 같은 두 옵션을 켠다(전달함). 평가기로 돌려 서버 로그·JSON 이 비트 동일인지는 재생 비교(6.1)로 확인한다.
- RGB-D 는 요청이 224 RGB 의 13 배라 묶음 재생(요청 1/16)이 더 중요하다.
- 왕복 시간은 이 PC 에서 다시 잴 것.

### 4.4 무거운 과제·환경 여러 개 — 측정 못 함

`bringing_water`(부분 장면 물체 596 개, 가장 많음)와 `--num-envs 2·4` 시간은 아직 안 쟀다. `--num-envs 2` 는 물리가 N=1 과 달라진다(5.4).

## 5. 공식 평가기 노이즈 바닥과 검은 화면

π0.5 로 한 번 돌린 radio 500 스텝(`t1_n1`)의 행동열을 재생 서버로 다시 넣어 공식 평가기를 여러 번 돌리고 `tools/trace_compare.py` 로 비교했다.

### 5.1 물리·판정은 비트 동일, 픽셀만 매번 다르다

`nf_a` vs `nf_b` (501 스텝)

| 항목 | 판정 |
|---|---|
| 행동 23 | 비트 동일 |
| proprio 61 · 카메라 상대 pose 21 (정책 입력의 숫자 부분) | 비트 동일 |
| 로봇 base pose · 관절 28 개 위치·속도 | 비트 동일 |
| 과제 물체 pose (agent, floor, table, radio_receiver) | 비트 동일 |
| 만족한 목표 조건 목록 · 종료 · 시간 초과 | 비트 동일 |
| 지표(스텝별 이동량) · 결과 JSON(q_score, success, steps, agent_distance 3 개) | 비트 동일 |
| RGB 카메라 3 대 해시 | **501 스텝 전부 다름** |

- π0.5 폐루프 실행 `t1` 의 JSON 도 재생 4 번과 비트 동일(`agent_distance.base = 0.006470457566507548`, left 0.32885492951481865, right 0.4425150075585407).
  → **같은 행동이면 PhysX·물체 상태·BDDL 판정·지표는 결정적**이다. 원문의 "simulator can be nondeterministic" 은 픽셀 쪽(→ 폐루프 정책의 행동)에서 온다.
- 계측이 결과를 바꾸지 않는다: 평가기에 아무것도 안 붙인 `nf_plain` 과 계측한 `nf_a`, 시간 계측(`t2`)의 서버 쪽 기록(proprio·카메라 pose)·JSON 이 비트 동일.
- **픽셀 노이즈 바닥**(둘 다 안 검은 프레임, 스텝 0·1·2·10·50·100·150): 픽셀의 66~93% 가 다르고
  평균 |차| 0.5~2.4, 최대 28~71 (0~255, 한 번 97). RTX 실시간 렌더 잡음이다(이 PC 에서 다시 잴 것).
- 판정 기준: 물리·판정·지표·JSON 은 **비트 동일만 통과**(`--strict`). 픽셀은 **둘 다 안 검을 때 평균 |차| 3 이하**면 공식 범위, 검은 프레임은 따로 센다.

### 5.2 검은 프레임

- 이 PC 의 공식 평가기는 검은 프레임(카메라 RGB 전부 0)을 내지 않았다: 0 행동 5 판 0/151, 행동열 재생 2 판 0/501 ([Linux_설치.md](Linux_설치.md) 4절).
- 검출기(`tools/eval_instrumented.py --black-guard`, `tools/black_frame_check.py`)는 제출 판 증거로 계속 켠다. 검출된 판은 무효로 처리하고 고쳐 넣지 않는다(사용자 결정).

(Windows 시절 기록은 [archive/windows/평가기_가속설계.md](archive/windows/평가기_가속설계.md) 참고.)

### 5.3 음성 대조 — 작은 차이를 정말 잡나

`nf_neg`: 100 번째 요청의 행동[7](왼팔 첫 관절 목표)에 +0.01 rad. `nf_a` 와 비교:
- 평가기 쪽 행동·proprio·관절·로봇 pose·카메라 상대 pose·스텝 이동량이 **정확히 스텝 100** 에서 처음 달라짐(서버 쪽 관측은 한 요청 늦은 101).
- 관절 차이 스텝 100 에서 9.8e-3 rad → 200 스텝 3.3e-5, 500 스텝 4.1e-5 (제어가 되돌림). base pose 도 3e-5 m 바뀜(몸 전체 결합).
- 결과 JSON: agent_distance 세 값 모두 다름(q_score·success 는 둘 다 0/False). 라디오는 안 건드려 과제 물체 pose 는 동일. `--check` exit 1.

### 5.4 환경 2 개로 묶으면 같은가 (`--num-envs 2`, `nf_n2` 의 0 번 환경 vs `nf_a`)

- **다르다, 스텝 0 부터.** 관절 5.3e-5 rad(스텝 0) ~ 2.5e-4, 로봇 base 1.1e-4 m, 라디오 pose 3.0e-5 m, 테이블 6.2e-6 m, proprio 속도 성분 최대 0.22.
  결과 JSON 의 agent_distance 세 값도 다름(base 0.006470 → 0.006424). 행동·목표 조건·종료는 같다(짧은 radio 실행에서는 판정까지 안 갈라짐).
- 두 장면(두 번째는 x 로 57.25 m 옮겨 놓임)이 한 PhysX 장면에 같이 있으면 첫 안정화 스텝부터 반올림이 달라진다(추정 — PhysX 의 "enhanced determinism" 을 켜지 않았다, OmniGibson 에 설정 없음).
- → **`--num-envs` 는 결과를 바꾼다.** 로컬 N 을 공식 재평가의 N 과 같게 해야 같은 결과다(11절 질문).

## 6. 일치 검증 도구 — JSBSim GPU 포팅 때와 같은 틀

JSBSim GPU 포팅(`jsbsim-f16-cuda`)의 `fdm_verify --check` 가 쓴 원칙 세 가지를 그대로 가져왔다(`jsbsim_f16_cuda/fdm_verify.py`, `docs/verification.md`).

| JSBSim 에서 | 여기서 |
|---|---|
| 궤적이 얼마나 벌어졌나는 혼돈에 잠겨 "어느 항이 틀렸는지" 못 짚는다 → **한 프레임씩** 같은 입력을 넣고 중간량 전부 비교 | ① 행동을 고정(재생 서버)해 정책 쪽 되먹임을 끊는다. ② 스텝마다 중간량 전부(행동·proprio·관절·로봇/과제 물체 pose·목표 조건·지표·영상 해시)를 비교하고 **처음 달라진 스텝**을 적는다. ③ 부품 하나를 갈아끼울 때는 같은 스텝에서 공식 함수와 새 함수에 같은 입력을 넣어 비교하고, 진행은 공식 결과로 한다(그림자 실행 — 누적 없음, 아래 6.3) |
| 임계 = 실측 최대의 약 3 배, `--check` 면 넘을 때 exit 1 | 공식 자기 자신과의 차이(5절)가 물리·판정에서 0 이므로 **가속판도 비트 동일이어야 통과**(`--strict`). 픽셀만 노이즈 바닥 분포와 비교 |
| `--negative`: 진짜 버그 하나를 일부러 넣어 비교가 잡는지 | `nf_neg`(100 스텝째 행동 0.01 rad) → 100 스텝에서 잡음(5.4절). `trace_compare.py --negative` 는 기록 자체를 조금 바꿔 도구가 잡는지 본다 |

### 6.1 쓰는 법

```
# 기준 기록: 공식 평가기 + 고정 행동열 (π0.5 로 한 번 돌린 결과의 actions.npz 를 재생) — 평가기 인자 전체는 tools/setup/linux_first_check.sh ②
python tools/replay_policy_server.py --actions <기준>/actions.npz --port 8110 --log <ref>/server_log.npz --once --quickack &
python tools/eval_instrumented.py --black-guard=warn --trace -- --task-name turning_on_radio --policy websocket --host 127.0.0.1 --port 8110 <평가기 인자> --output-dir <ref>
# 가속판(또는 다른 설정)으로 같은 행동열 -> 비교
python tools/trace_compare.py <ref 결과폴더> <가속판 결과폴더> --check --strict
python tools/trace_compare.py <A> <B> --env-a 0 --env-b 1     # 묶은 실행의 다른 환경끼리
python tools/trace_compare.py <A> <B> --negative              # 도구 자체 음성 대조
```

- 항목마다 `비트 동일 / 허용오차 안 / 다름` + 최대 |차이| + 처음 비트가 다른 스텝 + 처음 임계를 넘은 스텝. 결과 JSON 은 항목마다 따로.
- 두 채널: `trace.npz`(평가기 안에서 읽기만 하는 기록) 와 `server_log.npz`(서버가 받은 관측). 후자는 평가기에 아무것도 안 붙인 실행에도 있다
  → `nf_plain` 과 `nf_a` 를 비교해 **기록 자체가 결과를 안 바꾼다**는 것도 확인했다(5.2).
- `trace_images.npz`: 몇 스텝(0,1,2,10,50,100,…,500)의 카메라 원본 → 픽셀 차이 비율·평균·최대와 검은 화면 여부.

### 6.2 한계
- 폐루프(정책이 픽셀을 보고 행동)는 픽셀이 실행마다 달라 궤적이 갈라질 수 있다 → 폐루프 비교는 여러 판의 점수 분포로만 할 수 있다(비쌈).
  픽셀을 바꾸지 않는 가속은 재생 비교(비트)만으로 충분하다. 픽셀을 바꿀 수 있는 가속(타일 렌더 등)은 이 단계에서 "불가" 로 둔다.
- 서버 쪽 변경(행동 묶음 등)은 시뮬레이터 없이 같은 관측열을 두 경로에 넣어 행동을 비트 비교한다(`src/fasteval/verify_chunk_equivalence.py`).

### 6.3 부품 교체용 그림자 실행 (설계)
C++/Rust 로 옮기는 부품(7절: 물리 콜백, 관측 계산 등)은 `src/fasteval/` 의 얇은 파이썬 접착부가 공식 함수를 감싸
① 공식 함수 실행 → ② 같은 입력으로 새 함수 실행 → ③ 출력 비트 비교(다르면 스텝·항목 기록) → ④ 공식 출력을 돌려준다.
진행은 공식 값으로 하므로 차이가 누적되지 않고, 첫 불일치가 곧 그 부품의 버그다. 통과한 뒤에만 새 함수 출력으로 진행하는 모드로 바꾸고
6.1 의 재생 비교(비트 동일)를 한 번 더 한다.

## 7. 병목마다 — "병목 제로" 설계, 언어, 결과 위험, 검증

원칙(사용자 지시): 뜨거운 경로(매 스텝 도는 곳)는 라이브러리 호출(torch 연산, numpy, PyAV 등) 대신 **손으로 짠 C++/CUDA**. 라이브러리를 남기는 곳은
손으로 짜는 것이 비합리적인 경우(공식과 같아야 하는 닫힌 내부)만. GPU 가 아닌 조율 코드는 Rust. 파이썬은 평가기 프로세스에 거는 얇은 접착부만.

**torch 경계**(사용자 방침 "파이토치 갖다 버리고 최대한 최적화할수있을만큼 최적화")
- **우리가 짜는 코드에는 torch 가 없다.** 서브스텝 콜백(컨트롤러·보조 잡기), 접촉 복사, proprio, 관측 전처리(카메라 상대 pose), 통신, π0.5 추론 —
  전부 손으로 짠 C++/CUDA(+조율 Rust). π0.5 는 `src/pi05_native/` 의 네이티브 엔진(다른 에이전트 담당, 로컬은 평가기 안 pybind11, 제출은 리눅스 네이티브 웹소켓 서버).
- **공식 OmniGibson·Isaac Sim 안의 torch 는 그대로 둔다.** 공식 평가기와 결과가 같아야 하므로 공식 코드 경로(물체 상태·BDDL·지표·컨트롤러 원본 등)는 손대지 않는다.
- 경계에서의 약속: 우리 C++ 가 공식 torch 함수를 **대신하는** 곳(위 뜨거운 경로)은 6.3 의 그림자 실행으로 공식 torch 출력과 **비트 동일**을 먼저 보이고,
  그 뒤 재생 비교(6.1, `--strict`)를 통과해야 쓴다. 비트가 안 맞으면 그 항목은 공식 torch 그대로 둔다(불가).
- π0.5 엔진은 우리 제출물(정책)이라 공식 평가기와 같을 필요는 없다(규칙은 "reproducible from the files you submit"). 다만 공식 JAX 체크포인트와
  행동이 얼마나 다른지는 같은 관측열로 재서 적는다(반올림이 달라 비트 동일은 기대하지 않음 — 폐루프 점수로 판단).

실측 ms 칸(radio·224 RGB·환경 1 의 스텝당 ms, π0.5 폐루프 / 재생)은 이 PC 에서 다시 잴 것. "공식에 쓰나" = 주최 측 재평가에서도 그대로 쓸 수 있나

## 8. 전체 상한 (암달)

"못 없앰" = RTX 렌더 제출 + GPU 대기 + 카메라 읽기 + PhysX. 정책 추론은 모델 계산이라 따로.
상한 = 지금 ÷ (못 없앰 + 정책 추론). 묶음 재생만 하면 통신 × 15/16 이 빠진다. 수치는 4절을 이 PC 에서 다시 잰 뒤 채운다.

전체 평가 스텝 수(100 과제 × 10 판, 모두 제한시간까지 간다고 보면 1,581 만 스텝 — `task.jsonl` 의 사람 평균 × 1.5 합; 장면 로딩 1,000 번은 별도).

- 24 GB(채점용): π0.5 8 GB + 시뮬 환경 1~2 개(추정). 환경을 묶으면(`--num-envs`) 렌더·Kit 고정비가 나뉘어 처리량이 오를 수 있으나(측정 대기) **N=1 과 결과가 비트 단위로 다르다**(5.4) — 공식 재평가가 어떤 N 으로 도는지 모르면 로컬 N 을 정할 수 없다(11절 질문).

## 9. 시제품 — 행동 묶음 재생 서버 (`src/fasteval/pi05_chunk_server.py`)

고른 이유: 통신은 평가기에 이미 공식 인자가 있어 평가기를 한 줄도 안 바꾸고 제출에도 쓸 수 있다. C++/CUDA 로 새로 짤 뚜렷한 파이썬 병목 하나는 없었다(4절).
언어: 파이썬 — openpi 정책이 JAX 파이썬 객체라서 붙는 접착부(버퍼 인덱싱 몇 줄)뿐이다. 계산은 JAX/XLA.

동작
- 요청에 `__action_chunk_size__ = K` 가 있으면 평소처럼 `act()` 로 첫 행동을 만들고(16 스텝 경계라 추론이 돈다), 같은 버퍼에서 이어지는 K−1 개를
  `action_chunk` 로 준다. 버퍼 위치·스텝 카운터를 K−1 만큼 넘겨 다음 요청이 공식 경로와 같은 스텝(16 의 배수)에서 추론하게 한다.
- K 가 재계획 경계를 넘으면 거부한다(원문 "choose `K` so replay never crosses the policy's replanning boundary").
- 묶음 요청이 없으면 openpi 공식 서버와 똑같이 동작한다.

결과가 같은 이유 (구조)
- 공식 경로(`eval_b1k_wrapper.py` `act_receding_horizon`)는 16 스텝마다만 추론하고, 사이 스텝의 관측은 크기 조정만 하고 버린다 → 안 보내도 같다.
- JAX 난수(`policy.py:65` `jax.random.key(0)`, `:75` 추론마다 split)는 추론 횟수가 같으므로 같은 순서로 쪼개진다.
- 평가기 클라이언트는 묶음 첫 행동이 `action` 과 비트 같은지 확인하고(`network_utils.py` `th.equal`), 나머지를 그대로 쓴다.

검증 (`src/fasteval/verify_chunk_equivalence.py`, JSBSim 틀: 같은 입력 → 두 경로 → 출력 전부 비트 비교)
아직 못 돌렸다. 돌리는 법: `bash tools/run_verify_chunk.sh` — 스크립트 안 저장소 경로를 `~/behavior-2026` 으로 고치고 `~/openpi`·체크포인트를 갖춰야 돈다(미확인)
(같은 관측열 64 스텝, 배치 1·2, 음성 대조 2 가지 포함, 통과하면 exit 0). 서버 단 단위로는 구조상 같다(위).

속도
아직 못 쟀다. 예상(추정): π0.5 루프에서 통신 × 15/16 만큼 스텝당 시간이 준다. 이 PC 에서 잰다.

## 13. 실험 실행 — 두 평가기

사용자 지시 "최대한 빠르게 실험해볼 수 있게 세팅" + "오리지널 평가기도 두자, 우리가 포팅한 평가기랑". 한 명령 실험 실행기·제출 패키지 도구는 이 PC 용이 아직 없다(행렬 예: `tools/exp/*.json`).

- **두 평가기**
  - `original`: 공식 v3.9.3 그대로(BEHAVIOR-1K 무수정) + 계측·검출만(`eval_instrumented.py`). 가속 부품을 섞지 않는다. 제출·리더보드 수치는 이것으로만.
  - `ported`: 우리 엔진(`src/engine`)·네이티브 π0.5·가속 부품. 지금은 자리만 — 진입 모듈이 생기면 `BEHAVIOR_PORTED_EVAL` 로 붙인다. 약속: 공식 eval.py 와 같은 인자·같은 결과 형식.
  - 비교: 두 결과에서 같은 설정·과제·인덱스끼리 짝지어 `trace_compare.py --check --strict --pixels-report-only` — 스텝별 행동·proprio·관절·로봇/과제 물체 pose·
    목표 조건·지표·결과 JSON(q_score 포함)은 비트 동일만 통과, 영상은 RTX 잡음(5.1)이라 표에만. 노이즈 바닥 쌍(`nf_a` vs `nf_b`)으로 시험: 통과(비트 동일 19, 픽셀 다름 9),
    음성 대조(`nf_neg`)는 실패로 잡힘(다름 10, JSON 3).
- **무효 판정**: 판마다 `--black-guard=abort` — 정책에 들어갈 RGB 가 전부 0 인 첫 스텝에서 그 판을 끊고 "무효(스텝, 카메라)" 로 적는다. 고쳐 넣지 않는다(5.2).
- **정책 연결**: `--native-policy=모듈:함수` 로 공식 `load_policy` 자리에 평가기 프로세스 안 정책을 넣는다(평가기 코드는 그대로 — 정책은 우리 제출물).
  네이티브 π0.5(`src/pi05_native/`, pybind11)가 나오면 여기에 붙는다.
- **장면 로딩**(인스턴스마다 약 2 분)
  - 인스턴스마다 새 프로세스(공식 기본, `--num-envs 1`) — **기본**.
  - 장면 재사용(한 프로세스에서 공식 `evaluator.run()` 을 인스턴스마다 다시 부름, `--instances-seq`) — 둘째 인스턴스의 과제 물체 pose 가 스텝 0 부터 2~3 µm 다름(JSON·로봇은 같음, 09-30) → **안 씀**. 제출 판은 늘 새 프로세스.
  - 공식 `--num-envs N` — N=1 과 물리 비트가 다름(5.4) → 안 씀.
  - 공식 eval.py 는 인스턴스 수 = `--num-envs` 를 강제한다. 그래서 재사용은 공식 main 에 첫 인스턴스만 넘기고, 첫 `run()` 호출을 가로채 인스턴스마다 공식 `run()` 을 부른다.
