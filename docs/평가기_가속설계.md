2. **물리·판정은 같은 행동열이면 비트 단위로 재현된다.** 같은 행동을 다시 넣은 실행 5 번(π0.5 폐루프 1 + 재생 4)에서 관절·로봇 pose·
   과제 물체 pose·목표 조건·지표·결과 JSON 이 전부 비트 동일. **픽셀만 매번 다르다**(RTX 렌더 잡음 + 검은 화면 위치가 실행마다 바뀜).
   → "공식과 같다"의 기준은 물리·판정·JSON = 비트 동일, 픽셀 = 공식 자기 자신과의 차이(노이즈 바닥) 안. 5절.
3. **radio, 헤드리스, 224 RGB, 환경 1 개** 기준 스텝당 시간(실측): π0.5 폐루프 151.6 ms(6.6 스텝/초), 재생(추론 없음) 96.3 ms(10.4 스텝/초).
   상위 5 개(π0.5 루프): 정책 추론 56.1 ms(37%) · WSL 넘는 통신 28.0 ms(18.5%) · RTX 렌더 제출 23.3 ms(15%) ·
   물체 상태 캐시 9.5 ms(6.3%, 이 중 8.7 ms 는 렌더가 끝나길 기다리는 GPU 대기) · 물리 서브스텝 콜백(컨트롤러·보조 잡기) 9.4 ms(6.2%).
   PhysX 물리 자체는 3.7 ms(2.4%) 뿐이다. 4절.
4. **못 없애는 것**: RTX 렌더(≈32 ms, GPU 대기·카메라 읽기 포함)와 PhysX(3.5 ms)는 닫힌 내부라 다시 짜서 같은 결과를 낼 수 없다 → "불가".
   정책 추론은 모델 계산이라 없앨 수 없다. 그 나머지를 **전부 0 으로 만들 때의 상한**: π0.5 루프 151.6 → 약 93 ms(1.6 배),
   재생 루프 96.3 → 35.5 ms(2.7 배). 8절.
5. **시제품(하나)**: 가장 큰 '없앨 수 있는' 병목인 통신을, 평가기에 이미 있는 공식 인자 `--replay-action-chunk-size 16` 에
   응답하는 π0.5 서버(`src\fasteval\pi05_chunk_server.py`)로 줄였다. ⟪시제품 결과⟫ 9절.
6. **C++/CUDA 로 새로 짤 뚜렷한 파이썬 병목 하나는 없다.** 파이썬 쪽 항목은 각각 스텝당 2~5 ms(2~6%)로 흩어져 있고, 물체 상태는
   OmniGibson 이 이미 warp CUDA 그래프로 돌린다(`simulator.py` `_capture_warp_graph`). "병목 제로" 설계(7절)는 이것들을
   물리 콜백 C++ 이식·관측 계산 C++ 한 함수·영상 작업 스레드로 한꺼번에 치우는 순서로 짰다 — 대부분 공식 평가기 내부를 바꾸므로 **개발용**이다.

## 1. 조건과 규칙

사용자 조건: 물리 120 Hz / 렌더 30 Hz / 행동 30 Hz, 정책이 받는 관측(RGB·depth·proprio), 종료·BDDL 목표 판정, q_score·지표 JSON 이
공식 평가기와 같아야 한다. 같다는 것을 증명 못 하는 가속은 "불가". 언어: GPU 로 할 수 있는 일은 C++/CUDA, 나머지 새 코드는 Rust,
파이썬은 OmniGibson·평가기 프로세스에 거는 얇은 접착부만. 목표는 "병목 제로".

규칙 원문 ([raw/site_challenge_submission.md](raw/site_challenge_submission.md), [raw/site_challenge_evaluation.md](raw/site_challenge_evaluation.md)):
- "Final evaluation must be reproducible from the files you submit." (submission:33)
- "Do not modify the output JSON files or rollout videos in any way." (submission:72)
- "After running the evaluation script at `OmniGibson/omnigibson/eval/eval.py`, each rollout produces:" (submission:23)
- README 에 넣을 것: "Instructions for evaluating your policy, including the full evaluator command, wrapper path, robot config path, Docker image details or IP address information." (submission:102)

정리
- 공식 인자(`--num-envs`, `--replay-action-chunk-size`)와 우리 서버 쪽 변경은 제출 README 의 "full evaluator command" 에 적으면 되는 범위다.
- **평가기 내부를 바꾼 가속판으로 만든 JSON 을 제출에 써도 되는지는 원문에 없다.** "evaluation script at eval.py" 로 만든다고만 적혀 있다 → Discord 에 물을 것(11절). 그 전까지 가속판은 **우리 개발 반복용**이다.
- "같다"의 범위: 같은 PC·같은 드라이버에서 공식 평가기와 같음. 주최 측 GPU(원문 "RTX 3090, A5000, and TitanRTX", submission:84)와 이 PC(RTX 5070 Ti)는 RTX 렌더·DLSS 가 달라 픽셀이 원래 다를 수 있다 (추정 — RTX 렌더 설정은 `simulator.py:664` "RealTimePathTracing", `:670` DLSS).

## 3. 측정 방법

도구 (평가기 코드는 한 줄도 안 바꿈)
- `tools\eval_instrumented.py` — 공식 `omnigibson.eval.eval` 을 그대로 부르면서 함수들을 '겉싸개'로 감싸 perf_counter 로 들어간/나온 시각만 적는다.
  구간은 호출 경로(`step/apply_actions/env.step/sim.step/app.update/physx`)별 '자기 시간'. PhysX 계산 = 앞 콜백 끝 ~ 뒤 콜백 시작(서브스텝마다).
  겉싸개 비용 실측 1.2 μs/호출(`t2` 에서 스텝당 약 400 번 → 0.5 ms). `--summary` 가 경로를 아래 병목 항목으로 묶는다.
- 예전 `tools\profile_eval.py`(cProfile)는 지웠다: Kit 이 `carb.profiler` 를 불러오며 파이썬 프로파일 훅을 가져가서, 그 뒤로 아무것도
  안 잡혔다(19:29 실행: 206 초 전부가 `carb\profiler\__init__.py` import 한 줄에 몰림, `outputs\eval_turning_on_radio_20260929_1929\profile.prof.cumulative.txt`).
  `run_eval_radio.ps1 -Profile` 은 `-Timing`(+ `-Deep`)·`-Trace` 로 바꿨다.
- `tools\replay_policy_server.py` — 기록한 행동열을 그대로 돌려주는 서버. 정책 쪽 잡음이 빠지고 시뮬레이터만 남는다. 받은 관측을 해시로 남겨,
  평가기에 아무것도 안 붙인 실행도 비교할 수 있다. `tools\run_replay_eval.ps1` 이 서버(WSL)와 평가기를 한 번에 띄운다.
- `tools\transport_bench.py` — 시뮬레이터 없이 정책 왕복만(평가기 클라이언트와 같은 연결 인자).
