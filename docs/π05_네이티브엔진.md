작성 2026-09-29~30. 코드 `src\pi05_native\`(영문 README 있음). 이 문서의 숫자는 전부 이 PC(RTX 5070 Ti 16 GB, sm_120)에서 잰 값이고,

## 0. 한눈에

- **무엇**: openpi π0.5(radio 체크포인트)와 2025 1위 모델(PiBehavior)의 추론을 **PyTorch·JAX 없이** C++/CUDA 로 다시 짰다.
  행렬곱도 텐서 코어 명령(`mma.sync` bf16)으로 손으로 짰고 cuBLAS·cuDNN·pybind11·sentencepiece·msgpack·웹소켓 라이브러리는 안 쓴다.
- **왜**: ① 이 PC 에서는 다른 프로세스가 GPU 메모리를 약 5 GiB 넘게 잡으면 시뮬레이터 RGB 가 검게 나온다(plan.md 4.0) → π0.5 를
  **평가기 프로세스 안**에 넣어야 하는데 JAX 는 Windows 에서 GPU 를 못 쓴다. ② π0.5 추론(스텝당 평균 56 ms, 37%)과 WSL 왕복(28 ms)이
  평가 스텝 시간의 절반이다([평가기_가속설계.md](평가기_가속설계.md) 4.1).
- **정확도(radio)**: 층마다 JAX-GPU 와 비교한 오차가 "JAX-CPU 대 JAX-GPU"(노이즈 바닥) 이하~1.5 배. 최종 행동(로봇 단위) 최대차 9.6e-3
  (바닥 8.8e-3). 판정 규칙(우리 ≤ 2 × 바닥) 실패 0. 3절.
- **속도·메모리(1차 최적화 후)**: radio GPU 추론 **78.0 ms**(CUDA Graph 한 번, 최적화 전 108.6 ms). JAX 서버는 같은 GPU 단독에서
  모델 84.9 ms / infer 전체 120.1 ms. 1위 모델(20 단계, 접두부 805 토큰) **91.6 ms**, JAX 는 infer 212 ms. GPU 메모리는 가중치 5.05 GiB + 활성값 0.15 GiB(JAX 는 7.3 GB 사용, 8 GB 선점). 4절.
- **연결**: Windows 평가기 안(`--policy local` 런처, 원본 무수정)과 Linux 제출용 웹소켓 서버(openpi 프로토콜) 둘 다 같은 엔진. 5·6절.
- **학습(12절)**: openpi 학습 스텝을 C++/CUDA 로 포팅 — expert·LoRA 두 모드가 자른 판 JAX 대조 통과(몇 점 예외), 전체 크기 16 GB 에 들어감(expert 3.0 s·lora 11 s / 배치 32). 실제 학습은 보류.
- **1위 모델**: JAX 대조 4 샘플 전 지점 통과(7절). 같은 엔진을 일반화해 PiBehavior(과제 임베딩·단계 토큰·KV 층 결합·상관 잡음·부드러운 인페인팅·단계 투표·3차 보간·
  교정 규칙)를 옮겼다. 단계를 밖에서 고정하는 통로(`pi05_set_stage`)를 만들었다. 7절.

## 3. 정답 기준과 층별 대조 (JSBSim 틀)

`C:\jsbsim-f16-cuda\jsbsim_f16_cuda\fdm_verify.py` 와 같은 생각: **정답의 한가운데 상태를 심고 한 층만 돌려** 층 하나의 차이를 떼어 보고,
처음부터 끝까지도 돌려 누적을 본다.

- 정답: WSL JAX, 공식 `create_trained_policy` 로 만든 정책 그대로. 층별 값은 공식 flax 모듈(`siglip.Encoder1DBlock`, `gemma.Block`,
  `gemma.RMSNorm`)을 층 하나씩 불러 얻었다. 공식 fused `sample_actions` 결과도 같이 덤프.
- **노이즈 바닥** = 같은 입력으로 JAX 를 CPU 에서 돌린 값과 GPU 값의 차이. 층 하나(교사강제) 바닥은 CPU JAX 층에 GPU 정답 입력을 심어서 잰다.
  참고로 "JAX-GPU 층별 호출 vs JAX-GPU 한 덩어리 jit" 도 최종 행동 상대오차 1.8e-2 — XLA 가 연산을 묶는 방식만 바뀌어도 이만큼 흔들린다.
- 도구: `pi05_verify --weights W --ref DIR --tag gpu --floor cpu --floor-single cpu_planted --check`(`tools\verify.cpp`). 판정 = 모든
  지점에서 상대 L2 오차 ≤ 2 × 바닥. 실패 시 종료 코드 1.

## 4. 속도·메모리

| 항목 | 네이티브 | JAX 서버 |
|---|---:|---:|
| 모델만(radio, 10 단계) | 78.0 ms (CUDA Graph; WSL 과 Windows exe 같음. 최적화 전 108.6) | 84.9 ms (`policy_timing.infer_ms`, 같은 GPU 단독) |
| 모델만(1위, 20 단계) | 91.6 ms | infer 212 ms (`dump_reference_pb.py --bench`) |
| 단계별(radio, 그래프 없이) | SigLIP 12.5 · 접두부 48.1 · 잡음 제거 10 단계 27 ms | |
| infer 전체(변환 포함) | 109.8 ms (Windows, 파이썬 경계 포함) | 120.1 ms |
| GPU 메모리 | 가중치 5.05 GiB + 활성 0.15 GiB | 사용 7.3 GB, 선점 8 GB(XLA 비율 0.5) |
| 로드 시간 | 4.4 s (Windows, 그래프 캡처 포함) | 16~32 s |
| 평가기와 통신 | 0 (같은 프로세스) | WSL 왕복 스텝당 28 ms |

손 GEMM 대 cuBLASLt(같은 모양, 무게 순환으로 DRAM 에서 읽게 함): 대부분 ±10% 안이고 어텐션 모양은 우리가 더 빠르다.
Gemma gate/up(968×32768×2048)만 1.88 ms 대 1.40 ms 로 느렸다 → 원인은 격자 순서(무게 타일을 M 타일마다 DRAM 에서 다시 읽음). M 을
먼저 도는 격자로 바꿨다. 1차 최적화(108.6 → 78.0 ms): M 우선 격자, 분할-K 를 커널 안 티켓으로 결정적으로 합치기, PDL(앞 커널이
끝나기 전에 무게 미리 읽기), 끝단 합치기(RoPE+KV 캐시 쓰기, gelu·up, 게이트 잔차). 최종 행동은 최적화 전과 비트 동일.

## 5. 평가기 안에서 (Windows)

- 빌드: `src\pi05_native\build_windows.bat` — MSVC 2022 + CUDA 12.8 nvcc(별도 conda 환경 `pi05build`, 관리자 권한 없이, [설치기록.md](설치기록.md)).
  CUDA 런타임은 정적 링크(평가기의 torch 가 가진 cudart DLL 과 안 부딪히게).
- 파이썬 접착부: `glue\pi05native_module.c` — CPython C API 와 버퍼 프로토콜만(pybind11·numpy 헤더·torch 없음). 이미지·상태는 버퍼 포인터로,
  CUDA 텐서는 `__cuda_array_interface__` 의 장치 포인터로 받아 복사 없이 넘긴다. 추론 동안 GIL 을 푼다.
- 정책: `glue\pi05_policy.py` — 공식 `LocalPolicy` 의 `policy` 자리에 들어가는 객체. 행동은 우리 float32 버퍼를 `torch.from_numpy` 로
  감싸 돌려준다(평가기 API 가 텐서를 요구, 복사 없음). 매 스텝 검은 프레임(RGB 전부 0)·스텝 시간·추론 시간을 CSV 로 남긴다.
- 실행: `powershell -File src\pi05_native\glue\run_eval_native.ps1 [-MaxSteps 600] [-Video]` — 공유 GPU 잠금을 잡고, 다른 시뮬레이터가
  없고 다른 프로세스 VRAM 이 3.5 GB 아래일 때만 시작한다. 실험 행렬은 `tools\exp_run.ps1` 의 `policy: native`,
  `module: pi05_policy:make_policy` 와 `PYTHONPATH=src\pi05_native\glue;src\pi05_native\build_win`, 환경변수 `PI05_MODEL=radio|pb2025`.

## 6. 제출용 서버 (Linux)

`server\pi05_server.cpp` — openpi 웹소켓 프로토콜(연결 때 메타데이터, 관측 msgpack(`__ndarray__` 맵) → `{"action", "server_timing"}`,
`{"reset": true}`, `GET /healthz`)을 RFC 6455·SHA-1·base64·msgpack 까지 직접 짰다. `TCP_NODELAY` + 읽을 때마다 `TCP_QUICKACK`
(Rust 중계기 `src\agent\src\ws.rs` 와 같은 방식; 평가기 가속 에이전트 실측 32.3 → 4.1 ms). `__action_chunk_size__` 요청이 오면 같은
receding-horizon 묶음의 다음 K 개를 한 번에 준다(재계획 경계를 넘으면 경고).
Rust 코드 재사용은 검토 후 안 했다: 엔진과 같은 C++ 한 빌드로 두는 쪽이 Docker 에 Rust 툴체인이 필요 없고 FFI 경계도 없다.
방식(QUICKACK 재설정, writev 한 번)은 Rust 구현을 그대로 따랐다.

## 12. 학습 — openpi π0.5 학습 스텝을 C++/CUDA 로 (JAX·PyTorch 없이)

코드 `src\pi05_train\`(영문 README). 학습을 실제로 돌리는 것은 보류 — 여기까지는 포팅과 대조, 몇 스텝 시험만.

### 12.1 무엇을 옮겼나 (대조 기준 = WSL `~/openpi` behavior 브랜치)

| openpi | 여기 |
|---|---|
| 손실 `models/pi0.py:189-214` (접두+접미 한 번에, x_t = t·잡음 + (1-t)·행동, u = 잡음 - 행동, 평균 (v-u)²) | `src\trainer.cu`(전문가 모드), `src\lora.cu`(LoRA 모드) |
| 학습 스텝 `scripts/train.py:85-180` (얼린 파라미터 bf16, 학습 파라미터 f32 원본을 einsum 때 bf16 로, value_and_grad, EMA 0.99) | `Trainer/LoraTrainer::accumulate → finalize_grads → opt_step` |
| 옵티마이저 `training/optimizer.py` (clip_by_global_norm 1.0 → AdamW b1 .9 b2 .95 eps 1e-8 wd 1e-10, warmup 1000 → 코사인 2.5e-5 → 2.5e-6) | `src\tparams.cu`, `src\tkern.cu adamw_step`(설정은 상태 파일에서 읽음) |
| 난수 사슬 (`key(seed)` → split → 스텝마다 `fold_in` → split 3 → 증강 키·잡음 normal·시간 beta(1.5,1)) | `src\trng.h` (threefry, split, uniform, gamma/beta 를 JAX 코드 그대로) |
| 영상 증강 `models/model.py:168-187` (augmax: 자르기 95%·크기·회전 ±5°, 색 흔들기) | `src\augment.cu` |
| 데이터 로더 (fasttrain 네이티브 로더) | `tools\train_main.cu` 가 C API 로 직접 (파이썬 경계 0) |

- 역전파는 JAX 가 실제로 만드는 연산 순서·bf16 반올림 위치를 따랐다: 예) 여러 einsum 이 같은 입력을 쓰면 뒤에 쓴 einsum 의 기여부터
  bf16 로 더함, LoRA einsum 안에서는 LoRA 경로가 기본 곱보다 먼저, bf16 einsum 의 가중치 기울기는 배치 전체 합을 한 번 bf16 로 반올림,
  f32 logits 를 받는 어텐션의 dq·dk 는 f32 기울기를 bf16 세 조각(hi+mid+lo)으로 나눠 텐서코어로 정확히 계산.
- 행렬곱은 손으로 짠 범용 텐서코어 GEMM(`src\tgemm.cuh`) — 피연산자 배치 4 가지를 `ldmatrix`/`ldmatrix.trans` 로 받아 openpi 의
  `[in, out]` 파라미터를 전치 없이 y=xW, dx=dyWᵀ, dW=xᵀdy 에 그대로 씀(CPU 배정밀도 대비 상대 1.8e-7 이내, `tools\tgemm_test.cu`).
- 샘플 하나씩(미세배치 1) 앞·뒤로 돌리고 기울기를 f32 로 누적해 배치 평균을 만든다. LoRA 모드는 openpi 처럼 층마다 입력만 두고 역전파 때
  층을 다시 계산(remat, openpi `nn.remat(..., nothing_saveable)` 과 같은 방식).
- 증강은 augmax 코드 그대로라 augmax 의 성질도 그대로다: 색 흔들기 기본값 hue 0.1·p 0.5, saturation 단계는 결과를 버려서 효과 없음
  (augmax `colorspace.py:274-275`).

### 12.3 대조 (자른 판: 실제 radio 체크포인트의 SigLIP 2 층·Gemma 2 층, 배치 4, 10 스텝)

판정은 추론과 같게 우리 상대오차 ≤ 2 × 바닥(바닥 = 같은 JAX 계산의 CPU 대 GPU). 파라미터는 갱신량(p - p0)으로 비교.
정답 `tools\train_ref.py`, 대조 `tools\train_verify.cpp`, 기록 `data\pi05_train\s8~s9.log`.

| 모드 | 손실 | 기울기 | AdamW 1·10 스텝 뒤 갱신량·EMA |
|---|---|---|---|
| expert (19 텐서) | 3.1e-5 (바닥 7.9e-4) | 19/19 통과 (바닥의 0.8~1.4 배) | 1 점 빼고 통과 |
| lora (51 텐서, 층별로도 확인) | 4.3e-5 (바닥 9.7e-4) | 49/51 통과 | 2 점 빼고 통과 |

남은 점(모두 작은 값):
- LayerNorm scale 기울기 둘: SigLIP `encoder_norm/scale` 5.6e-3(바닥 2.3e-3, 2.5 배), 마지막 층 `LayerNorm_1/scale` 6.2e-3(바닥 3.1e-3,
  2.0 배 경계). 같은 LayerNorm 의 bias 기울기·그 뒤 Dense 기울기는 통과 — 원인 미확정(추정: Σ dy·x̂ 의 상쇄가 커서 상류 오차가 커 보임).
- 1 스텝 Adam 갱신: 1 스텝의 Adam 은 g/(|g|+eps) ≈ 부호라서 |g| 가 0 근처인 원소 하나의 부호가 바뀌면(`embedding/bias` 865 번,
  `time_mlp_in/bias` 1015 번) 그 원소 갱신이 ±lr 로 뒤집힌다. 10 스텝 뒤는 통과. EMA 1 ulp 차이 한 점.
- 난수·증강(`tools\aug_ref.py`, `tools\aug_test.cu`): 스텝 키 비트 일치, 잡음 99.6% 비트 일치(나머지 1 ulp), beta 시간 1 ulp 안,
  증강 영상은 JAX-CPU 와 같고 JAX-GPU 와의 차이는 JAX 자신의 CPU 대 GPU 차이와 같다(상대 3.6e-3).
