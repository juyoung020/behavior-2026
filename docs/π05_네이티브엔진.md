## 0. 한눈에

- **무엇**: openpi π0.5(radio 체크포인트)와 2025 1위 모델(PiBehavior)의 추론을 **PyTorch·JAX 없이** C++/CUDA 로 다시 짰다.
  행렬곱도 텐서 코어 명령(`mma.sync` bf16)으로 손으로 짰고 cuBLAS·cuDNN·pybind11·sentencepiece·msgpack·웹소켓 라이브러리는 안 쓴다.
- **왜**: π0.5 를 **평가기 프로세스 안**에 넣어 정책 통신을 없애고, 프레임워크 없이 병목을 직접 줄이려고(plan.md 0절 "병목 제로").
- **정확도(radio)**: 층마다 JAX-GPU 와 비교한 오차가 "JAX-CPU 대 JAX-GPU"(노이즈 바닥) 이하~1.5 배. 최종 행동(로봇 단위) 최대차 9.6e-3
  (바닥 8.8e-3). 판정 규칙(우리 ≤ 2 × 바닥) 실패 0. 3절.
- **메모리**: 가중치 5.05 GiB + 활성값 0.15 GiB. 속도는 이 PC 에서 다시 잴 것. 4절.
- **연결**: 평가기 안(`--policy local` 런처, 원본 무수정)과 제출용 웹소켓 서버(openpi 프로토콜) 둘 다 같은 엔진. 5·6절.
- **학습(12절)**: openpi 학습 스텝을 C++/CUDA 로 포팅 — expert·LoRA 두 모드가 자른 판 JAX 대조 통과(몇 점 예외), 전체 크기 두 모드 모두 24 GB 안. 추론·평가는 지금 작업 PC(RTX 5070 Ti 16 GB)에서 잘 돈다. LoRA 학습은 학교 4090(24 GB)에서 한다. 실제 학습은 보류.
- **1위 모델**: JAX 대조 4 샘플 전 지점 통과(7절). 같은 엔진을 일반화해 PiBehavior(과제 임베딩·단계 토큰·KV 층 결합·상관 잡음·부드러운 인페인팅·단계 투표·3차 보간·
  교정 규칙)를 옮겼다. 단계를 밖에서 고정하는 통로(`pi05_set_stage`)를 만들었다. 7절.

## 3. 정답 기준과 층별 대조 (JSBSim 틀)

JSBSim F16 CUDA 검증기(`fdm_verify.py`)와 같은 생각: **정답의 한가운데 상태를 심고 한 층만 돌려** 층 하나의 차이를 떼어 보고,
처음부터 끝까지도 돌려 누적을 본다.

- 정답: JAX, 공식 `create_trained_policy` 로 만든 정책 그대로. 층별 값은 공식 flax 모듈(`siglip.Encoder1DBlock`, `gemma.Block`,
  `gemma.RMSNorm`)을 층 하나씩 불러 얻었다. 공식 fused `sample_actions` 결과도 같이 덤프.
- **노이즈 바닥** = 같은 입력으로 JAX 를 CPU 에서 돌린 값과 GPU 값의 차이. 층 하나(교사강제) 바닥은 CPU JAX 층에 GPU 정답 입력을 심어서 잰다.
  참고로 "JAX-GPU 층별 호출 vs JAX-GPU 한 덩어리 jit" 도 최종 행동 상대오차 1.8e-2 — XLA 가 연산을 묶는 방식만 바뀌어도 이만큼 흔들린다.
- 도구: `pi05_verify --weights W --ref DIR --tag gpu --floor cpu --floor-single cpu_planted --check`(`tools/verify.cpp`). 판정 = 모든
  지점에서 상대 L2 오차 ≤ 2 × 바닥. 실패 시 종료 코드 1.

- JAX 와 같은 난수: `jax.random.key(0)` → split → normal 을 C++ 로 옮겼다(threefry2x32, 파티션 가능 모드). 키는 비트 동일, 값은 95%
  비트 동일·나머지 1 ulp(log1p 구현 차). 그래서 같은 관측을 넣으면 JAX 서버와 같은 행동 묶음이 나온다(바닥 안에서).

## 4. 속도·메모리

- GPU 메모리: 가중치 5.05 GiB + 활성 0.15 GiB(토큰 임베딩 표는 호스트, 2절). 평가기 안에서 돌면 정책 통신은 0(같은 프로세스).
- 추론·로드 시간과 JAX 서버 대비는 이 PC 에서 다시 잴 것. (Windows 시절 기록은 [archive/windows/π05_네이티브엔진.md](archive/windows/π05_네이티브엔진.md) 참고.)

손 GEMM 대 cuBLASLt(같은 모양, 무게 순환으로 DRAM 에서 읽게 함): 대부분 ±10% 안이고 어텐션 모양은 우리가 더 빠르다.
Gemma gate/up(968×32768×2048)만 느렸다 → 원인은 격자 순서(무게 타일을 M 타일마다 DRAM 에서 다시 읽음). M 을
먼저 도는 격자로 바꿨다. 1차 최적화: M 우선 격자, 분할-K 를 커널 안 티켓으로 결정적으로 합치기, PDL(앞 커널이
끝나기 전에 무게 미리 읽기), 끝단 합치기(RoPE+KV 캐시 쓰기, gelu·up, 게이트 잔차). 최종 행동은 최적화 전과 비트 동일.

## 5. 평가기 안에서

- 파이썬 접착부: `glue/pi05native_module.c` — CPython C API 와 버퍼 프로토콜만(pybind11·numpy 헤더·torch 없음). 이미지·상태는 버퍼 포인터로,
  CUDA 텐서는 `__cuda_array_interface__` 의 장치 포인터로 받아 복사 없이 넘긴다. 추론 동안 GIL 을 푼다.
- 정책: `glue/pi05_policy.py` — 공식 `LocalPolicy` 의 `policy` 자리에 들어가는 객체. 행동은 우리 float32 버퍼를 `torch.from_numpy` 로
  감싸 돌려준다(평가기 API 가 텐서를 요구, 복사 없음). 매 스텝 검은 프레임(RGB 전부 0)·스텝 시간·추론 시간을 CSV 로 남긴다.
- 런처: `glue/run_eval_native.py`(공식 `omnigibson.eval.eval` 을 `--policy local` 로, 원본 무수정). 환경변수 `PI05_MODEL=radio|pb2025`.
- 리눅스용 파이썬 모듈: `build_linux.sh` 가 `src/vla/pi05_native/build/_pi05native.cpython-311-x86_64-linux-gnu.so` 도 만든다(conda env behavior 의 python, `PI05_PY` 로 바꿈). 런처·정책의 데이터·로그 경로는 저장소 기준 상대 경로. (Windows 시절 기록은 [archive/windows/π05_네이티브엔진.md](archive/windows/π05_네이티브엔진.md) 참고.)

## 6. 제출용 서버 (Linux)

`server/pi05_server.cpp` — openpi 웹소켓 프로토콜(연결 때 메타데이터, 관측 msgpack(`__ndarray__` 맵) → `{"action", "server_timing"}`,
`{"reset": true}`, `GET /healthz`)을 RFC 6455·SHA-1·base64·msgpack 까지 직접 짰다. `TCP_NODELAY` + 읽을 때마다 `TCP_QUICKACK`
(Rust 중계기 `src/agent/planner/src/ws.rs` 와 같은 방식). `__action_chunk_size__` 요청이 오면 같은
receding-horizon 묶음의 다음 K 개를 한 번에 준다(재계획 경계를 넘으면 경고).
Rust 코드 재사용은 검토 후 안 했다: 엔진과 같은 C++ 한 빌드로 두는 쪽이 Docker 에 Rust 툴체인이 필요 없고 FFI 경계도 없다.
방식(QUICKACK 재설정, writev 한 번)은 Rust 구현을 그대로 따랐다.

## 12. 학습 — openpi π0.5 학습 스텝을 C++/CUDA 로 (JAX·PyTorch 없이)

코드 `src/vla/pi05_train/`(영문 README). 학습을 실제로 돌리는 것은 보류 — 여기까지는 포팅과 대조, 몇 스텝 시험만.

### 12.1 무엇을 옮겼나 (대조 기준 = `~/openpi` behavior 브랜치)

| openpi | 여기 |
|---|---|
| 손실 `models/pi0.py:189-214` (접두+접미 한 번에, x_t = t·잡음 + (1-t)·행동, u = 잡음 - 행동, 평균 (v-u)²) | `src/trainer.cu`(전문가 모드), `src/lora.cu`(LoRA 모드) |
| 학습 스텝 `scripts/train.py:85-180` (얼린 파라미터 bf16, 학습 파라미터 f32 원본을 einsum 때 bf16 로, value_and_grad, EMA 0.99) | `Trainer/LoraTrainer::accumulate → finalize_grads → opt_step` |
| 옵티마이저 `training/optimizer.py` (clip_by_global_norm 1.0 → AdamW b1 .9 b2 .95 eps 1e-8 wd 1e-10, warmup 1000 → 코사인 2.5e-5 → 2.5e-6) | `src/tparams.cu`, `src/tkern.cu adamw_step`(설정은 상태 파일에서 읽음) |
| 난수 사슬 (`key(seed)` → split → 스텝마다 `fold_in` → split 3 → 증강 키·잡음 normal·시간 beta(1.5,1)) | `src/trng.h` (threefry, split, uniform, gamma/beta 를 JAX 코드 그대로) |
| 영상 증강 `models/model.py:168-187` (augmax: 자르기 95%·크기·회전 ±5°, 색 흔들기) | `src/augment.cu` |
| 데이터 로더 (fasttrain 네이티브 로더) | `tools/train_main.cu` 가 C API 로 직접 (파이썬 경계 0) |

- 역전파는 JAX 가 실제로 만드는 연산 순서·bf16 반올림 위치를 따랐다: 예) 여러 einsum 이 같은 입력을 쓰면 뒤에 쓴 einsum 의 기여부터
  bf16 로 더함, LoRA einsum 안에서는 LoRA 경로가 기본 곱보다 먼저, bf16 einsum 의 가중치 기울기는 배치 전체 합을 한 번 bf16 로 반올림,
  f32 logits 를 받는 어텐션의 dq·dk 는 f32 기울기를 bf16 세 조각(hi+mid+lo)으로 나눠 텐서코어로 정확히 계산.
- 행렬곱은 손으로 짠 범용 텐서코어 GEMM(`src/tgemm.cuh`) — 피연산자 배치 4 가지를 `ldmatrix`/`ldmatrix.trans` 로 받아 openpi 의
  `[in, out]` 파라미터를 전치 없이 y=xW, dx=dyWᵀ, dW=xᵀdy 에 그대로 씀(CPU 배정밀도 대비 상대 1.8e-7 이내, `tools/tgemm_test.cu`).
- 샘플 하나씩(미세배치 1) 앞·뒤로 돌리고 기울기를 f32 로 누적해 배치 평균을 만든다. LoRA 모드는 openpi 처럼 층마다 입력만 두고 역전파 때
  층을 다시 계산(remat, openpi `nn.remat(..., nothing_saveable)` 과 같은 방식).
- 증강은 augmax 코드 그대로라 augmax 의 성질도 그대로다: 색 흔들기 기본값 hue 0.1·p 0.5, saturation 단계는 결과를 버려서 효과 없음
  (augmax `colorspace.py:274-275`).

### 12.2 모드와 메모리

전체 미세조정은 24 GB 에도(16 GB 는 물론) 안 들어간다(3.3B × (f32 원본 4 + 기울기 4 + Adam 8 + EMA 4 B) ≈ 66 GB). 두 모드를 지원한다.

| 모드 | 학습 대상 | 비고 |
|---|---|---|
| expert | 액션 전문가 전체(4.3억) + action_in/out + time MLP | SigLIP·Gemma 는 얼림, 접두부는 추론 엔진 그대로(비트 동일 경로) |
| lora | openpi pi05 LoRA 변형: SigLIP 전체(f32) + Gemma r16·전문가 r32 LoRA + 머리 | `Pi0Config(paligemma_variant="gemma_2b_lora", action_expert_variant="gemma_300m_lora")` 의 얼림 규칙 |

옵티마이저 상태(Adam m·v, EMA)는 `--offload` 로 핀 고정 호스트 메모리에 두고 스텝마다 GPU 로 흘려 같은 산술로 갱신한다.

시험한 구성(전체 크기 SigLIP 27·Gemma 18 층, 배치 32): expert·lora 각각 offload 2(m·v·EMA 호스트)·offload 1(EMA 만 호스트), 실제 데이터·증강 포함(`pi05_train`, fasttrain 로더).
GPU 메모리·한 스텝 시간은 이 PC 에서 다시 잴 것. (Windows 시절 기록은 [archive/windows/π05_네이티브엔진.md](archive/windows/π05_네이티브엔진.md) 참고.)

### 12.3 대조 (자른 판: 실제 radio 체크포인트의 SigLIP 2 층·Gemma 2 층, 배치 4, 10 스텝)

판정은 추론과 같게 우리 상대오차 ≤ 2 × 바닥(바닥 = 같은 JAX 계산의 CPU 대 GPU). 파라미터는 갱신량(p - p0)으로 비교.
정답 `tools/train_ref.py`, 대조 `tools/train_verify.cpp`, 기록 `data/pi05_train/s8~s9.log`.

| 모드 | 손실 | 기울기 | AdamW 1·10 스텝 뒤 갱신량·EMA |
|---|---|---|---|
| expert (19 텐서) | 3.1e-5 (바닥 7.9e-4) | 19/19 통과 (바닥의 0.8~1.4 배) | 1 점 빼고 통과 |
| lora (51 텐서, 층별로도 확인) | 4.3e-5 (바닥 9.7e-4) | 49/51 통과 | 2 점 빼고 통과 |

남은 점(모두 작은 값):
- LayerNorm scale 기울기 둘: SigLIP `encoder_norm/scale` 5.6e-3(바닥 2.3e-3, 2.5 배), 마지막 층 `LayerNorm_1/scale` 6.2e-3(바닥 3.1e-3,
  2.0 배 경계). 같은 LayerNorm 의 bias 기울기·그 뒤 Dense 기울기는 통과 — 원인 미확정(추정: Σ dy·x̂ 의 상쇄가 커서 상류 오차가 커 보임).
- 1 스텝 Adam 갱신: 1 스텝의 Adam 은 g/(|g|+eps) ≈ 부호라서 |g| 가 0 근처인 원소 하나의 부호가 바뀌면(`embedding/bias` 865 번,
  `time_mlp_in/bias` 1015 번) 그 원소 갱신이 ±lr 로 뒤집힌다. 10 스텝 뒤는 통과. EMA 1 ulp 차이 한 점.
- 난수·증강(`tools/aug_ref.py`, `tools/aug_test.cu`): 스텝 키 비트 일치, 잡음 99.6% 비트 일치(나머지 1 ulp), beta 시간 1 ulp 안,
  증강 영상은 JAX-CPU 와 같고 JAX-GPU 와의 차이는 JAX 자신의 CPU 대 GPU 차이와 같다(상대 3.6e-3).

## 13. 배치 추론과 제출용 서버 (09-30)

### 13.1 배치 추론 C API (`include/pi05_batch.h`)

- `pi05_create_batch(가중치, 장치, max_batch)`
- `pi05_infer_batch`: 판 n 개를 한 번에 추론.
- `pi05_act_batch`: 슬롯 n 개의 한 스텝.
  - radio 는 receding horizon.
  - 1위 모델은 공식 래퍼 로직을 네이티브로 옮겼다: 26→20 3차 보간, 4 개 유지 인페인팅, 단계 투표, 교정 규칙.
  - 행동 출력은 래퍼와 같은 f32 [n][23].
- 영상 입력: 평가기가 넘기는 그대로 받는다(RGB/RGBA, 원 해상도, stride, 호스트/장치). 224 가 아니면 openpi `resize_with_pad` 를
  정수 연산 그대로 옮겨 적용한다(장치 영상은 GPU 에서).
- 구조: 판마다 접두부는 단일 추론과 같은 CUDA 그래프로 돌리고, 잡음 제거 단계는 모든 판을 한 번에 돈다. 판별 split-K 분할을
  유지해서 비트 동일이다.
- 대조(`tools/batch_test.cpp`) — 모두 비트 동일:
  - n = 1/16/64/256 에서 모든 판이 단일 추론과 같다.
  - 엔진 난수 흐름 + 1위 인페인팅을 섞은 12 판이 순차 호출과 같다.
  - 래퍼 8 슬롯 × 40 스텝에서 `pi05_act_batch` 가 `pi05_act` 와 같다.

- 판 수별 처리량·엔진 GPU 메모리는 이 PC 에서 다시 잴 것. (Windows 시절 기록은 [archive/windows/π05_네이티브엔진.md](archive/windows/π05_네이티브엔진.md) 참고.)
- 병목은 판마다 도는 접두부다(968 토큰 × Gemma 2B ≈ 3.9 TFLOP). 옛 PC 에서 이미 손 GEMM 실측 상한 가까이 돌고 있어,
  비트 동일 조건에서 처리량 2 배는 목표에서 뺐다(09-30 결정).
- SigLIP 을 판 여러 개로 묶는 것도 해 봤다. 비트 동일은 유지됐지만 이득이 0 이고 메모리만 +0.45 GiB 라 되돌렸다.

### 13.2 제출용 정책 서버 (`server/pi05_server.cpp`, `server/Dockerfile`)

- 공식 평가기 프로토콜(`omnigibson/eval/utils/network_utils.py`)을 직접 짰다:
  - 연결 시 메타데이터, msgpack `__ndarray__` 관측, `{"action", "server_timing"}` 응답

  이미지 안에 Python 은 없다.
  - GPU 가 붙은 이미지 확인은 아직 안 했다(남은 일, 이 PC 에서).
- TitanRTX(Turing, sm_75) 대응은 14절.

## 14. Turing(sm_75, TitanRTX) 대체 경로

최종 재평가 GPU 예시에 TitanRTX(Turing)가 있다(제출지침 6절). Turing 에는 bf16 텐서코어(`mma.m16n8k16.bf16`)와 `cp.async` 가 없다.

- **선택: fp16 텐서코어**. 가중치는 bf16 그대로 둔다. GEMM 타일을 공유 메모리에 올리면서 bf16 → fp16 으로 바꾸고,
  `mma.m16n8k8.f16`(fp32 누산)으로 곱한다(`src/gemm.cuh`).
  - bf16 의 유효 비트 8 은 fp16 의 11 비트 안에 들어간다. 그래서 |x| 가 6.1e-5 ~ 65504 인 값은 변환이 정확하고, 곱도 bf16 경로와 같다.
    달라지는 것은 두 가지다. 아주 작은 값은 fp16 비정규수가 되어 아래 비트를 잃고, 65504 를 넘는 값은 포화된다.
  - GEMM 입력은 정규화된 활성값·확률·가중치·KV 라서 범위를 넘는 일이 드물다(대조에서 NaN·포화 흔적 없음).
  - fp32 CUDA 코어 경로도 생각했다. 하지만 TitanRTX fp32 는 16 TFLOPS 라 접두부 3.9 TFLOP 만으로 0.3 s 가 넘는다(추정).
    fp16 쪽은 bf16 경로와 곱이 같아서 정확도도 이쪽이 더 가깝다.
- **경로 선택**: 실행 파일에 sm_75 코드와 sm_80 이상 코드를 같이 넣었다(Dockerfile). 드라이버가 GPU 에 맞는 코드를 고르므로
  Turing 에서는 자동으로 fp16 경로가 된다. PDL(griddepcontrol)은 sm_90 이상에서만 켠다. 원소별 bf16 커널은 CUDA 헤더의
  sm_75 에뮬레이션으로 컴파일된다(sm_75 전체 빌드 확인).
- **정확도**: `-DPI05_FP16_MMA` 로 같은 코드를 bf16 텐서코어 GPU 에서 강제로 돌렸다(`data/pi05_native/fp16.log`).

| 지점 | fp16 경로 | bf16 경로 | 바닥(JAX CPU 대 GPU) |
|---|---:|---:|---:|
| radio 최종 행동, 정규화 (상대 L2) | 1.10e-2 | 2.24e-2 | 2.05e-2 |
| radio 최종 행동, 로봇 단위 | 1.61e-3 | 3.01e-3 | 3.02e-3 |
| 1위 모델 정규화 행동 (4 샘플 최악) | 3.39e-2 | 4.38e-2 | 3.56e-2 |
| 1위 모델 로봇 단위 | 1.42e-2 | 1.09e-2 | 5.55e-2 |
| 1위 인페인팅 호출 | 2.4e-3 | 1.9e-3 | 3.7e-3 |

  - 1위 모델은 전 지점 통과다.
  - radio 는 최종 행동이 바닥 안이다. 다만 초반 흐름 단계 몇 곳(s2~s6 의 x 등)이 바닥의 2.1~2.5 배다.
    교사강제 한 층 11 곳은 bf16 경로와 같은 이유(3.1 절)로 판정 밖이다.
  - 배치 API 는 fp16 빌드 안에서도 판 1 개 결과와 비트 동일이고, 래퍼도 비트 동일이다.
- **속도**:
  - fp16 경로를 강제로 돌리면 bf16 경로보다 느리다. 비동기 복사(cp.async) 대신 동기 로드를 쓰기 때문이다. 값은 이 PC 에서 다시 잴 것.
  - TitanRTX 추정: fp16·fp32 누산 텐서코어 130 TFLOPS(Titan 은 GeForce 처럼 절반으로 줄지 않음), 대역폭 672 GB/s.
    옛 PC 의 fp16 경로 실측을 계산량 비율로 옮기면 radio 약 150~250 ms, 1위 모델 약 170~280 ms 로 본다(추정, 실측 불가).
  - 평가기는 시뮬레이터 스텝 수로 시간을 재고, 정책 응답에는 벽시계 제한이 없다(클라이언트 ping timeout 300 s). 그래서 이 속도로도
    판정에는 영향이 없다. 전체 재평가 시간만 늘어난다.
- 주최 측 확인 질문은 [FAQ_공지.md](FAQ_공지.md) 6절 9번에 넣었다.

## 15. RTX 4090 에서 학습하기 (학교 4090, LoRA 학습용)

학교 4090(24 GB)으로 π0.5 학습(특히 LoRA)을 하는 절이다. 지금 작업 PC(16 GB)에서는 LoRA 학습을 하지 않는다. 설치·실행은 `tools/setup/train_4090.sh` 하나로 묶었다(파일 이름일 뿐).
**4090 에서는 아직 한 번도 돌리지 않았다.** 옛 PC 에서 만든 것이고, 아래 속도·메모리는 옛 PC 실측에서 옮긴 추정이다.
스크립트는 4090 용으로 sm_89(`FT_CUDA_ARCH=89`, `PI05_ARCH` compute_89)로 고정되어 있다. 지금 작업 PC(`jy-desktop`, RTX 5070 Ti, sm_120)용이 아니다.

### 15.1 준비물

### 15.2 순서

```
bash tools/setup/linux_setup.sh driver          # (처음 한 번) 드라이버, 재부팅
bash tools/setup/train_4090.sh deps             # CUDA 12.8 툴킷·Rust·uv
bash tools/setup/train_4090.sh repos            # 이 저장소 + openpi(behavior 브랜치 + 가속 로더 패치), uv sync
bash tools/setup/train_4090.sh fetch            # 데이터·체크포인트 (SRC=옛PC 면 rsync)
bash tools/setup/train_4090.sh build            # 엔진(sm_89)·학습기·fasttrain
bash tools/setup/train_4090.sh prepare          # 색표 만들기+확인, fasttrain 표, 엔진 가중치, 초기 학습 상태(expert·lora)
bash tools/setup/train_4090.sh verify           # GEMM·로더 짧은 확인
MODE=expert STEPS=30000 bash tools/setup/train_4090.sh train
MODE=lora   STEPS=30000 bash tools/setup/train_4090.sh train
STATE=~/pi05_runs/expert/state_step30000.pi05d bash tools/setup/train_4090.sh export   # openpi 체크포인트 + .pi05w
```

- 학습 설정은 openpi `pi05_b1k` 그대로다. 상태 파일에 들어 있어서 따로 줄 필요가 없다.
  - 배치 32, AdamW b1 0.9·b2 0.95·eps 1e-8·wd 1e-10, 기울기 전역 노름 1.0 으로 자르기
  - 학습률: warmup 1000 → 코사인 2.5e-5 → 30000 스텝에 2.5e-6. EMA 0.99, seed 42
  - 원래 `num_train_steps` 는 50000 이다. 30000 이 넘으면 학습률이 2.5e-6 으로 고정된다.
- **openpi `pi05_b1k` 는 원래 전체 미세조정이다.** 전체 미세조정은 24 GB 에도 안 들어간다(12.2 절, 약 66 GB).
  그래서 여기서도 expert 모드나 LoRA 모드 중 하나를 고른다.
- 저장·이어 학습: `--save-every`(기본 1000) 스텝마다 `state_stepN.pi05d` 를 쓴다(파라미터·EMA·Adam m/v·스텝 수).
  이어서 하려면 `STATE=<그 파일> bash train_4090.sh train` — 옵티마이저 상태와 학습률 스케줄 위치가 이어진다.
  LoRA 모드의 얼린 가중치는 원래 상태 파일에서 읽는다(`frozen_from`).
  - 데이터 섞기 순서는 이어진 스텝부터 새로 시작한다(openpi 도 재시작하면 로더를 새로 만든다).
  - 난수 키는 `fold_in(스텝)` 이라 스텝 번호가 같으면 같은 잡음·시간·증강이 나온다.

### 15.3 24 GB 권장 구성 (추정, 4090 기준)

| 모드 | offload | GPU 메모리 | 한 스텝(배치 32) | 30000 스텝 |
|---|---:|---:|---:|---:|
| expert | 0 (옵티마이저 상태 전부 GPU) | 약 15~16 GB | 약 1.6~1.8 s | 약 14~15 시간 |
| lora | 0 | 약 18~19 GB | 약 4.7~5 s | 약 40 시간 |
| lora | 1 (EMA 만 호스트) | 약 17 GB | 약 4.8~5.2 s | |

- 근거: 옛 PC 실측(12.2 절 구성)에 EMA·Adam 을 GPU 에 올린 만큼 더했다. 4090 의 bf16 텐서코어(fp32 누산) 약 165 TFLOPS 가
  옛 PC 손 GEMM 실측 상한의 약 1.8 배라고 봤다.
- 24 GB 에서는 호스트 offload 가 필요 없다: `OFFLOAD=0`(기본). 다른 프로세스가 GPU 를 쓰면 1 이나 2 로 올린다.
- 첫 스텝에 나오는 `profile per sample`(`PI05_TRAIN_PROFILE=1`)과 `GPU used` 로 실제 값을 확인해서 이 표를 고친다.
  GEMM 타일 선택이 옛 PC(sm_120) 기준이라 4090 에서는 최적이 아닐 수 있다.

### 15.4 학습 뒤 평가

1. `export`: 학습 상태 → openpi 체크포인트(EMA 파라미터 — openpi 가 저장하는 값, LoRA 는 기본 가중치에 합침 `--merge-lora`)
   → 엔진 가중치 `.pi05w`.
   - LoRA 합치기 수식은 openpi einsum 식과 같은 결과인지 작은 텐서로 확인했다(차 1e-14).
   - 실제 학습된 상태로 export 해 본 적은 아직 없다.
2. 평가: `pi05_server --weights X.pi05w` 를 띄우고 공식 평가기(`--policy websocket`)를 붙인다.
3. 기준선: 공식 radio 체크포인트 판(실행기록_베이스라인.md)과 같은 인스턴스·제한시간으로 비교한다.

### 15.5 학습 전에 정해야 할 것 (사용자 결정)

1. **학습 문장**: 이 데이터를 openpi 그대로 학습하면 모델이 받는 문장은 과제 **이름**("Task: turning on radio, State: …")이다.
   서빙(공식 `serve_b1k.py`, 우리 서버 기본값)은 **긴 문장**("Turn on the radio receiver that's on the table in the living room.")을
   보낸다(학습환경_가속.md 6절 1번).
   - 둘 중 하나로 맞춰야 한다: ① 학습 표를 긴 문장으로 다시 만들거나, ② 서버 `--prompt` 를 과제 이름 문장으로 바꾸거나.
   - 단계 문장(plan 4.1)을 쓸 거면 그 형식으로 표를 다시 만든다.
   - 네이티브 학습기는 표에 든 토큰을 그대로 쓴다. 표를 바꾸면 다음 `prepare` 가 새로 만든다.
2. **과제 범위**: 과제 0 만인지, 50·100 과제인지. 100 과제면 데이터 약 490 GB, 표 약 154 GB(추정)다.
   `orig.train_config` 의 `episodes`·`repo_id` 도 바꿔야 한다.
3. **모드**: expert(시각·언어 고정, 빠름) / LoRA(SigLIP 전체 + LoRA, openpi 의 저메모리 변형).
4. **시작점**: 공식 radio 체크포인트(이미 radio 로 학습됨) / openpi `pi05_base`(원래 `pi05_b1k` 시작점).
