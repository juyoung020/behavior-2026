# 학습 환경 가속 — π0.5 학습 데이터 파이프라인 (2026-09-29)

π0.5 학습(openpi `pi05_b1k`)에서 GPU 가 데이터를 기다리지 않게, 데이터 파이프라인(영상 디코딩 → 크기 조정 → 변환 → 묶기
→ GPU 전송)을 재고 NVDEC·CUDA 로 바꿨다. **조건: 학습 데이터는 원래 파이프라인과 비트 단위로 같아야 한다.**
π0.5 학습 자체는 이 PC(16 GB)로는 못 돌려서(LoRA 도 22.5 GB 초과, openpi README) 외부 GPU 에서 쓴다 — 5절.

- 코드: `src\fasttrain\` (접착부 파이썬, `csrc\` C++/CUDA, `ftprep\` Rust), 도구: `tools\ft_bench.py`(측정), `tools\ft_verify.py`(일치 검증),
  `tools\ft_run.sh`(WSL 실행기). openpi 쪽 스위치는 WSL `~/openpi` 로컬 브랜치 `fast-data`(커밋 c43d08d, push 안 함),
  같은 내용을 `src\fasttrain\openpi-fast-data.patch` 로도 둠. 측정 원자료는 `logs\fasttrain\*.json`.
- 측정 환경: RTX 5070 Ti 16 GB, Ryzen 9 9950X(32 스레드), WSL Ubuntu-22.04, 데이터는 WSL ext4 사본
  `~/data/2026-challenge-demos`(과제 0 turning_on_radio, 에피소드 200개, 샘플 429,928개). GPU·CPU 를 시뮬레이터 에이전트와
  같이 써서(측정 중 load 7~13) 원래 파이프라인 숫자는 조용한 기계보다 조금 낮을 수 있다(추정).

## 1. 원래 파이프라인과 측정

### 1.1 샘플 하나가 거치는 일

1. LeRobot 이 parquet 에서 그 프레임 행 + 행동 32개(action_horizon 32)를 읽는다 (lerobot `dataset_reader.py:292-302`).
2. **영상 6개**(RGB 3 + 깊이 3)를 스레드로 동시에 디코딩한다 (`dataset_reader.py:212, 281-283`). RGB 는 torchcodec(CPU),
   깊이는 PyAV 로 가고(`video_utils.py:80`) 로그 양자화를 되돌린다(`dataset_reader.py:263`). 키프레임 간격(GOP)은 8.
3. RGB 를 /255 해서 float32 로 (`video_utils.py:350`).
4. openpi 변환 (`data_loader.py:150-153, 214-222`): 과제 문장 → 키 재배치(여기서 **깊이는 버려진다**, `config.py:376-439` 의
   repack 은 RGB 3개·state·action·prompt 만 고른다) → `B1KInputs`(상태 61→23차원, 이미지 `(255*x).astype(uint8)`,
   `b1k_policy.py:44-50`) → 델타 행동 → 정규화 → **JAX 크기 조정 224²**(`transforms.py:185-191` → `image_tools.py:29`)
   → 토큰화(상태를 256칸으로 나눠 문장에 넣음, `tokenizer.py:26`) → 32차원으로 채움.
5. 워커가 32개를 `np.stack` 으로 묶고(`data_loader.py:527-531`) 메인이 `jax.make_array_from_process_local_data` 로 GPU 에 올린 뒤
   `Observation.from_dict` 가 uint8 → [-1,1] float 로 바꾼다(`data_loader.py:522, 594-596`, `model.py:118`).

- 워커는 `spawn` 8개(`config.py:610`, `data_loader.py:484-502`), 섞기 seed 42(`config.py:605`, `data_loader.py:488-489`).
- 실측: 워커 안에서 JAX 는 **GPU(cuda:0)** 를 쓴다 → 크기 조정이 워커마다 GPU 에서 돈다(워커마다 CUDA 문맥).

### 1.4 병목 상위 3개

1. **깊이 영상 디코딩 — 74 ms/샘플, 결과는 버려짐.** π0.5 는 RGB 만 쓰는데 LeRobot 이 영상 키 6개를 모두 푼다.
2. **RGB 영상 디코딩(CPU)** — 30 ms/샘플(하나씩), 원래 방식(6개 동시)에서는 영상 전체가 181 ms 로 늘어난다.
3. **JAX 크기 조정** — 16 ms/샘플. 원본 해상도 3장을 워커마다 GPU 로 보냈다 받는다(워커마다 CUDA 문맥).

그 다음: 묶기 26 ms/배치, GPU 전송 54 ms/배치(지금 속도에서는 병목 아님, 빨라지면 590 샘플/s 에서 막힌다), 행 읽기 4.4 ms/샘플.

## 2. 바꾼 것 — torch 없는 네이티브 로더

사용자 방침(09-29): "병목 제로", 뜨거운 경로에서 torch·라이브러리 걷어내기, GPU 일은 C++/CUDA, 나머지는 Rust, 파이썬은 얇은 접착부만.
처음 판(09-29 오후, 커밋 99a1d9b~5839055)은 torch DataLoader 워커 + torch 확장이었고, 지금 판(7f89e74~)은 아래처럼 torch 를 전혀 부르지 않는다.

### 2.2 병목마다: 없애는 방법 / 남는 것과 이유

| 병목 (원래 비용) | 없애는 방법 | 언어 | 남는 것과 이유 |
|---|---|---|---|
| 깊이 디코딩 (74 ms/샘플) | 안 푼다 — 원래도 repack 에서 버리므로 결과가 같다 | – | 없음 |
| RGB 디코딩 (30~181 ms/샘플, CPU) | **NVDEC 직접 호출**: Rust 색인(.ftidx)으로 목표 프레임 직전 키프레임~목표 패킷만 `pread` → cuvid 파서·디코더. 엔진 스레드마다 자기 디코더·CUDA 스트림, 작업 큐라 배치 경계에서도 NVDEC 이 쉬지 않는다 | C++ (드라이버 API, dlopen) | GOP 8 이라 목표 1장에 평균 4.5장을 풀어야 한다 — P 프레임이 앞 프레임에 기대므로 비트 동일을 지키려면 못 줄인다. 한계 = NVDEC 처리량 ⟨4절⟩ |
| YUV→RGB (swscale, CPU) | **색 변환 표**: 원래 출력이 (Y, 2×2 블록의 U, V) 의 함수임을 확인, 2^24 조합을 원래 디코더로 풀어 만든 50 MB 표를 GPU 커널이 조회 | CUDA (표: Rust 합성 + 원래 디코더) | 없음. 표는 그 기계의 FFmpeg 로 한 번 만든다(5절) |
| /255 → ×255 → uint8 왕복 | 표에 흡수 | – | 없음 |
| JAX 크기 조정 (16 ms/샘플, 워커마다 GPU 문맥) | **직접 짠 CUDA 커널** 2단계, 원래 cuBLAS 와 같은 덧셈 순서(시작 때 보정, 3.4) | CUDA | 시작 때 보정 약 4 초 |
| 파이썬 변환 8개 + 행 읽기 (4.6 ms/샘플) | 프레임마다 정해지는 것(상태 추출·정규화·토큰화·프레임 번호)은 **Rust 로 한 번**(43만 프레임 13.5 초, 파이썬이면 약 33 CPU·분, 100과제면 약 270 CPU·시간), 샘플마다 다른 것(행동 창 델타·정규화)은 **C++** 로 매 배치 | Rust + C++ | 없음 (전수 비트 동일, 3.6) |
| torch DataLoader·워커 프로세스·IPC | 없앰 — C++ 생산 스레드 1개 + 엔진 스레드 | C++ | 없음 |
| 섞기 순서 (torch randperm) | torch 와 같은 MT19937·randperm·시드 소비 순서를 C++ 로 (3.7) | C++ | 없음 |
| 묶기 (26 ms/배치) | 슬롯에 바로 써서 묶기 단계가 없다 | C++ | 없음 |
| GPU 전송 (54 ms/배치, 14.8 MB) | 이미지는 GPU 에서 만들어져 전송 0. 나머지 0.3 MB 는 고정 메모리에서 비동기 복사 | C++/CUDA | 없음 |
| JAX 로 넘기기 | DLPack 으로 복사 없이. 슬롯은 JAX 가 다 쓴 뒤에만 다시 쓴다(deleter) | C ABI + 파이썬 ctypes | 파이썬 호출 배치당 수십 번 (⟨4절에서 잰 값⟩) |
| GPU 가 데이터를 기다리는 시간 | 슬롯 링(기본 6)이 다음 배치들을 미리 만든다 | C++ | 학습 스텝이 배치 만드는 시간보다 길면 0 ⟨4절⟩ |

### 2.3 구성 요소와 언어

| 파일 | 언어 | 하는 일 · 이 언어인 이유 |
|---|---|---|
| `src\fasttrain\csrc\nvdec.cpp` | C++ | NVDEC 엔진. cuvid 를 라이브러리(torchcodec·FFmpeg) 없이 드라이버 API 로 직접(ffnvcodec 헤더, dlopen). 작업 큐 + 스레드마다 디코더·스트림 |
| `src\fasttrain\csrc\kernels.cu` | CUDA | 색표 조회 커널, 크기 조정 커널 2개 (`__fmaf_rn`·`__fadd_rn`·`rintf` 로 연산 순서 고정, `--fmad=false`) |
| `src\fasttrain\csrc\loader.cpp/.h` | C++ | 표(mmap)·섞기 순서·행동 창 계산·GPU 슬롯 링·생산 스레드·DLPack 텐서 |
| `src\fasttrain\csrc\capi.cpp`, `dlpack_min.h` | C++ | C ABI (`ft_loader_*`, `ft_table_*`, `ft_engine_*`, `ft_sampler_order`). 버퍼는 포인터로. torch·pybind11 없음 |
| `src\fasttrain\csrc\ftbench.cpp` | C++ | 로더 처리량을 파이썬 없이 측정 |
| `src\fasttrain\ftprep\` | Rust | `index`: mp4 상자 직접 읽기 → 패킷 표 + HEVC 매개변수(.ftidx). `table`: parquet(arrow) 읽기, 상태 추출·정규화·SentencePiece 토큰화(원래와 같은 C++ 라이브러리의 Rust 바인딩)·프레임 번호 → 프레임 표. `yuvgrid`: 색표용 합성 YUV |
| `src\fasttrain\build.sh` | bash | 소스를 WSL 쪽으로 옮겨(rsync) 빌드: nvcc + g++ → `libftcore.so`, cargo → `ftprep` |
| `src\fasttrain\fast.py` | 파이썬 | 접착부만: openpi 설정에서 표 스펙 뽑기, ctypes, DLPack 캡슐 → `jax.dlpack.from_dlpack`, openpi 로더와 같은 모양 |
| `src\fasttrain\calib.py` | 파이썬 | 크기 조정 보정 — **원래 JAX 함수**를 불러야 해서 파이썬(시작 때 한 번) |
| `src\fasttrain\lut.py` | 파이썬 | 색표 만들기·확인 — **원래 torchcodec 경로**를 불러야 해서 파이썬(기계당 한 번) |
| `src\fasttrain\orig.py` | 파이썬 | 원래 파이프라인을 이 PC 경로로 세움 + 검증 기준(`NonImageRef`) |
| `tools\ft_verify.py`, `tools\ft_bench.py` | 파이썬 | 기준 쪽이 원래 openpi·JAX·torchcodec(파이썬에만 있음)이라 파이썬. 네이티브 쪽은 C ABI 로 부르고, 네이티브 한계는 C++ `ftbench` 로 |

학습 중 매 배치 도는 경로의 라이브러리: 디코딩·색·크기 조정·행동 창·묶기·전송 모두 직접 짠 C++/CUDA. 파이썬은 배치당 ctypes 1번 +
DLPack 10개, JAX 는 원래와 같은 `Observation.from_dict`(uint8→float, `model.py:118`)만. torch 는 부르지 않는다
(openpi `train_b1k.py` 가 `data_loader.py` 를 import 하면서 torch 를 불러오긴 한다 — 우리 경로는 안 쓴다).

### 2.4 설치한 것 · 작업 파일

- 시스템에는 아무것도 설치하지 않았다. CUDA 는 `/usr/local/cuda-12.8` 을 직접 지정(`build.sh`, `CUDA_HOME` 으로 바꿈).

## 3. 일치 검증 — `tools\ft_verify.py` (JSBSim `fdm_verify --check` 와 같은 틀)

판정은 텐서마다 **비트 동일 / 허용오차 안(최대 |오차|) / 다름**. 기준은 원래 파이프라인이 같은 인덱스에서 낸 텐서.

### 3.1 원래 파이프라인 자체의 성질 (실측)

| 질문 | 결과 |
|---|---|
| 무작위 증강이 있나 | 데이터 파이프라인에는 없다. 증강은 학습 스텝 안(`model.preprocess_observation`). 섞기는 seed 42 고정 |
| 워커 안 JAX 는 어디서 도나 | GPU(cuda:0). spawn 워커에서 확인 |
| JAX 크기 조정 CPU vs GPU | 한 프레임 150,528 값 중 **4개가 1 다르다** → 기준은 GPU(원래가 실제로 도는 곳) |
| 새 프로세스에서 다시 | 같은 해시(3번) |
| 여러 장을 묶어 크기 조정 vs 한 장씩 | 원래는 샘플마다 한 장씩이다(`transforms.py:190`). 묶으면 GEMM 모양이 바뀌어 split-K 가 달라질 수 있다 — 처음에 16장 묶음을 기준으로 잡았다가 480² 파일에서 2.4M 값 중 4개가 어긋났고, 그 4개는 한 장씩 보정한 경계로는 설명되지 않았다. 직접 비교 ⟨GPU 진단 뒤⟩ |
| 두 프로세스에서 고정 인덱스 전체 텐서 | ⟨3.8⟩ |
| 섞기 순서를 torch 없이 재현할 수 있나 | 된다 (3.7) |

→ **원래 결과는 기계에 따라 달라질 수 있다**: 크기 조정은 GPU 기종·cuBLAS 버전(3.4), 색 변환은 그 기계 FFmpeg 빌드에 달려 있다.
그래서 가속판은 고정값을 박지 않고, 학습하는 그 기계에서 시작할 때 원래 함수로 보정·점검한다.

### 3.2 mp4 패킷 색인 (Rust) — `ft_verify.py index`

Rust `ftprep index` 가 mp4 상자를 직접 읽어 만든 패킷 표(위치·크기·키프레임·표시 시각)를 libavformat(PyAV) 이 읽은 것과 대조:
RGB 영상 10개 파일, 패킷 **1,289,784 개 모두 같다**. 모든 파일이 GOP 8, 표시 순서 = 디코딩 순서(B 프레임 없음).

### 3.3 색 변환 (NVDEC YUV + 표 vs 원래 torchcodec + float 왕복)

- torchcodec 의 RGB 는 (Y, 가까운 U, V) 의 함수다: 실제 프레임 2장(720², 480²) 70만 픽셀에서 같은 (Y,U,V) 가 다른 RGB 를 낸 경우 0.
  부동소수 BT.601 공식과는 최대 3 다르다(고정소수점 경로라서) → 공식이 아니라 표.
- 표 만들기 9 초: Rust `yuvgrid` → FFmpeg libx265 무손실 → 원래 torchcodec + /255 + ×255 → 표. 720 폭(filtergraph 경로)과
  480 폭(swscale 경로) 표가 같다(2^24 중 다른 것 0).
- 확인: 실제 프레임 36장(35M 값)에서 PyAV 로 푼 YUV + 표 = 원래 결과, 다른 값 0 (`lut.py check`).

### 3.4 크기 조정 — 덧셈 순서 보정

원래 크기 조정을 XLA 가 컴파일한 프로그램(HLO)은 cuBLAS SGEMM 두 번이다: 행 방향 `T[i,(w,c)] = Σ_h W[h,i]·X[h,(w,c)]` →
열 방향 `O[(i,c),j] = Σ_w T·W[w,j]` → round-half-even → [0,255] → uint8. 가중치는 탭 5~7개짜리 띠.
처음에 "k 오름차순 FMA" 로 짠 커널은 480² 파일에서 2.4M 값 중 4개가 1 달랐다. 원인: cuBLAS 가 **split-K**(k 를 구간으로 나눠
따로 더한 뒤 합침)를 고르는데, 나누는 곳이 모양·GPU·cuBLAS 버전에 따라 다르다. 이 PC 에서 알아낸 경계(입력 좌표):

| 입력 | 행 방향 (1단계) | 열 방향 (2단계) |
|---|---|---|
| 720² | 360 | 60, 120, …, 660 (60 간격) |
| 480² | 240 | 96, 192, 288, 384 |

보정(`calib.py`, 약 4 초): 원래 jit 함수에 float32 탐침 영상을 넣는다(uint8 판과 GEMM 호출이 같음을 HLO 로 확인 — 축·stride·작업공간 동일).
행을 16칸마다 하나만 채우면 1단계가 곱 하나라 2단계 순서만 보이고, 열을 16칸마다 채우면 반대다. 출력마다 "몇 번째 탭부터 새 구간"
인지 찾고, 모형(구간마다 순차 FMA, 두 구간을 더함)으로 설명 안 되는 출력이 하나라도 있으면 멈춘다. 이어서 uint8 무작위 영상
48장으로 원래 함수 vs 커널을 대조해 0 이 아니면 멈춘다(실측 0).

## 5. 외부 GPU 에서 쓰는 법

전제: NVIDIA 드라이버에 NVDEC(`libnvcuvid.so.1`)가 있을 것(데이터센터 GPU 대부분 있음, A100 NVDEC 5개·H100 7개 — 이 PC 보다
디코딩 여유가 크다(추정)). CUDA 툴킷(nvcc), 시스템 FFmpeg(+libx265, 색표 만들 때만), Rust.

```bash
# 0) 코드
git clone <behavior-2026>   # src/fasttrain, tools
cd ~/openpi && git checkout -b fast-data && git am <behavior-2026>/src/fasttrain/openpi-fast-data.patch   # train_b1k.py 20줄
uv pip install ninja
export PYTHONPATH=<behavior-2026>/src FT_WORK=~/fasttrain_work
git clone --depth 1 https://github.com/FFmpeg/nv-codec-headers $FT_WORK/third_party/nv-codec-headers
CARGO_TARGET_DIR=$FT_WORK/target cargo build --release --manifest-path <behavior-2026>/src/fasttrain/ftprep/Cargo.toml
# 1) 이 기계에서 색표 만들기·확인 (원래 색 변환은 그 기계 FFmpeg 에 달려 있다)
python <behavior-2026>/src/fasttrain/lut.py build && python <behavior-2026>/src/fasttrain/lut.py check
# 2) 이 기계에서 일치 검증 (크기 조정 보정은 로더가 시작할 때마다 자동)
FT_CUDA_ARCH=9.0 python <behavior-2026>/tools/ft_verify.py stage        # 기종에 맞는 아키텍처 (H100 9.0, A100 8.0)
python <behavior-2026>/tools/ft_verify.py ref --tag a && python <behavior-2026>/tools/ft_verify.py check --tag a
# 3) 학습 — 원래 명령에 FT_FAST_DATA=1 만 더한다
FT_FAST_DATA=1 FT_CUDA_ARCH=9.0 XLA_PYTHON_CLIENT_MEM_FRACTION=0.85 \
  uv run scripts/b1k/train_b1k.py pi05_b1k --exp_name=... --data.repo_id=... --data.base_config.dataset_root=... --num_workers=4
```

- `CUDA_HOME` 기본값은 `/usr/local/cuda-12.8`(`fast.py`) — 다른 기계에서는 환경변수로 준다.
- JAX 가 GPU 메모리를 90 % 미리 잡으면 엔진(색표 50 MB + NVDEC 표면·버퍼 수백 MB, 추정)이 모자랄 수 있어 0.85 권장.
- 데이터셋 인자는 원래와 같다: 일부 과제만 받았으면 원래 로더처럼 `dataset_kwargs` 에 `episodes` 를 줘야 한다(`orig.py` 참고).
- 여러 GPU: 지금은 GPU 0 에서 배치 전체를 풀고 `device_put` 으로 나눈다. GPU 마다 엔진을 두는 것은 아직 안 했다.
- 깊이 영상을 쓰는 모델로 바꾸면 깊이 디코딩(12비트 흑백 HEVC)을 따로 다뤄야 한다 — NVDEC 이 4:0:0 을 지원하지 않아 CPU 로 남을 가능성이 크다(추정).

## 6. 사용자에게 물을 것

1. **외부 GPU 가 무엇인가** — 기종·장수·드라이버·CUDA 버전·CPU 코어 수. 아키텍처(`FT_CUDA_ARCH`)와 NVDEC 여유가 달라지고,
   그 기계에서 색표 만들기(`lut.py build/check`)와 `ft_verify.py` 를 한 번 돌려야 한다.
2. **"원래와 같다"의 기준을 "학습하는 그 기계에서 원래 openpi 가 내는 텐서"로 잡아도 되나** — 원래 결과 자체가 기계마다
   드물게 달라진다(크기 조정: GPU 기종·cuBLAS 의 split-K / 색 변환: 그 기계 FFmpeg). 가속판은 시작할 때 그 기계의 원래 함수로
   보정·점검하고, 안 맞으면 멈춘다. 이 PC 에서 만든 텐서를 다른 기계 결과와 비교하면 드물게 1 차이가 날 수 있다.
3. **학습 범위** — 과제 0 만인지, 50·100과제인지(전체 3 TB, 영상 파일 약 1.7만 개). 여러 과제면 데이터 받는 범위와
   데이터셋 인자(에피소드 목록)를 정해야 하고, 색인(.ftidx)은 파일당 0.01 초라 문제없다.
